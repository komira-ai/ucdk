# ucdk release: permissions

Status: design (Proposal). This page is the full text of section 6 of [release.md](release.md). It says how a release machine gets permission to stage and to commit a set in a channel, what it records about each grant, and what happens when a grant is refused, expired or already used. Section numbers below without a file name are those of release.md.

## 1. What needs a grant

Only an action that writes to a channel, reads a private part of it, or reads staged state needs a grant. A build, a test, a validation and a stranger's read of a `PUBLIC` repository (the read-back and a Smoke action there) need none. **Staged state is never readable by a stranger**, so the observations that decide a publish carry the action's grant on every repository, `PUBLIC` ones included: a `PUBLIC` repository read anonymously would answer `Absent` for a coordinate that is staged, and the commit would be refused for a staged state it could not see.

| Effect | Grant | Why |
|---|---|---|
| Publish action, stage phase: the preflight observation of the action's coordinates on any repository, the observation after `stage`, `stage` | the **stage grant**, scope `Federated.stage_scope` | puts bytes in the channel where nothing can read them, and sees them |
| Publish action, commit phase: the observation before the commit on any repository, and `commit` | the **commit grant**, scope `Federated.commit_scope` | makes the set readable and permanent |
| Smoke action on a `PRIVATE` repository, a stage-level `CHANNEL_READBACK` of a `PRIVATE` repository, and the read-back inside a Publish action's own commit phase (5.2, step 5) on a `PRIVATE` repository | the **read grant**, scope `Federated.read_scope` | it reads what the commit made and can neither stage, abort nor commit, so a read is never the authority to make a set permanent |
| The read-back inside a Publish action's own commit phase (5.2, step 5) on a `PUBLIC` repository | none (`Grant::none()`, a stranger's read) | it reads what a stranger is served; the stage and commit grants are never used for a read-back |
| `ucdk release abort` | a stage grant | it undoes what the stage phase did and makes nothing readable |
| `ucdk release yank` | a commit grant for the one coordinate | it changes what is published |
| A channel that does not stage (`Publisher::stages()` is false) | the commit grant only, covering the write | there is no stage phase |
| `Anonymous` push identity | none | the channel needs no authority to write |

**The grants are separate on purpose.** The stage grant is never presented for a commit, and the commit grant is exchanged after the stage phase, as late as possible, so the authority to make a set permanent exists for the shortest time and only for a set that was validated (in the preflight, before any exchange), staged and observed. The read grant exists so that reading a private repository does not borrow that authority: its scope is its own (it may equal another scope only where the issuer has one scope for everything, and then the declaration says so).

**A read grant's request and record.** A read grant covers the coordinates of one read in one repository, at most `Publisher::grant_limit`; a read of more coordinates than that is several grants, each its own exchange and record, because a read changes nothing. Its `grant` record is named `<stage>/<holder>/read/a<attempt>-<n>`, where the holder is the Smoke action, or `validation:<name>` for a stage-level validation, which belongs to no action (a name cannot contain `:`, so the two never collide). Tests: `grant::a_read_grant_is_exchanged_per_repository_with_the_read_scope`, `readback::a_stage_level_readback_on_a_private_repository_reads_with_a_read_grant_and_never_a_commit_grant`, `smoke::a_smoke_action_on_a_private_repository_reads_with_a_read_grant_and_never_a_commit_grant`, `credential::a_read_grant_cannot_stage_abort_or_commit`, the grant-source kit scenario `a_read_grant_carries_the_read_scope_and_covers_exactly_the_coordinates_asked`, `codec::grant_record_carries_the_read_phase_and_the_validation_holder_name`.

**What each grant reads.** A stage grant and a commit grant are for `observe`, the one read that shows them the staged state they made (told the set it was staged in, on a registry that addresses staged state by group). Their `fetch`, `newest` and `list` find nothing of staged state, and a `PRIVATE` repository may refuse those three to them with `GrantRefused(Denied)` instead; the publisher kit accepts either. A read grant is for reading and is never refused a read of its repository. A `newest` and a `list` name no coordinate, so any good grant of the repository, whatever coordinates it names, serves them: the coordinates a read grant names limit `observe` and `fetch`, and not a listing of the repository. A read of a `PUBLIC` repository needs no grant, but a grant that is presented is checked like any other, and a bad one (for another repository, expired, or naming no coordinate asked about) is refused with `Denied` or `Expired`. A stranger is refused every read of a `PRIVATE` repository, of what it holds and of what it does not, a coordinate, a name or a prefix nobody holds included, so that no answer tells it which packages exist.

## 2. The model

**What a channel declares.** Each repository of a channel carries a `PushIdentity`. `Federated` is the declaration of the identity the channel trusts to push:

| Field | Meaning |
|---|---|
| `subject` | the identity as the issuer states it, for a CI platform the `sub` claim of the job's identity token |
| `audience` | the audience the identity token must be issued for, which the channel's issuer checks |
| `environment` | the CI environment the publishing job runs in; a stage that publishes here has this `environment` (`machine.environment_mismatch`) |
| `exceptional_subject`, `exceptional_environment` | the identity and environment of an exceptional run off the mainline (5.6); a different identity, so the trust of an exceptional run is separate |
| `pinned_claims` | other claims of the identity token that the issuer pins (numeric ids, the workflow file, the ref, the event); ucdk compares them exactly and interprets none |
| `stage_scope`, `commit_scope` | the scope names the issuer grants for each phase; both are required and may be equal for an issuer that has one publish scope |
| `read_scope` | the scope name the issuer grants for a read of a `PRIVATE` repository (a Smoke action, a stage-level read-back); required on a `PRIVATE` repository and refused on a `PUBLIC` one, whose reads are anonymous (`machine.federated_shape`) |

**ucdk may be stricter than the issuer and never looser.** Before any exchange, the grant source compares the claims of the job's own identity token with `subject`, `audience`, `environment` (or the exceptional pair) and `pinned_claims`; a difference is `GrantRefused(Denied)` with the first differing claim named, and the identity token is dropped unspent. The issuer remains the authority: passing the local check proves nothing to it.

**What is exchanged.** The CI platform gives the job a short-lived, signed identity token on request, for an audience the job names; every request returns a new token and the issuer accepts each one **once**. The grant source sends one identity token and the list of coordinates (names and versions) of the action, and the issuer answers a **grant**: a short-lived token that carries the scope and exactly those coordinates, acting as the identity the channel trusts. The grant is a `Grant` value that is neither `Debug` nor `Display`, cannot be cloned or serialised and zeroes on drop. It carries the expiry the issuer stated and nothing else ucdk reads. One grant covers one phase of one action: it is never presented in the other phase or for another action, and a grant that is expired or whose identity token was already used is replaced, never retried.

**What a run does, for a Publish action on a channel that stages.**

1. Every local check, including the claims comparison, `Publisher::grant_limit` and the action's own validations (`SET_CLOSURE`, a pure check of the set that runs here and not between the phases), makes zero exchanges and zero calls if it refuses.
2. A `grant` record `Intent` (phase `stage`) is written; both held leases are renewed; the stage grant is exchanged; the answer is recorded. This is the last step of preflight, because the first observation of the action's coordinates (which tells a coordinate that is staged from one that is absent) carries the stage grant on every repository.
3. The coordinates are staged; the stage grant is dropped.
4. A `grant` record `Intent` (phase `commit`) is written; the commit grant is exchanged with a **new** identity token and the same coordinates; the answer is recorded.
5. The staged state is found by observation with the commit grant, and the commit is made.
6. The commit grant is dropped when the commit is made.
7. On a `PRIVATE` repository a **read grant** is exchanged for the read-back (its own `grant` record, holder the Publish action, never the commit grant); on a `PUBLIC` one there is no exchange and the read-back is made as a stranger. The read-back is polled and its bytes fetched with that grant.

**The margin.** Before each call the engine uses a grant only while its stated expiry is later than the ledger's clock reading plus `GRANT_MARGIN`, 30 seconds; otherwise it exchanges again first and records the exchange. The expiry is on the issuer's clock and the reading is on the one clock ucdk has, the ledger's, so the margin covers the permitted skew between them (`MAX_CLOCK_SKEW`, 5 seconds) and the time a call takes to reach the registry. Two limits are stated. A grant that is already inside the margin when it is issued (an issuer lifetime shorter than the margin, or a clock far ahead) is exempt from the margin check for the rest of its phase: it serves every call of that phase (the observations, the stage or commit call, a retry, an abort, the polls) with the one exchange that made it, because another exchange would give the same answer. The registry's own `Expired` refusal is then the backstop, and that refusal is an expiry answer like any other (it counts against `Publish.attempts`, 5.2). **An exchange made because of the margin is not an answer to a refusal and does not count against `Publish.attempts`; it is bounded by the rule above**: each margin exchange yields either a grant that is good for longer than the margin, which is exchanged again only after real time has used its lifetime, or a short one, which is exempt, so a phase makes one exchange plus at most one more per issuer lifetime that its calls span. Each exchange, margin or not, writes its own `grant` record. And a clock that is behind the issuer's makes ucdk exchange early, which costs an exchange and no correctness. Tests: `grant::a_grant_inside_the_margin_is_exchanged_again_before_the_call`, `grant::a_short_lived_grant_serves_every_call_of_its_phase_with_one_exchange` (an issuer lifetime under the margin and a phase of observe, stage, observe: the fake issuer saw exactly one exchange for the phase and the ledger holds one `grant` record for it), `grant::a_margin_exchange_does_not_count_against_the_attempt_bound` (a phase that exchanges for the margin more often than `Publish.attempts` still makes every call it needs, and an `Expired` refusal still counts), `grant::a_clock_ahead_of_the_issuer_recovers_through_the_registrys_refusal_within_the_bound`, `grant::a_clock_behind_the_issuer_exchanges_early_and_still_commits`.

**A grant is not single-use; the identity token is.** One grant serves the several calls of its phase (observe, stage or commit, a retry, an abort) and none of another phase or action. If an issuer's grant is itself single-use, a second call answers `GrantRefused(Used)` and the engine exchanges again, which is the same path as an identity token that was spent.

A call that is refused for an expired or spent grant (`GrantRefused(Expired)` or `GrantRefused(Used)`) makes the engine exchange again, observe, and go on from what it saw, as many times as `Publish.attempts` allows (5.2).

## 3. Bootstrap

**Nothing standing.** ucdk holds no long-lived credential and no stored secret: there is none in the repository, the machine, the ledger or the store. It reads the CI platform's identity-token request variables in-process and nowhere else, and they never reach a child process, because a child gets only the environment the machine names (4.2). No grant or identity token enters any hash: the machine hash covers the declared `Federated` fields, which are not secret, and nothing an issuer returned (`grant::no_issued_value_enters_any_hash`). An error text that echoed any 16-byte run of a credential is withheld (`credential::an_error_echoing_a_sixteen_byte_run_of_a_token_is_withheld`).

**Bootstrap is the one-time step an administrator takes, with their own credentials, to create the trust on the channel.** ucdk has no verb that writes trust and never takes the administrator's credentials. What the administrator must create is exactly what `ucdk release trust --machine <file>` prints, per channel and repository: the channel, its kind and location, the artifact type, the `subject`, `audience`, `environment`, the exceptional pair if any, every `pinned_claims` pair in sorted order, the scope of each phase, and the artifact names the machine publishes. For a package registry this is: register the CI identity (those claims) as an allowed publisher on the registry, with the registry's own tooling; make sure the package names exist, or may be created by that publisher, as the registry requires; if the registry gates group or staged publication, enable it for the publisher; and protect the CI environment named by `environment` so that only the intended branch and reviewers can run in it. Then `ucdk release plan --check-credentials` exchanges a grant for each phase and discards it, and reports for each one of `MINTED`, `NOT_UNDER_PLATFORM` (the job has no identity token to give), `NOT_FEDERATED` (the push identity is `Anonymous`) or `REFUSED` with the issuer's code; only `MINTED` is a pass.

## 4. When a grant is refused, expires or was already used

**Between the stage and the commit.** The stage grant is dropped when the stage phase ends, and the commit phase does not use it, so its expiry between the two is invisible: the commit exchanges its own grant. The risk that remains is not an expired grant but a staged state that did not survive (a registry that expires an open staging area, or someone who aborted it). That is found by observation, never assumed: before the commit, every coordinate is observed with the commit grant, and a coordinate that is not `Staged` with the set's digest is `REFUSED` with `PUBLISH_STAGE`, nothing committed (5.2 step 2). Both halves are executable: `publish::stage_grant_expiry_before_commit_is_invisible_the_commit_uses_its_own_grant` (the shared clock moves past the stage grant's expiry between the stage and the commit, a slow stage phase or a wait, and the commit still succeeds on its own grant), `publish::staged_state_reaped_between_stage_and_commit_is_refused_and_a_rerun_stages_again` (the fake registry loses the staged state, the commit is refused with nothing committed, and the rerun stages and commits) and `publish::a_rerun_after_the_staged_state_vanished_stages_and_commits_each_coordinate_once` (the rerun is idempotent: every coordinate is committed once).

**Between the commit exchange and the commit call**, or during the read-back. The registry answers `GrantRefused(Expired)` (or the engine sees the stated expiry has passed). The engine writes a new `grant` record, exchanges a **commit-scoped** grant again with a fresh identity token, observes (`Staged` with our digest commits again; `Present` with our digest is read back; anything else is refused as in 5.2) and goes on. A stage-scoped grant is never substituted.

**A grant that lacks the scope a call needs.** The issuer or the registry refuses the call (a `403` or its equivalent), and that is `GrantRefused(Denied)`: `REFUSED` with `CREDENTIAL`, nothing written (`publish::a_grant_without_the_needed_scope_is_denied_and_nothing_is_written`, and the grant-source kit scenario `a_missing_scope_is_denied`). Where the two scope names are equal no call can lack the scope, which is the discipline-only case of section 5.

**An issuer that cannot be reached, or an identity token that cannot be had.** An exchange that gets no answer, or a job whose platform can no longer issue an identity token (its request credential outlived the job's, say), is `GrantRefused(Unreachable)`. Nothing reached the registry. The engine exchanges again, within the same `Publish.attempts` bound, and then stops `REFUSED` with `CREDENTIAL` (`PARTIAL` when anything is staged or committed); each exchange is its own `grant` record, with `fault` `unreachable` once answered (`grant::an_unreachable_issuer_is_retried_within_the_bound_then_refused`). Outside a run, `plan --check-credentials` reports the same condition as `NOT_UNDER_PLATFORM`.

**An identity token already used.** An exchange that the issuer refuses because the identity token was spent (for instance a retry of an exchange whose answer was lost) is `GrantRefused(Used)`: the grant source asks the platform for a new identity token and exchanges again, within the same bound. Each exchange is its own `grant` record.

**What is recorded in the ledger.** Per grant, in the run ledger, a `grant` record named `<stage>/<action>/<phase>/a<attempt>-<n>` (3.3):

- **Before the exchange**, state `Intent`: `phase`, `channel`, `repository` (the artifact type), `subject`, `audience`, `scope`, and a digest of the sorted coordinates the grant is for. This says that an exchange may have been made, whatever its answer.
- **After the exchange**, state `Confirmed`: `outcome` `granted` with `expires_ms` (the issuer's stated expiry), or `outcome` `refused` with `fault` `denied`, `expired`, `used` or `unreachable`.
- **Never** the grant, the identity token, an issuer's token id or any value of the claims beyond the declared `subject`, `audience` and scope names; the record codec has no key for them (`codec::payload_keys_are_a_closed_list`), so no code path can write one. A `grant` record is audit data: a `Confirmed` one is never re-opened, and an exchange whose answer was lost stays `Intent` and is simply exchanged again by the next run (a token that was issued and never used expires).
- The `publication` records carry `phase` (`staging` or `committing`) while they are an `Intent`, so a reader knows which effect may have landed. The grant records say which authority was asked for; the publication records say what was done with it.

**What the run reports when the exchange is refused.** The action is `REFUSED` with `Reason.CREDENTIAL`, exit class 3, when nothing landed; it is `PARTIAL`, exit class 6, with `Reason.CREDENTIAL` when any coordinate is staged or committed, because those landed. The message names the phase, the channel and repository type, the scope, the `subject` and `audience` that were declared, the fault class and the issuer's own error code, and says what remains: for example `commit grant refused for channel registry, repository FILE: denied (an issuer code, here the illustrative `oidc_not_trusted`; issuer codes are quoted verbatim and ucdk interprets none); subject repo:example-org/ucdk:environment:publish, audience packages.example.com, scope publish; nothing was committed; 2 coordinates remain staged (run again to commit, or run ucdk release abort)`. It never contains a token, and an error text that echoed any 16-byte run of one is withheld. The effects list has `STAGED` for each coordinate that is staged. Zero registry writes follow a refused exchange.

**Leftovers.** A job that dies between the stage and the commit leaves staged state, which holds registry resources until the registry's own deadline. The next run of the same stage observes it and goes on; a job that runs when the release failed gives it back with `ucdk release abort`, which exchanges a stage grant and calls `abort` for the coordinates that are `Staged` with the digest of the set, and never touches a committed one.

## 5. What this does and does not give

- **Enforced by the issuer.** That only the declared identity, in the declared environment, can obtain a grant; that a grant covers only the coordinates it was exchanged for and expires on its own; that an identity token works once.
- **Enforced by ucdk.** That the two phases use two grants; that a stage grant never reaches a commit; that a grant is never printed, cloned, logged or recorded; that nothing is exchanged before a local refusal; that a call whose grant is for another repository, has expired, is of another phase or does not name the coordinates of the call is refused before it is sent, so that the secret of a grant is never presented to a registry it was not issued for (the publisher kit counts what is sent, `PublisherRig::sent`); that a code-running action (a Build or Test action) never runs in a stage that can present a grant (`machine.publish_stage_runs_code`, section 6 of release.md).
- **A discipline, not a guarantee, on some issuers.** An issuer whose grants carry one publish scope for both phases (the two scope names are equal) does not stop a stage grant from committing: the separation then rests on ucdk's own use of the grants. The declaration says so by listing the same scope twice, and `ucdk release trust` prints that fact. An issuer that can mint stage-only grants makes the split enforceable by changing the declared scope names, with no engine change.
- **Short lifetimes are a fact of the issuer.** Grants live for minutes. An action whose phases take longer than one lifetime exchanges again; the bound is `Publish.attempts`, and a stage of very many coordinates is limited by `Publisher::grant_limit` and refused before any exchange when it exceeds it.
