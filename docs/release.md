# ucdk release: build, test, publish

Status: design. **Exists** means the code is on `main` today. **Decided** means a project decision that this document records. **Proposal** means a decision for review with no code yet. Sections 0 and 3.1 are Decided, and where a section below states a rule as a decision (marked "Decided here") the project has taken it and the test that holds it is named, and the statements in 3.1 about today's code are Exists (each was checked against `main` when this was written). Everything else is Proposal. Section 3 says, crate by crate, what stays and what goes, so the deletion pull request that follows this one is a mechanical list. Section 1.1 says what the build-system model of section 0 changes in the rest of the design, and section 1.2 gives the project's own first machine as a worked example. The permission model (how a release machine is allowed to stage and to commit, per channel) is in [release-permissions.md](release-permissions.md); section 6 summarises it. The full testing plan is in [release-testing.md](release-testing.md); section 8 summarises it.

## 0. Project decisions recorded here (Decided)

- The deployment side of ucdk is deleted and stays recoverable from git history. There are no real cloud providers for now.
- The release process is the priority. ucdk gains build, test and publish actions, with artifacts, release sets and channels.
- Fakes come first. A fake build system, a fake registry and a fake grant source are the executable specification, as the fake provider was for deployment.
- The release machine is not modelled on the deploy engine to keep that engine. It reuses what fits: the ledger with lease and fence, the write-ahead intent pattern for the one action that writes somewhere ucdk does not own (publish), the Kahn ordering, the length-framed hash, the C ABI pattern, the generator and the gates. Nothing else.
- **Builds and tests run only through a supported build system, Buck2 or Bazel.** A build is the build system pointed at a target. A test is the build system pointed at another target. ucdk never knows how the build system schedules work or picks hardware: a build system that sends actions to a remote execution farm gives a test the hardware it needs, and that is the build system's concern. ucdk has no compute model, no hardware field and no builder that is an arbitrary command.
- **A machine defines its build system once** (`BuildSystem`: kind, binary, config file and mode, base flags, base environment). **Each build artifact names its target** with per-target flags and environment, **and each test action names its targets** the same way, both layered on the build system's by the one rule of 2 (order, override versus append, environment conflicts, what is hashed).
- **Publish is generic over channels.** A channel has a kind that selects an implementation and nothing else; no kind is special-cased in the engine. The first kind the project uses is a package registry; others follow (4.3).
- **Every stage is an ordered list of actions, and every action has its validations attached** (1, 2): a build action carries the validations of the set it made; a test action carries none, because its target is its validation; a publish action carries the validations that run between staging and commit; a smoke action reads back what was published and carries the validations of that read; the stage carries the validations that run after its last action. Each action is followed by its validations, except a Publish action, whose validations run between its stage phase and its commit phase (5.2). **A stage is confirmed only when every action and every validation, at both levels, is `SUCCEEDED` or `NOOP`**; the `stage` record that says so is written last, and stage admission reads it (3.3, 5.7).
- **Permissions are per action and per phase.** A channel declares the identity it trusts and the scope each phase needs; staging and committing are separate grants; at run time the CI job's identity token is exchanged for a short-lived scoped grant for one phase of one action; nothing standing and no secret in the repository or the ledger; bootstrap is the one-time step an administrator takes with their own credentials (6, [release-permissions.md](release-permissions.md)). The identity token is single use and the grant is short-lived and scoped to one phase of one action; where an issuer has one scope for both phases the split is ucdk's own discipline and the declaration says so (6).
- **An on-demand compute scheduler is a separate project** and does not block ucdk.
- Sequence: (1) this design, (2) one deletion pull request, (3) the release pull requests (section 11).
- No earlier release PR changes a byte of the ledger format: PRs 5 to 8 write format 1.1, and the one format change (1.1 to 1.2, two new state names) lands in its own pull request, PR 9 (3.3).
- A stage has one platform, and a release for several platforms is several stages under one run id (one BUILD stage and one PUBLISH stage per platform; 2, `machine.stage_platform`). A group hash binding the platforms of one release comes with a second platform (question 10).
- Out of scope for v1, each stated so an SDK author knows: computing the set of targets a change affects (the build system's own queries do that, and a machine names targets), and build units that are checked but never shipped (a `CHANGE_CHECK` stage builds every artifact it names); lookahead into the next stage's channel; copying bytes from one channel to another by digest; concurrency inside an action; callbacks into the host; a networked ledger (5.8); a release whose stages run under different run ids (5.7).

**Proposal, not yet decided: yank.** Withdrawing a published coordinate (`yank`, 5.5) is part of this design as a proposal. It is the reason for the format change, for the `yanked` key of the `stage` record and for the admission clause that reads it (5.7), and for nothing else: all three land in PR 9. If it is not taken, PR 9 is not made, and the ledger stays at format 1.1 for good. Nothing in PRs 3 to 8 depends on it except the `Presence::Yanked` arm and the `PUBLISH_YANKED` reason, which are kept because a registry may report a coordinate withdrawn by someone else.

## 1. The model in one page (Proposal)

- A **release machine** is data: one **build system** (Buck2 or Bazel, defined once for the machine) and an ordered list of **stages**. A stage is an ordered list of **actions**, plus **stage validations** that run after its last action. An action is a **Build** (the build system builds the target of each declared artifact; ucdk locates the one output, copies it into a content-addressed store and writes its manifest), a **Test** (the build system runs test targets), a **Publish** (stage the set in a channel, then commit it) or a **Smoke** (read back what was published). A stage that holds a Build action is a BUILD stage and one that holds a Publish action is a PUBLISH stage, and no stage is both (6).
- A **validation** checks what an action made or published, and is attached to that action (or to the stage). It is one of a closed set of kinds that ucdk itself evaluates (the closure of a set, the read-back of a channel); it runs no command and creates nothing outside ucdk. Its result rows are derived from what it reads (one per member, one per coordinate). It passes only if at least one row is asserted and every asserted row passed. When its holder is reached a validation is evaluated, or skipped by the one rule of 5.4, including when the action it is attached to is skipped as `NOOP`. A **Test** action has no validations attached, because its targets are its validations: each target is one row, and a build system that ran no test is not a pass.
- An **artifact** is a file or an OCI layout in a content-addressed store, described by a **manifest** that ucdk composes from the declaration, the build stamp and the located output: type, name, version, platform, sha256, typed metadata. The manifest is the only interface between a build and everything after it.
- A **release set** is the verified set of members one Build action produced for one (revision, platform). Its **set hash** covers revision, platform, the producing stage and its environment, and every member, and not which run or attempt built it, nor which build system, flags or targets did. BUILD and PUBLISH share one definition of the set, so they cannot disagree about it. The set is persisted as a **set document** beside its members in the artifact store (4.2), so a PUBLISH job in another process rebuilds it from the store and checks it against the ledger.
- A **channel** is a publish destination of one kind: per artifact type one repository (location, visibility, push identity). A published coordinate (channel, type, name, version, platform) is **permanent**. The seam has no delete and no overwrite. Withdrawal is an explicit `yank`, which keeps the bytes and marks the coordinate.
- **Truth is observed.** The registry is truth for what is published and staged. The ledger is the write-ahead record of what ucdk intended and confirmed. A publish whose answer was lost, or whose grant expired between staging and commit, is resolved by reading the registry. Registry correctness never depends on a record: with every record deleted, the same rules reach the same registry state. Run-level gates do depend on records (stage admission, pin checks) and fail closed when a record they need is missing (5.1, 5.4, 5.7).
- **One core, many hosts.** Rust core, C ABI, generated Python and TypeScript SDKs, the CLI. The build system, the process runner, publishers and grant sources are traits, each with an in-memory fake, and each with a contract kit every real implementation must pass.

### 1.1 What the build-system model changes (Decided)

The spine of the design is `Machine { BuildSystem build_system; repeated Stage stages }`, `Stage { repeated Action actions; repeated Validation validations }` and `Action { oneof kind { Build, Test, Publish, Smoke }; repeated Validation validations }` (2). Every later section follows it: the machine rules are stated per action kind and per validation holder (2), the hashes cover the build system and the targets as 2 says, the engine runs a stage's actions in order and then its validations (5), records are per action (3.3), selectors are `action:<name>` and `validation:<name>` (7), and the testing plan and the PR sequence are organised by action kind (8, 11). What this changes in the earlier design, part by part:

| Part of the earlier design | What happens | Why |
|---|---|---|
| `Step`, `Stage.steps`, `step` ledger records, selector `step:<name>` | **Become** `Action`, `Stage.actions`, `action` records, `action:<name>`. `Build { platform, artifacts }` and `Publish { platform, artifacts, channel, attempts, polls }` keep their fields; `Test` and `Smoke` are new; `Stage` gains `validations`. | A stage is an ordered list of actions with their validations. |
| `ArtifactDecl.builder` and the `Command` message | **Go.** `ArtifactDecl.target` (`Target`: label, flags, environment) replaces them. | A build is the build system pointed at a target, not an arbitrary command. |
| `ArtifactDecl.independent_version` | **Goes** (number 6 reserved). Every member carries the release version. `MEMBER_VERSION` stays as the check that a stored manifest equals the stamp. | The manifest is composed by ucdk, and the only source of a different version was the builder's own manifest. |
| The `Builder` trait, `BuildRequest` (with `inputs`, the verified members a build needs), `Builder::plan`, `FakeBuilder`, the builder kit | **Go.** `BuildSystem` (4.2) replaces them, with `Buck2` and `Bazel` implementations over a `ProcessRunner`, a `FakeBuildSystem` as the executable specification and `run_build_system_kit`. A build no longer writes into the store through an `EntryWriter` or returns a manifest: the engine copies the one located output and composes the manifest. | The build graph carries a build's dependencies, so ucdk hands a build no members. |
| The process builder (PR 12), its placeholders `{out_dir}`, `{platform}`, `{revision}`, `{source_commit}`, `{build_number}`, `{timestamp_ms}`, the empty output directory per build, and its `process::` tests of them | **Go.** One closed list of placeholders in flag and environment values replaces them (2), and the Buck2 and Bazel implementations replace the process builder. `process::the_environment_is_not_inherited` is kept as a `ProcessRunner` test. | Process spawning is a `ProcessRunner` concern, and a placeholder is how the stamp reaches the build system. |
| The shared stage budget (whole seconds left on a monotonic clock), the builder kit scenario `timeout_is_reported_not_hung`, "a build that times out is `FAILED`" | **Go.** ucdk sets no deadline on a build or a test. The build system's timeouts and the driver's job limit do; a job that is killed leaves a lapsed lease and a resume (5.4). | Scheduling and time limits belong to the build system and the driver. |
| The builder heartbeat as a compute concept | **Becomes** progress events of a build-system invocation. The `Heartbeat` seam stays, and the `ProcessRunner` calls `beat()` on each chunk of output and each exit poll of a build or a test; `Stop` kills the child. Lease renewal is unchanged (3.3): `renew_if_due` on a beat and the re-acquire before a Confirmed write. | A build or test invocation can outlive the lease, which is all the heartbeat was for. |
| Build-inputs hash fields: builder executable, builder args, `independent_version` | **Go.** The build system (kind, binary, config file, mode, flags, environment), each declaration's target (label, flags, environment) and labels come in (2). | They are what decides a member's bytes and manifest. |
| `machine.publish_stage_has_build`; `machine.readback_on_build`; `machine.local_set_without_build` | **Become** `machine.publish_stage_runs_code` (it now covers Test actions too) and `machine.validation_placement`, which no longer lets `SET_CLOSURE` sit on a stage (the earlier "stage of a Build action" placement was a check that admission never read). New rules cover the build system, targets, placeholders, tests, smoke actions and scopes (2). | Code runs only in a stage that cannot present a push identity. |
| Validations that run their own commands (the registered `Validation.validator` kind name, `options`, authored `rows`, the `Validator` trait, `FakeValidator`, the validator kit) | **Go.** A test is a build-system target (a Test action). What is kept is what is neither a build nor a test: `Subject.LOCAL_SET` with the validator `set-closure` becomes the built-in kind `SET_CLOSURE`, and `Subject.CHANNEL_READBACK` becomes the built-in kind `CHANNEL_READBACK`. Both are evaluated by ucdk (a pure function of the set; a read of a channel through the `Publisher`), their rows are derived, and there is no third kind. | A check that runs code is a test target; a registry of validator kinds would be a second way to run commands. |
| Everything that existed because a validator could create objects outside ucdk: the validation run id (`vr-<hash>-k`), `CreatedJournal`, `created` records, `ValidationStamp`, `sweep` and `remove`, the `leaks` verb and `LeaksRequest`, `ValidationReport.leftovers` and `validation_run_id`, the `k` payload key, the rule that a creating validator refuses an in-memory run ledger | **Go.** Exit class 8 stays in the enum the deletion PR keeps, no release verdict maps to it, and PR 10 removes it with the match. | No kept validation creates anything. What a test target creates outside ucdk is the test's and the build system's concern: ucdk cannot stamp or sweep it and does not claim to. A later validator kind that creates objects brings its own journal with its own design. |
| `Publisher::put`, the one-call write | **Becomes** `stage` and `commit` (4.3). A channel that cannot stage skips the stage phase and `commit` does the atomic create-if-absent that `put` did. | Permissions are per phase, and some registries hold staged bytes without publishing them. |
| `CredentialSource`, `Presented`, `plan --check-credentials` reporting `MINTED`, `NOT_UNDER_PLATFORM`, `NOT_FEDERATED` | **Become** `GrantSource`, `Grant` and a check that reports one of those per phase, plus `REFUSED`. `Federated` gains the scope each phase needs and the other claims the issuer pins; `grant` ledger records and the reasons `BUILD_OUTPUT` and `PUBLISH_STAGE` are new (2, 3.3, 6). | Stage and commit are separate grants. |
| Verbs | `ucdk release leaks` goes. `ucdk release trust` (print the trust a machine expects) and `ucdk release abort` (discard staged state) are new (7). | Bootstrap needs the expected trust as data; a failed commit needs a way to give the staged state back. |
| The four kits (builder, publisher, validator, store) | The builder and validator kits go. Five remain: `run_build_system_kit`, `run_process_runner_kit`, `run_publisher_kit`, `run_grant_source_kit` and `run_store_kit` (4.6). | A seam each, and one contract per seam. |
| The `input` digest of an `action` record ("the action as authored, the build system, the set hash, platform, revision") | **Gets a byte layout** with its own domain tag and fields per action kind (2). Validations, the attempt and poll bounds and the timestamp are not in it. | It decides `NOOP` versus `INPUTS_CHANGED` for every action kind, so two implementations must agree on its bytes. |
| The stage record's `confirmed` ("every action is `Confirmed`") | **Becomes** the conjunction of every action and every action-level and stage-level validation, written last (3.3, 5.7). | A stage whose read-back failed must not admit the stage that waits for it. |
| Open questions 4, 8, 9, 11 and 15; risks 5, 9, 16 and 19; PRs 3 to 8 and 10 to 13 | Reworded or re-scoped. Questions 18 to 23, risks 20 to 24 and PR 14 (the package-registry channel kind) are new (10, 12, 11). PR 3 is split into 3 and 3b to 3d, and PR 12 into 12a and 12b (11). | The sections follow the spine, and the sizes follow the size rule. |

**Kept as it was:** the ledger, lease, fence, holder and renewal rules; the store keys, generations and the set document; the seal ledger, adoption and the build-inputs mechanism (its fields change, not its use); observe before every effect and write-ahead intent; the ambiguity table (extended by grants, 5.3); supersession and the monotonic rule; stage admission; the exit table and the run verdict rule (class 8 aside); the C ABI and SDK pattern.

**What a test proves.** A Test action says that the build system, run with the test's targets, flags and environment on this revision, reported every target passed with at least one test run. It does not say that the bytes in the store are the bytes the test ran against: that is what `verify_member` and the set hash prove. A machine that needs both gives the test target a dependency on the member targets and the same flags and environment as the build, so the build system returns the identical outputs from its own cache. ucdk does not check that (risk 20).

### 1.2 The project's own first machine (Proposal; worked example)

The project's first machine builds the release set with the build system, runs the release-set test target, then publishes the packages to a package-registry channel. The targets live under `//release` and do not exist yet; the first real release PR adds them. Written as text protobuf (the machine is binary protobuf or canonical JSON, 10 question 1):

```text
name: "ucdk"
build_system {
  kind: BUCK2
  binary: "buck2"
  config_file: "release/release.buckconfig"     # may send actions to remote execution; ucdk cannot tell
  mode: "release"
  env { key: "PATH" value: "/opt/tools/bin:/usr/bin:/bin" }   # the child's own PATH finds the bare `buck2` (2, layering)
}
artifacts {                                      # one member per package, each with its own target
  name: "ucdk-cli"  type: FILE
  target { label: "//release:ucdk_cli_package"
           flags: ["-c", "release.version={release_version}", "-c", "release.commit={source_commit}"] }
}
artifacts {
  name: "ucdk-lib"  type: FILE
  target { label: "//release:ucdk_lib_package"
           flags: ["-c", "release.version={release_version}", "-c", "release.commit={source_commit}"] }
}
channels {
  name: "registry"  kind: PACKAGE_REGISTRY  monotonic: false   # true needs a registry that stores the stamp (question 23)
  repositories {
    type: FILE  location: "https://packages.example.com/files"  visibility: PUBLIC
    push { federated { subject: "repo:example-org/ucdk:environment:publish"  audience: "packages.example.com"
                       environment: "publish"  stage_scope: "publish"  commit_scope: "publish" } }
  }
}
stages {
  name: "check"  trigger: CHANGE_CHECK           # a pull request: the same targets, no environment, no channel, no seal ledger
  actions { name: "build"
            build { platform: "linux-x86_64"  artifacts: ["ucdk-cli", "ucdk-lib"] } }
  actions { name: "test"
            test { targets { label: "//release:set_test" } } }
}
stages {
  name: "build"  trigger: RELEASE
  actions { name: "build"                        # one build-system invocation per artifact, then the seal
            build { platform: "linux-x86_64"  artifacts: ["ucdk-cli", "ucdk-lib"] }
            validations { name: "closure"  kind: SET_CLOSURE } }
  actions { name: "test"                         # the release-set test target; the target is the validation
            test { targets { label: "//release:set_test" } } }
}
stages {
  name: "publish"  needs: ["build"]  trigger: RELEASE  environment: "publish"
  actions { name: "publish"                      # stage, then commit: two grants (6)
            publish { platform: "linux-x86_64"  artifacts: ["ucdk-cli", "ucdk-lib"]  channel: "registry" } }
  actions { name: "smoke"                        # read back as a stranger would
            smoke { platform: "linux-x86_64"  artifacts: ["ucdk-cli", "ucdk-lib"]  channel: "registry" }
            validations { name: "visible"  kind: CHANNEL_READBACK  wait_polls: 5 } }
}
```

What it does, in order. The `build` stage job runs, for each artifact, `buck2 build --show-full-output` with the layered flags and the target (2), takes the one output the build system names, copies it into a new generation of the store, composes the manifest, verifies every member twice, writes the set document and the seal (4.2, 5.4), then the action's `closure` validation reads the sealed set, and the `test` action runs `buck2 test` on the release-set target; the stage is confirmed when all three passed. The `publish` stage job is admitted only if the `build` stage is confirmed with the same set (5.7), exchanges the job's identity token for a stage grant, stages both coordinates in the channel (the `publish` action has no validations of its own, so nothing runs between its two phases), exchanges for a commit grant, finds the staged state by observation, commits and polls the read-back; then the `smoke` action reads the coordinates back as a stranger would and its `visible` validation checks every row, and the stage is confirmed when both passed. A pull request runs the `check` stage, the one of trigger `CHANGE_CHECK`: it holds the same Build and Test actions and nothing else, has no `needs`, no environment, no channel and no seal ledger, and no stage may need it (`machine.change_check_publishes`). The listing passes every rule of 2: a `build_system` is present and its bare `binary` has a `PATH` to be found on; every artifact has a target and the `build` action's list is closed under `needs`; the test has one target and no validations; the publishing stage holds no Build or Test action, needs exactly one stage whose Build action carries a `SET_CLOSURE` validation, has one platform that equals the build stage's, and its `environment` (`publish`) equals the `environment` of the repository's `Federated` identity; the `smoke` action reads back what the `publish` action published and carries a `CHANNEL_READBACK` validation; no other stage needs the publishing stage, so `machine.gating_stage_lacks_readback` does not apply (it would, if one did, and the `smoke` action would satisfy it). **What the example does not yet satisfy.** It is checked by the machine reader and run over the fakes (PR 3 to PR 8), and two things stand between it and a real registry channel, both decided before PR 14 and neither by the engine (question 23): the channel is `monotonic: false` because a `monotonic` channel needs a home that stores the `Held` stamp beside the bytes (4.3, kit scenario `observe_returns_the_stamp_it_was_given`), and a registry that does not store it is refused as such a home; and the members are `FILE` because that is the type the reader accepts, while a registry of ecosystem packages needs the ecosystem's own type, which the reader refuses until its metadata arm carries the platform subdir (4.2). The first real machine uses `FILE` packages only if the registry kind accepts them.

## 2. The protos (`ucdk.release.v1`, Proposal)

Everything crossing the ABI is protobuf bytes. The package sits beside the existing ones. Retired numbers are `reserved`. The generator reads the proto list in `ucdk_codegen::PROTO_FILES` (Exists; today two files), so the new file is one more entry. Enum zero values are `*_UNSPECIFIED` and are refused on read. Names (stage, action, validation, channel) match `[a-z][a-z0-9-]*`, at most 63 bytes, no trailing `-`. Artifact names also allow `_`.

Three names differ from their neighbours on purpose. `ucdk.api.v1` already has a message `Outcome`, an enum `ErrorCode` and an enum `CredentialSource` (all Exists, all deploy-shaped). The release package therefore says `Verdict`, `Reason` and `PushIdentity`, so a generated SDK never has two things of one name in one namespace.

```proto
syntax = "proto3";
package ucdk.release.v1;

// ---- declaration (authored; the SDKs build these) ----
message Machine {
  int32 schema_version = 1;          // 1. A newer major is a distinct refusal.
  string name = 2;
  repeated Stage stages = 3;
  repeated ArtifactDecl artifacts = 4;   // declaration order is part of the contract
  repeated Channel channels = 5;
  repeated string stamp_ignore = 6;      // path globs whose commits never raise the build number
  BuildSystem build_system = 7;          // defined once; required when any stage holds a Build or Test action (machine.build_system_required)
}
// ---- the build system: defined once for the machine (2, layering) ----
message BuildSystem {
  BuildSystemKind kind = 1;
  string binary = 2;                 // a bare name (found on the child's own PATH, which the machine must name) or an absolute path; run as argv, never through a shell
  string config_file = 3;            // relative to --root: the kind's config file (buck2 --config-file, bazel --bazelrc); empty means none
  string mode = 4;                   // the kind's named mode (buck2 a mode file, bazel a --config name); empty means none
  repeated string flags = 5;         // base flags, one argv element each, in order
  map<string, string> env = 6;       // base environment; the child inherits nothing else
}
enum BuildSystemKind { BUILD_SYSTEM_KIND_UNSPECIFIED = 0; BUCK2 = 1; BAZEL = 2; }
message Target {
  string label = 1;                  // exactly one target of the build system's label grammar; no pattern
  repeated string flags = 2;         // per-target flags, one argv element each, appended after the base flags
  map<string, string> env = 3;       // per-target environment; a key also in the base environment replaces its value
}

// ---- the spine: a stage is an ordered list of actions, and every action has its validations ----
message Stage {
  string name = 1;                   // also the unit of trust and of driver job
  repeated string needs = 2;         // earlier-declared stages; a DAG ordered by Kahn; each must be confirmed for the run before this stage's first effect (5.7)
  Trigger trigger = 3;
  string environment = 4;            // the trust scope the driver gives this stage; default = name
  bool exceptional = 5;              // may run off the mainline, with a reason (5.6)
  repeated Action actions = 6;       // run in this order; stop at the first not SUCCEEDED/NOOP; a stage with a Publish action has no Build or Test action; the actions that name a platform name the stage's (2, checked)
  repeated Validation validations = 7;   // stage-level: run after the last action, in this order; the stage is confirmed only when these passed too (3.3)
}
enum Trigger { TRIGGER_UNSPECIFIED = 0; RELEASE = 1; CHANGE_CHECK = 2; }  // CHANGE_CHECK: Build and Test only
message Action {
  string name = 1;                   // unique in the stage
  oneof kind { Build build = 2; Test test = 3; Publish publish = 4; Smoke smoke = 5; }
  repeated Validation validations = 6;   // a Build action's run after its seal; a Publish action's run between stage and commit (the one exception to "after the action", 5.2); a Smoke action's after its read; a Test action has none (its targets are its validations)
}
// Field numbers of Stage.actions (6) and Action (publish 4, validations 6) differ from the `Step` message of the
// model branch (publish 3, validations 4). The branch is unreleased, so the numbers move without a reservation;
// from the first release on a number is only ever added or reserved.
message Build   { string platform = 1; repeated string artifacts = 2; }   // each artifact names its Target in its declaration
message Test    { repeated Target targets = 1; }                           // one to 32; each target is one row; the stage's platform is not named here
message Publish {
  string platform = 1; repeated string artifacts = 2; string channel = 3;
  uint32 attempts = 4;               // calls per phase that a Transient, RateLimited or expired-grant answer may use (5.2); 0 = DEFAULT_PUT_ATTEMPTS (3); at most 10
  uint32 polls = 5;                  // read-back polls per coordinate (5.2); 0 = DEFAULT_READBACK_POLLS (3); at most 10
}
```

The request and response messages (`ReleaseCheckRequest`, `ReleasePlanRequest`, `ReleaseRunRequest`, `ReleaseStatusRequest`, `ReleaseTrustRequest`, `ReleaseAbortRequest`, `YankRequest`, their responses) are `ucdk.api.v1` messages owned by `ucdk-api`, as today; the generic `LedgerShowRequest` and `LedgerShowResponse` arrive earlier, in the deletion PR, and are specified in 3.4. A run request carries the machine, run identity, source facts, stage, selectors and the approved run hash. The report is a pure function of the ledger and the engine's action results. No decision reads a report. A machine refusal carries a stable rule id (`machine.<name>`, listed below and held by tests) next to `MACHINE_FORMAT`, so a test names the rule it holds and no one parses a message.

**Layering: one build-system invocation (Decided here).** An invocation is one `ProcessRunner` call with an argument vector and an environment, never a shell. A Build action makes one invocation of the verb `Build` per artifact and, for Bazel, the two invocations `Query` and `Info` that locate its output (4.2); a Test action makes one invocation of the verb `Test` per target. Every verb has the same shape. The argument vector is these elements, in this order, and nothing else: (1) the binary, `BuildSystem.binary`; (2) the kind's startup arguments from `config_file` (Bazel `--bazelrc=<file>`; Buck2 has none); (3) the verb word of the table below; (4) the kind's command arguments from `config_file` (Buck2 `--config-file <file>`) and `mode` (Buck2 the mode file as `@<mode>`, Bazel `--config=<mode>`); (5) `BuildSystem.flags`, in order; (6) the target's `flags`, in order; (7) the flags ucdk owns for that kind and verb; (8) the tail of the verb. Elements (2) and (4) are absent when `config_file` and `mode` are empty (an empty string means none, since a proto3 string cannot say absent).

| Kind | Verb | Word (3) | ucdk-owned flags (7) | Tail (8) |
|---|---|---|---|---|
| Buck2 | `Build` | `build` | `--show-full-output` | the label |
| Buck2 | `Test` | `test` | `--event-log=<report>` | the label |
| Bazel | `Build` | `build` | none | `--`, the label |
| Bazel | `Query` | `cquery` | `--output=files` | `--`, the label |
| Bazel | `Info` | `info` | none | `execution_root` |
| Bazel | `Test` | `test` | `--build_event_json_file=<report>` | `--`, the label |

`<report>` is a file path in a directory the engine creates for that one invocation under the required `--scratch` flag of a stage with a Test action (`SessionConfig.scratch`); ucdk reads the file after the child exits (4.2, item 3) and removes the directory. The path is neither authored nor hashed. **Its file name is fixed, because Buck2 chooses the event-log encoding and compression from the name's suffix:** `events.json-lines` for Buck2 (uncompressed JSON lines; a `.pb` or compressed suffix would select another encoding) and `events.json` for Bazel (the build event protocol's JSON form is chosen by the flag, and the name only says what it holds). So the path is `<scratch>/<invocation>/events.json-lines` or `.../events.json`. `Query` and `Info` are given the same startup and config arguments, base flags and target flags as the `Build` whose output they locate, so that they see the same configuration, and the on-demand job confirms that each verb accepts them (a build flag that `bazel info` does not take is a finding of that job, not a silent drop); `Info` has no label and no `--`. The spellings in the table, and the claim that each of these verbs accepts the author's flags, are the intended ones and are confirmed by the on-demand job of 8 (question 19); until then the goldens pin ucdk's intent. **Flags are appended.** They are never merged, de-duplicated or interpreted by ucdk: a flag the build system treats as last-wins is overridden by the target's occurrence, because the target's flags come after the base flags, and a flag it treats as repeatable accumulates, base values first. ucdk's own flags come after both lists so no author can override them, and a flag in the closed list a kind owns is refused in either list (`machine.reserved_flag`): Buck2 `--show-output`, `--show-full-output`, `--show-simple-output`, `--show-json-output`, `--show-full-json-output` and `--event-log`; Bazel `--output`, `--build_event_json_file`, `--build_event_text_file`, `--build_event_binary_file` and `--symlink_prefix` (the last decides where the output tree is linked, which a located path must not depend on). A startup option such as Bazel's `--output_base` has no place among the flags, which follow the verb; it can only come from the author's config file, which is hashed by name. The spellings of the table and of (2) and (4) are pinned by one golden argument vector per kind and verb (`invocation::argv_goldens`, PR 3), six in all. **The environment is overridden, key by key.** The child's environment is the base `env`, then the target's `env` over it: a key in both takes the target's value (a replacement, never a concatenation or a path-list merge), and an empty value is a variable set to the empty text. There is no unset: a variable that some targets must not have is written on the targets that need it, not in the base. Nothing is inherited from ucdk's own process, so the build system sees the variables the machine names and no others; a machine that needs `PATH` or `HOME` names them. Keys match `[A-Za-z_][A-Za-z0-9_]*` (so `http_proxy` and `no_proxy` are allowed) and do not start with `UCDK_` in any case (`machine.env_key`). **A bare binary is found on the child's own `PATH`.** When `binary` is a bare name the runner resolves it by scanning the `PATH` of the layered environment of that invocation, in order, for the first regular executable file of that name, and runs that file with the name as `argv[0]`; it never reads ucdk's own `PATH`, so "nothing is inherited" holds for the lookup too. A machine whose `binary` is a bare name must therefore name `PATH` in the base environment (`machine.build_system_shape`); a name found nowhere on it is unstartable (`Unknown`, `INDETERMINATE`). The hashes cover the name and the `PATH` text, not the bytes of the file found: which `buck2` answers is the host's, and an absolute path pins it no better, because ucdk does not hash the file either (question 18). **What the environment is.** It is the environment of the build-system client process, and nothing more. Whether a variable reaches an action or a test is the build system's rule, not ucdk's: Bazel passes its client environment to actions and tests only through its own forwarding flags (`--action_env`, `--test_env`, `--repo_env`, `--host_action_env`), and Buck2 gives an action only the environment its rule declares. A machine that needs a value inside an action or a test therefore says so in a flag of the same list, with a placeholder where the value is a stamp field (for example `--action_env=RELEASE_VERSION={release_version}`); that flag is per invocation and hashed like any other. A long-lived server that either build system keeps between invocations may hold the environment it started with; ucdk passes the layered environment on every invocation and does not start, stop or inspect the server, and whether a changed variable restarts it is the build system's behaviour (question 22, risk 24). **Placeholders.** In each flag and each environment value the closed list `{release_version}`, `{build_number}`, `{source_commit}`, `{revision}`, `{timestamp_ms}` and `{platform}` is replaced by the build stamp field, the run's revision or the stage's platform (a Test target that uses `{platform}` in a stage that names no platform is refused); `{{` and `}}` are literal braces; any other brace is refused when the machine is read (`machine.placeholder`, which also refuses that `{platform}`). The binary, config file, mode and labels are not substituted. Placeholders are the only way the stamp reaches a build, and a flag that uses `{timestamp_ms}` makes the action differ on every run, which defeats a build system's cache: that is the author's choice. **What is hashed (stated again in the layouts below).** The machine hash covers every authored byte (build system, targets, flags, environment, placeholders as written). The build-inputs hash covers the build system and each declaration's target as authored, the stamp without its timestamp, and the labels. The layered result is never hashed on its own: it is a function of those inputs and the stamp. The set hash covers none of it, only what the build produced. No grant, identity token or other credential value enters any hash (6): the hashes cover the declared `Federated` fields, which are not secret, and never a value an issuer returned.

**Identity digest (Decided here).** `Manifest.sha256` is the identity of a member, and it is the only digest a publisher compares. For `FILE` it is the SHA-256 of the file's bytes. For `OCI` it is the image manifest digest of the layout (hex, no algorithm prefix), which is what a registry reports; `OciMeta` has no second digest and the layout directory's own bytes are not the identity. A new `ArtifactType` names its identity before it is accepted (`machine::every_artifact_type_names_its_identity`). `verify_member` recomputes the identity from the stored bytes, and for `OCI` requires `os`-`cpu` to equal the run's platform (`PLATFORM_MISMATCH`; `any` is refused for `OCI`).

**Byte layouts of the four hashes and the action input digest (Decided here).** Each hash is SHA-256 over a domain tag fed raw, then a sequence of fields. A **field** is its 8-byte big-endian length followed by its bytes, written by the `Framed` hasher that 3.1 moves into `ucdk-core`. A **text** field is the UTF-8 bytes of the string. A **number** field is the decimal text of the number (no sign, no padding, `0` for zero); an enum is its number in decimal; a bool is `1` or `0`. A **count** is a number field holding the length of the list that follows it. A **string list** is a count and then one text field per item. The hash text is 64 lowercase hex digits. The domain tags are `ucdk/release-set/1`, `ucdk/release-machine/1`, `ucdk/release-run/1`, `ucdk/release-build-inputs/1` and, for the action input digest, `ucdk/release-action-input/1`, each followed by a newline (the convention the plan hash uses today, Exists), so no tag is a prefix of another. Fields of a hash are, in order:

- **Set hash** (`set_hash::golden_text`): text revision; text platform; text producer stage; text producer environment (an absent producer is two empty texts); number of members (count); then, for each member sorted bytewise by manifest name (a member with no manifest reads as an empty manifest): text name; text version; number type; text platform; text file; number size; text sha256; number build number; text source commit; then the metadata arm. A member with no metadata arm is the number `0`. A `FileMeta` arm is the number `10`, a count of labels, and for each label in sorted key order a text key and a text value. An `Oci` arm is the number `11`, text `os` and text `cpu`.
- **Machine hash** (`machine_hash::golden_text`): one field, the `Machine` message in canonical encoding (fields in number order, map entries in sorted key order, defaults omitted; the generated types use ordered maps), as the one length-framed field.
- **Run hash**: text machine hash (the 64 hex digits); text stage name; string list of the selectors as text (`action:<name>` or `validation:<name>`), sorted bytewise; text revision; text stage platform (empty when the stage names none); text build stamp version; number build number; text source commit; and, only when the stage holds a Publish or Smoke action (it consumes the set of the BUILD stage it needs), text sealed set hash. A stage that holds a Build action or only Test actions has no set among its run-hash inputs (a set cannot be given to it), and a stage that holds a Publish or Smoke action has one. A Test-only stage that `needs` an earlier stage still reads that stage's set, for admission only (5.7): admission recomputes it from the store and the run hash does not cover it, because the stage consumes no member (a test target reaches the packages through the build system, not through ucdk).
- **Build-inputs hash** (`build_inputs::*`): text platform of the Build action; text revision; text stamp version; number build number; text source commit; then the build system as authored: number kind; text binary; text config file; text mode; string list of the base flags (in order); number of base environment pairs (count) and for each pair in sorted key order a text key and a text value; then number of declarations (count); then, for each declaration of the action's artifacts, in Kahn order (the list is closed under `needs`, `machine.build_not_closed`; of the declarations ready at once, the one with the smallest name bytewise comes first; the machine rules have already refused a cycle or a dangling name), text name; number type; text target label; string list of the target's flags (in order); number of target environment pairs and each pair in sorted key order as text key and text value; string list of `needs`; number of labels and each label in sorted key order as text key and text value. Flags and values are the authored text, placeholders unsubstituted. The machine hash, other stages, Test actions, channels and validations are not inputs.
- **Action input digest** (`action_input::golden_text`; the `input` key of an `action` record, 3.3). It decides, on a resume, whether a `Confirmed` action is the same work (`NOOP`) or `INPUTS_CHANGED` (5.4). After the tag, the first field is a text naming the kind, and the rest depends on it. **`build`:** text `build`; text build-inputs hash (the 64 hex digits of the hash above, so the build system, every declaration, the stamp and the platform are in it). **`test`:** text `test`; text revision; text stage platform (empty when the stage names none); text stamp version; number build number; text source commit; the build system as authored, in the field order of the build-inputs hash (number kind; text binary; text config file; text mode; string list of the base flags; the base environment pairs); number of targets (count); then, for each target in the order listed (the order they run in), text label; string list of its flags; its environment pairs in sorted key order. **`publish`:** text `publish`; text set hash; text revision; text platform; text channel name; string list of the artifact names in the order listed. **`smoke`:** the same fields with the text `smoke`. Not in any of them: validations (a validation has its own record and its own subject, 5.4), `Publish.attempts` and `polls` and `Validation.wait_polls` (a bound changes how long a run tries, not what it does), the action name (it is in the record's name), the timestamp, the run id and attempt, the `<report>` path, and everything of other actions. Flags and values are the authored text, placeholders unsubstituted.

These are the layouts the code builds, and the goldens pin them, so a second implementation that follows the list byte for byte reproduces the goldens. What each hash covers, and why, follows. Revision and platform are inside the hash so an approval of one commit or platform cannot be replayed on another; the typed metadata and the stamp are inside it so two sets that differ in an OCI `os`, `cpu` or a build number cannot share a hash (`set_hash::every_metadata_field_changes_the_hash` flips each field of each arm in turn). The producer is inside it so a set built by a `CHANGE_CHECK` stage, or by any other stage or environment, can never carry the hash of a set a release BUILD stage made, whatever bytes it holds (`set_hash::changes_with_the_producing_stage_and_environment`); `file` and `size` are inside it so two sets with one hash cannot publish different file names (`set_hash::file_and_size_change_the_hash`). `ProducedBy` (the run id and attempt) and the stamp's timestamp are never hashed (`set_hash::ignores_the_run_and_attempt_that_built_it`). **The set hash does not cover the build system, a target, a flag or an environment.** A set is what was built: a rebuild through another target or flag that yields the same members has the same hash, and the adoption checks of 5.4 recompute the bytes anyway (`set_hash::ignores_the_build_system_and_the_targets`). **The build-inputs hash covers all of them** because it answers one question, whether a sealed set could have been made by this machine for this revision: the build system as authored (its kind, binary, config file, mode and flags decide how every member is built, and its environment is the client's, which a flag may forward into the actions, so it is an input even where it changes no byte), each declaration's target as authored (label, flags, environment) and its labels (they are in the manifest), and the stamp without its timestamp (adoption keeps the recorded timestamp, 5.4, so a flag that uses `{timestamp_ms}` is hashed as the placeholder text). It does not cover the bytes of the config file or the sources, which the revision pins, nor the build system's own version or the bytes of the binary found on `PATH`, which ucdk cannot observe (question 18). Test actions are not inputs to a set, so editing a test target or its flags never defeats adoption (`build_inputs::a_test_edit_does_not_change_it`). Every other build-system edit does, which is the intended refusal: a changed flag may change the bytes. The domain tags keep their `/1` suffix: no hash of this family has been written by a released ucdk, and the layout above replaces the build-inputs layout that the model PR (3) carries in review.

The **machine hash** covers the `Machine` message in canonical encoding, as laid out above: the build system, every target with its flags and environment, the labels, the actions with their validations, the channels with their trust declarations. An approver therefore approves every flag and variable a build or test will run with (`machine_hash::covers_the_build_system_and_every_target`). The **run hash** covers the machine hash, the stage name, the selectors sorted bytewise, the revision, the stage's platform, the build stamp (version, build number, source commit; for a stage with neither a Build nor a Test action, the one the run record holds) and, only when the stage holds a Publish or Smoke action, the sealed set hash. The timestamp is not hashed: the run record pins it and adoption keeps it (5.4). It approves this machine, this stage and selection, this revision and platform, and where the stage consumes a sealed set, that set. It never covers observed registry state, the run id, the attempt or a ledger, so a resume after a partial publish presents the hash that was approved (`run::approved_hash_survives_a_kill_and_resume`). `plan` prints it and takes the same stamp inputs as `run` (7), so the hash it prints is the hash `run` recomputes for the same stage (`run_hash::plan_and_run_agree_for_a_build_stage`, `run_hash::plan_and_run_agree_for_a_stage_without_build`); `run`, `abort` and `yank` take it as `--expect-hash` (a yank's hash is over `ucdk/release-yank/1`, the machine hash, the coordinate and the reason); a different value is `REFUSED` with `RUN_HASH_MISMATCH` before any record is written.

Checked on read. Every rule below is written as the condition that is refused, each refusal is named by a rule id, and each is held by one test in PR 3:
- `machine.unknown_enum`: an unknown enum value. `machine.stage_cycle`: a stage cycle, a stage needing itself or a later stage. `machine.duplicate_name`: a stage name, an action or validation name within a stage (action-level and stage-level validations share one namespace), an artifact name or a channel name used twice. `machine.unknown_channel`: a Publish or Smoke action or a lookup naming a channel that is not declared (the message lists the declared ones).

- `machine.target_shape`: a target whose label is not exactly one label of the kind's grammar (Buck2 `[cell]//package:name`, Bazel `[@repo]//package:name`), or holds a wildcard (`...`, `:all`, `*`), a space or a control character. `machine.artifact_target_missing`: an artifact with no target. `machine.build_undeclared`: a Build action naming an undeclared artifact. `machine.build_not_closed`: a Build action whose artifact list is not closed under `needs` (an artifact it lists that needs one it does not list), so the sealed members are exactly the listed artifacts, as 5.4 check 5 requires, and "the action's artifacts" is the whole input. `machine.labels_on_non_file`: `labels` on an artifact that is not `FILE`.
- `machine.test_shape`: a Test action with no target, more than 32, or the same label twice; or a Test action that carries validations (its targets are its validations).
- `machine.change_check_publishes`: a `CHANGE_CHECK` stage that holds a Publish or Smoke action, has `needs`, is needed by another stage, sets `environment`, or sets `exceptional`.
- `machine.stage_platform`: a stage whose actions that name a platform (Build, Publish, Smoke) name more than one distinct platform, or that holds more than one Build action. A stage has one platform and seals one set (5.4), so a stage has one run record entry, one `set` and one `SET_CLOSURE` validation record, and a release for several platforms is one stage per platform under one run id. A Test action names no platform: it runs wherever the build system runs it.
- `machine.artifact_cycle`: an artifact `needs` cycle (every member is listed) or a dangling name.
- `machine.channel_shape`: a channel whose kind is unspecified, a channel with no repository, two repositories of one type in a channel, a location shared by two repositories (within or across channels), a repository with no `push`.
- `machine.exceptional_subject`: `exceptional_subject` equal to `subject`, `exceptional_subject` set without `federated`, `exceptional_environment` equal to `environment`, or one of the pair set without the other.
- `machine.federated_shape`: a `federated` identity with an empty `subject`, `audience`, `stage_scope` or `commit_scope`, or a `pinned_claims` key that is empty or is `sub`, `aud` or `exp` (which have their own fields or are the issuer's), or a pinned value that is empty. The two scopes may be equal.
- `machine.publish_undeclared`: a Publish or Smoke action naming an undeclared artifact, or a channel with no repository for that artifact's type.
- `machine.validation_placement`: a validation on a place its kind may not hold. `SET_CLOSURE` is allowed on a Build action and on a Publish action, never on a stage (the one closure that admission reads is the Build action's, 5.7, and a stage-level one would be a check nothing waits for); `CHANNEL_READBACK` is allowed on a Smoke action and on a stage that holds a Publish action (its subject is fixed by the holder, 4.4), never on a Publish action, because nothing is readable before the commit; neither is allowed on a Test action. `machine.smoke_shape`: a Smoke action with no `CHANNEL_READBACK` validation, or that names a channel or artifact no earlier Publish action of the stage published.
- `machine.environment_mismatch`: a stage that holds a Publish action and whose `environment` is not the `environment` of every `federated` repository it publishes to (6); for an `exceptional` stage, whose `environment` is neither that nor the repository's `exceptional_environment`. `environment` is an explicit field of `Federated`, never parsed out of `subject`.
- `machine.publish_stage_runs_code` (the trust split, Decided here): a stage that holds a Publish action together with a Build or a Test action. A build or a test runs code the machine's authors, or the code under test, wrote, and that code never runs in a process or environment that can present a push identity. A Smoke action reads and runs no code, so a publishing stage may hold one; a check that must run code after publishing (installing the package and running it) is a Test action in a later stage that needs the publishing stage and holds no Publish action. That stage is admitted like any stage with `needs` (5.7), so its job gives `--run-id`, `--run-ledger` and `--store`, and, as a stage with a Test action, the stamp flags, which the run record checks (7).
- `machine.publish_stage_needs_validated_build`: a stage that holds a Publish action and does not directly need exactly one stage that holds a Build action with a `SET_CLOSURE` validation on that action (it may need other stages that hold no Build action, so "the needed BUILD stage" of 5.7 is one stage).
- `machine.publish_chain_shares_the_build`: a stage S that holds a Publish action and directly needs another stage N that holds a Publish action, when the one BUILD stage S needs is not the one N needs (each needs exactly one, by the rule above). With two BUILD stages A1 and A2 of one platform, B needing A1 and C needing B and A2 is refused, so a later channel is only ever given the set the earlier channel published (5.7); the rule holds edge by edge, so it holds along any chain.
- `machine.publish_stage_scope`: a stage that holds a Publish or Smoke action whose platform differs from that of the BUILD stage it needs, or whose action names an artifact the Build action does not declare.
- `machine.bound_out_of_range`: `Publish.attempts`, `Publish.polls` or `Validation.wait_polls` above 10. The closure is a built-in kind, not a registered one, so no other check stands in for it. `SET_CLOSURE` is specified in 4.4; the platform and lockstep checks are not part of it but of `verify_member`, which a publishing stage runs itself (4.2).
- `machine.gating_stage_lacks_readback`: a stage that holds a Publish action and is needed by another stage and carries no `CHANNEL_READBACK` validation (on a Smoke action or on the stage), so the stage a later one waits for has read back what it published. The rule only says the validation exists; that it passed is what makes the gate: a stage is confirmed only when every validation at both levels passed (3.3), and admission reads that (5.7).
- `machine.exceptional_needs_exceptional`: an `exceptional` stage that needs a stage that is not `exceptional`, or a non-`exceptional` stage that needs an `exceptional` one.
- `machine.every_artifact_type_names_its_identity` (2).

- **Ledgers, lease, fence and holder (Decided here).** Three kinds of ledger document: one **per channel** (publication records), one **per run** (run, stage, action, validation and grant records) and one **seal ledger** (seal records, 5.4; durable across runs, written only by BUILD stages of a `RELEASE` trigger). A `CHANGE_CHECK` stage takes no channel lease, and is refused a seal ledger (`LEDGER`, `run::change_check_is_refused_a_seal_ledger`). **The seal lease** is taken only to write a seal and given back at once (acquire, one fenced write, release), never held through a build, and it is not in the beat set of the renewal rules below, which name the run and channel leases only; reading the seal ledger for adoption (5.4) takes no lease. Its holder is the rule's, `run:<run id>/<stage>`, and the stages of one release differ (one platform per stage, 2), so BUILD jobs of several platforms that share a seal ledger exclude each other only for the length of a write. Held by `lease::two_stages_sharing_a_seal_ledger_both_complete`, `lease::the_seal_lease_is_not_in_the_beat_set` and `lease::a_seal_write_after_a_long_build_takes_the_seal_lease_at_write_time` (a `ManualClock` moved past the TTL during the build). The **holder** of every lease a process takes is `run:<run id>/<stage>`, the same for every attempt of that stage (an explicit `SessionConfig.holder` overrides it and is the operator's choice). Stages of one run therefore exclude each other on the run ledger by lease, and never fence each other: `Doc::acquire` grants at once only to the holder already named in the lease, so a rerun of the same run id and stage retakes its leases immediately after a kill, while a sibling stage of the same run, or another run id, is refused (`LEASE_HELD`) until the lease is given back or lapses plus `MAX_CLOCK_SKEW`. Whether sibling stages may run at the same time is answered by that rule: they may be started, one of them runs and the other is refused with the advice to run it again when the first ends; stages ordered by `needs` never meet this. The release TTL is the existing 600 s. A `LEASE_HELD` refusal says so and gives the advice: "rerun the same stage of the same run id, or wait for the lease to lapse (at most the TTL plus the skew bound)"; it is class 3 and promises nothing changed. `yank` takes the holder `yank:<run id>` (the `--run-id` flag it requires) on the channel lease, and on the run ledger too for the one write of 5.5 when `--run-ledger` is given (`yank::the_run_ledger_write_uses_the_yank_holder`); a yank right after a killed publish waits out that publish's lease, and says so. `check`, `plan`, `status`, `trust` and `ledger show` take no lease and write nothing. Held by `lease::sibling_stages_do_not_fence_each_other`, `lease::a_sibling_stage_is_refused_while_the_other_holds_the_run_lease`, `lease::the_same_stage_and_run_id_retakes_both_leases_at_once`, `lease::yank_waits_for_a_killed_publishers_lease_and_says_so`.
- **Renewal, builds and tests (Decided here).** A release action is a whole build-system invocation, a stage or commit of a set, or a validation, not one node, so the guard renews at every effect and the long invocations are kept alive by explicit progress events, never by a timer.
  1. *Before an effect:* the guard renews every held lease (run and channel) immediately before each intent write, before each grant exchange and before each `stage`, `commit` or `abort` call, once per wave of coordinates and once per build or test invocation, and the engine stops before the call on `Fenced` or `LeaseLapsed` from either ledger. Held by `publish::run_lease_lost_means_zero_registry_writes`, `publish::channel_lease_lost_means_zero_registry_writes` and `lease::renews_both_leases_before_each_registry_write` (11).
  2. *During a build or test invocation:* a `ProcessSpec` carries `&dyn Heartbeat` (`fn beat(&self) -> Result<(), Stop>`, in `ucdk-release-seams`), and the `ProcessRunner` calls `beat()` on each progress event of the child it can observe: every chunk of its output and every exit poll. The build system's own progress lines are those events, whether it works locally or sends its actions to a remote service. The engine's `beat()` calls `renew_if_due()` on each held lease, which renews when less than half the TTL remains by the ledger's own clock (`Snapshot.at`), so a busy invocation renews about every half TTL of ledger time and a chatty one does not hammer the ledger. `Stop` (a lease fenced or lapsed) makes the runner kill the child, and the whole process group it started, and answer `Refused(LEASE_LOST)`; the engine then records nothing further and reports `INTERRUPTED` with `LEASE_LOST`. The seam has no timer and the engine has no thread: with no events there is no renewal, by design, and (3) covers that case. Held by `lease::a_build_longer_than_the_ttl_that_reports_progress_keeps_both_leases` and `lease::a_test_longer_than_the_ttl_that_reports_progress_keeps_both_leases` (a `ManualClock` moved by the fake process runner between beats), `lease::a_beat_after_a_takeover_stops_the_invocation_and_records_nothing`, `lease::a_beat_renews_only_when_less_than_half_the_ttl_remains`, and the `ProcessRunner` kit scenario `the_runner_beats_on_progress_and_stops_the_child_when_told` (4.6).
  3. *Before a Confirmed write after an effect* (a build or test result, a validation result, a publication confirmed after its read-back poll): the guard renews, and when the lease has lapsed, the document is still at the token the guard last wrote and no grant has been made since the guard's own, `reacquire_if_unchanged(token, fence)` takes it again under a new fence and the write goes ahead. The two conditions are both needed: a lapse with another writer in between changes the token, but a later grant to the same holder name does not (`Doc::acquire` raises the fence and leaves the version alone, so a killed attempt is retaken at once, 3.3 above), and a zombie first attempt whose silent build ends after attempt 2 acquired would otherwise reacquire, fence attempt 2 out and ping-pong with it. Refusing when the fence is not the guard's own closes that, but only if the check and the grant are one atomic call: reading `Snapshot.fence` and then calling `acquire` would leave a window in which attempt 2 acquires between attempt 1's read and its acquire, and attempt 1 would then fence attempt 2 out. The guard therefore calls `Ledger::acquire_if(holder, ttl, token, fence)` (3.1, `ucdk-ledger` row (5)) and never reads then acquires; a precondition that no longer holds is `LeaseError::Changed`. A refused write is `Lost`, `INTERRUPTED`, `LEASE_LOST`. This is the recovery for a silent build or test longer than the TTL: its result can be recorded, so a rerun adopts it (5.4) instead of rebuilding for ever. It is never used before an intent, a grant exchange or a `stage`, `commit` or `abort` call: nothing starts under a re-acquired lease. Held by `lease::a_silent_build_longer_than_the_ttl_is_confirmed_by_reacquiring`, `lease::a_silent_build_whose_lease_was_taken_over_is_not_confirmed`, `lease::a_second_attempt_of_the_same_holder_fences_a_silent_first_attempt` (attempt 2 acquires; attempt 1's silent build ends and its reacquire is refused; attempt 2 is not fenced and writes), `guard::reacquire_if_unchanged_calls_acquire_if_and_never_reads_then_acquires` (a ledger wrapper that fails the test on any `acquire` call while the guard reacquires), `lease::a_publication_confirmed_after_a_slow_read_back_poll_is_recorded`, and the end-to-end scenario `long_build_under_a_manual_clock` (8).
  4. *A `stage` or `commit` may outlive its lease.* The lease protects the ledger, not the registry (5.3): these calls have no deadline parameter and the engine cannot interrupt a seam call, so a hung registry call can land after the lease lapsed, and the next holder resolves it by `observe` (5.2). The claim that a write "cannot outlive the lease" is not made. Held by `publish::a_stage_or_commit_that_outlives_its_lease_is_resolved_by_the_next_holder`.
- **Engine.** A new engine on the same seam pattern (plain `Request` and `Outcome` enums, as `ucdk-engine/src/seam.rs` has today). It is not a reconciler: there is no desired-versus-observed graph, only an ordered machine and a record of where the run is. An action is `next = decide(machine, snapshot)` (pure) followed by executing `next` and writing the result. Only a Publish action behaves like the old engine (5.2). The engine takes a `Pause` as a parameter, and `LeaseGuard` takes no clock (it reads time only through the ledger, `Snapshot.at`, 3.1); neither reads any other time: `SystemTime::now` and `Instant::now` appear in one production constructor, `SystemClock`, and an `xtask lint` rule refuses them anywhere else in non-test code (`lint::wall_clock_is_read_only_in_system_clock`, PR 4).
- **`ucdk-api`: which taxonomy carries what (Decided here).** An `Error` with an `ErrorCode` answers a call that made no verdict: a malformed request, a session or ledger that could not be opened (`LEDGER`, `LEDGER_BUSY`), a busy session. A `Reason` lives inside a verdict, after the engine started: a ledger failure during a run is `Reason.LEDGER`, a held lease `Reason.LEASE_HELD`. One function, `exit_class(verdict, reason, landed)`, maps to the class, where `landed` says whether the engine recorded a landed or staged coordinate. Every verdict is named, so a new variant does not compile until it has a class. `Outcome` keeps wrapping a verb's answer next to its `ExitClass`; a call that made no verdict is its `invalid` arm (usage) or its `error` arm (a ledger that could not be opened or read), as 3.4 states.
- **C ABI.** Release verbs with the existing signature: `ucdk_release_check`, `_plan`, `_run`, `_status`, `_trust`, `_abort`, `_yank`, plus the kept `ucdk_ledger_show`. **Version rule (Decided here):** the deletion PR removes six exported functions, and under the loader rule "same major, library minor at least the SDK's" a stale SDK would pass the check and fail at symbol lookup. ## 4. Interfaces: build system, process runner, publisher, grants (Proposal)

All seams are synchronous, take `&mut self` and are `Send`. A session runs one call at a time. Every fallible method returns a classified error, never a bare bool or exception.

### 4.1 Error classification

```rust
pub enum SeamError {
    Refused(Reason),        // nothing happened; do not retry as is
    Permanent(String),      // will fail again; nothing happened
    Transient(String),      // failed, and may have landed: observe, then retry only if absent (5.2)
    RateLimited(Backoff),   // refused before it ran; retry after the stated number of Pause ticks
    InFlight(String),       // something may be underway; observe
    Unknown(String),        // the answer was lost; the effect may have landed; observe
    GrantRefused(GrantFault),   // the grant presented was refused before the call ran (6)
}
pub enum GrantFault { Denied, Expired, AlreadyUsed, Unreachable }   // Denied: the issuer or registry will not allow this identity this scope, including a grant that lacks the scope a call needs; Expired and AlreadyUsed: the grant (or the identity token behind it) is no longer good; Unreachable: the exchange got no answer from the issuer
```

`Refused`, `Permanent`, `RateLimited` and `GrantRefused` promise that no external effect landed. `GrantRefused(Expired)` and `GrantRefused(AlreadyUsed)` make the engine exchange again for the same phase and look before it goes on (5.2); `Unreachable` is an exchange that got no answer (the connection failed, or the platform could not give an identity token mid-job): nothing reached the registry, an identity token that was issued and not used expires, and the engine exchanges again within the same `attempts` bound and then stops `REFUSED` with `CREDENTIAL`; `Denied` stops the action (`REFUSED`, `CREDENTIAL`), and it is also what a registry's refusal for a missing scope maps to (a `403` or its equivalent at the call), so a stage grant used for a commit, where the issuer enforces the split, is `Denied` and writes nothing (`publish::a_grant_without_the_needed_scope_is_denied_and_nothing_is_written`, and the grant-source kit scenario `a_missing_scope_is_denied`). `Transient`, `InFlight` and `Unknown` do not: a registry may commit and then fail the response (a 5xx after the commit), and a seam that cannot tell must not call that `Permanent`, so `Transient` is "retry is allowed, after looking", not "nothing happened". The engine resolves all three by observing, never by assuming (`publish::transient_is_observed_before_retry`, kit scenario `transient_after_commit_is_observed_before_retry` against the fault `fail_after_commit(n)`).

### 4.2 Artifact store and build system

The store is a keyed tree, because a member is a file or an OCI layout directory and `verify_member` must see exactly what is in an entry:

```rust
pub struct SetScope { pub stage: String, pub platform: String, pub revision: String, pub generation: String }
pub struct StoreKey(String);                     // "<stage>/<platform>/<revision>/<generation>/m/<member name>" for a member, ".../set" for the set document; built only by StoreKey::member(&SetScope, name) and StoreKey::set(&SetScope)
pub trait EntryWriter {                          // scoped to one key; a `copy_out` caller gets only its own
    fn put_file(&mut self, rel: &str, bytes: &[u8]) -> Result<(), SeamError>;   // rel: relative, no "..", no empty part, never absolute
}
pub trait ArtifactStore: Send {
    fn begin(&mut self, key: &StoreKey) -> Result<Box<dyn EntryWriter + '_>, SeamError>;  // an empty entry; refused when it exists
    fn files(&mut self, key: &StoreKey) -> Result<Vec<String>, SeamError>;      // every relative path of the entry, sorted; empty when there is no entry
    fn get(&mut self, key: &StoreKey, rel: &str) -> Result<Option<Vec<u8>>, SeamError>;
    fn discard(&mut self, key: &StoreKey) -> Result<(), SeamError>;             // the whole entry
    fn keys(&mut self) -> Result<Vec<StoreKey>, SeamError>;                      // for the "nothing else is in the store" check
}
```

**The build system seam (Decided here).** Builds and tests run only through a `BuildSystem`. An implementation knows its kind's command line and output listing; it never decides what to build, where, or on what hardware, and it never writes into the store.

```rust
pub enum Verb { Build, Test, Query, Info }          // Query and Info are Bazel's two locating calls (2, layering); Info has no target
pub struct Invocation<'a> {
    pub system: &'a ucdk_release_proto::BuildSystem,   // the machine's, as authored
    pub target: &'a Target,
    pub verb: Verb,
    pub report: Option<&'a str>,    // Test only: the file the verb's ucdk-owned flag names (2), inside the invocation's own directory under --scratch
    pub stamp: &'a BuildStamp,      // an input; the build system reads it only through placeholders (2)
    pub platform: &'a str,          // the stage's, for the {platform} placeholder; "" when the stage names none
    pub heartbeat: &'a dyn Heartbeat,   // forwarded to the process runner; Err(Stop) means kill the child (3.3)
}
pub struct Command { pub argv: Vec<String>, pub env: Vec<(String, String)> }   // env in sorted key order
pub struct Located { pub label: String, pub path: String, pub shape: Shape }   // Shape: File or Directory; path is absolute in the build system's output tree
pub struct TestOutcome { pub passed: bool, pub ran: u32, pub tail: String }   // ran: test cases that ran (passed or failed, never skipped), read from the report file; tail: the last lines of its output
pub trait BuildSystem: Send {
    fn kind(&self) -> BuildSystemKind;
    fn command(&self, inv: &Invocation<'_>) -> Result<Command, SeamError>;   // no effect: the layering of 2 as a pure function (a default method over `ucdk_release::invocation`)
    fn build(&mut self, inv: &Invocation<'_>) -> Result<Vec<Located>, SeamError>;   // runs the build, then lists its outputs with the build system's own query
    fn test(&mut self, inv: &Invocation<'_>) -> Result<TestOutcome, SeamError>;
    fn copy_out(&mut self, out: &Located, into: &mut dyn EntryWriter) -> Result<(), SeamError>;   // the files of one located output
}
pub struct ProcessSpec<'a> { pub command: &'a Command, pub cwd: &'a str, pub heartbeat: &'a dyn Heartbeat, pub stdout_limit: usize }
pub struct ProcessResult { pub exit: Exit, pub stdout: Vec<u8>, pub stderr_tail: Vec<u8> }   // Exit: Code(i32) or Signal(i32)
pub trait ProcessRunner: Send {     // argv and an explicit environment only; no shell; nothing inherited; the git Source (4.5) uses it too
    fn run(&mut self, spec: &ProcessSpec<'_>) -> Result<ProcessResult, SeamError>;   // beats on each chunk of output and each exit poll; Stop kills the child and its process group
}
pub trait OutputFiles: Send {       // read-only view of local files: the build system's output tree, and the report file of a test invocation
    fn list(&mut self, path: &str) -> Result<Vec<String>, SeamError>;      // relative paths under a directory, sorted; symlinks are reported, never followed
    fn read(&mut self, path: &str, rel: &str) -> Result<Vec<u8>, SeamError>;
}
```

`Buck2` and `Bazel` implement `BuildSystem` over a `ProcessRunner` and an `OutputFiles`; the `FakeBuildSystem` is the executable specification (4.5). The seam has three jobs and the engine does the rest.

1. **Run.** `build` runs the command of the layering in 2 with the verb `build`, in `cwd` = `--root`. A nonzero exit or a signal is `Permanent` with the tail of the output (the engine reports `FAILED` naming the artifact and `BUILD_FAILED`); a binary that cannot be started is `Unknown` (the engine reports `INDETERMINATE`). `test` runs the verb `Test`, once per target, in `cwd` = `--root`.
2. **Locate.** The output comes from the build system's own listing, never from a guessed path. Buck2: the same `build` command carries `--show-full-output`, and its standard output has one line per output, the label then a space then the absolute path (the path may hold spaces, so a line is split at the first space). Bazel: after the `Build` invocation, the `Query` invocation (`cquery`, `--output=files`; the table of 2) prints the output files as paths relative to the execution root, and the `Info` invocation (`info execution_root`) prints that root; both are laid out by the rule of 2 and have goldens, and the path of each output is the root joined with the relative path. The output must be a file on the local disk when the invocation returns: a Bazel that executes remotely must be told by the machine's own flags to download the outputs of the requested target (`--remote_download_toplevel`), and a located path that does not exist is `BUILD_OUTPUT`; Buck2 materialises the outputs of a requested target by default. A target must have **exactly one output**; none, or more than one, is `BUILD_OUTPUT` naming the label and the outputs found. For a `FILE` member the output is one regular file; for an `OCI` member it is a directory that is an OCI layout; any other shape, or a symlink anywhere in the output, is `BUILD_OUTPUT`. These command spellings are the intended ones and are confirmed against the real binaries by the on-demand job of 8 before PR 12 is accepted.
3. **Test.** `passed` is true only when the build system exits 0 and its report shows at least one test case that ran. The report is the file the verb's ucdk-owned flag names (2): for Buck2 the event log `events.json-lines` (2), one JSON object per line, in which `ran` counts the lines that carry a test-result event (the `TestResult` record of Buck2's event schema) whose `status` field is none of `SKIP`, `OMITTED`, `LISTING_SUCCESS` and `LISTING_FAILED` (a listing is not a run); for Bazel the build event JSON file, in which `ran` counts the `testcase` elements of the `test.xml` that each test-result event names, outside skips. The implementation reads the file through `OutputFiles` after the exit, and a missing or unparseable report, or a result with no case, is `ran = 0`: not a pass, never a guess from the console text. The parse is the pure `ucdk_release::test_report` (PR 3c), tested over transcripts, and the exact record shapes are fixed with them and confirmed against the real binaries by the on-demand job of 8 (question 19). ucdk can be no stricter than the report: a Bazel test that writes no `test.xml` is expected to get the single case Bazel itself records for it (the on-demand job checks this), so a target that runs but exercises nothing is a pass there, which is a property of the build system's report and is stated, not hidden (risk 22). A target that runs nothing is not a pass (`ROW_FAILED` with the detail "no test ran", the kit scenario `a_test_target_that_runs_nothing_is_not_a_pass`).

**What the engine does with an output.** For each artifact, in Kahn order over `needs` (ties by name, as before), the engine runs the build, takes the one `Located`, begins a store entry at `StoreKey::member(scope, name)` and has `copy_out` write the output's files into it through the `EntryWriter` (the build system cannot address any other entry), then **composes the manifest itself**: type and name from the declaration, `version` from the stamp, `platform` from the action, `file` from the located file's name (for `OCI`, the layout directory's name), `size` and `sha256` recomputed from the entry that was just written, never from the build system's tree, `stamp` from the stamp, and the metadata arm (the declaration's `labels` for `FILE`; `os` and `cpu` read from the layout for `OCI`). `verify_member` then checks the entry against that manifest (below). Reading back from the store and not from the output tree matters because a later invocation in the same output tree can change a file after it was listed; the second verification before sealing catches a store entry that was altered, and the copy catches a tree that changed between listing and reading. No member is handed to a build: a build's dependencies are in the build graph, and `needs` orders builds and publications and feeds `SET_CLOSURE`, nothing more.

**Store key parts (Decided here).** Every part of a key (stage, platform, revision, generation and member name) is refused when it is empty, is `.` or `..`, or contains `/`, `\` or any control character. `StoreKey::member` and `StoreKey::set` reach one private `join`, the single constructor, and `join` enforces this, so no key exists that a filesystem store could resolve outside its generation. A part read back from a record is held to the same rule, because the ledger is editable by anyone; the codec also refuses an `attempt` of 0 on decode, since attempts start at 1. Held by `store_key::dot_parts_backslash_and_control_characters_are_refused` and `codec::attempt_zero_is_refused`.

**Store layout and the set document (Decided here).** The store is namespaced by what built a set, so one `--store` root serves every revision, platform and stage (5.8). A Build action writes into a **generation**, `<run id>-a<attempt>`, named by the attempt that first writes into it, so a key is a function of (stage, platform, revision, generation) and the member name, and two revisions, two platforms or two runs never meet at one key (`build::two_revisions_in_one_store_do_not_collide`, `build::two_platforms_in_one_store_do_not_collide`). A rebuild therefore writes beside a sealed set and never over it. After the second verification (`verify_member` on every member, `verify_keys` before the set key exists) the engine writes the **set document**, the `ReleaseSet` of 2 in canonical encoding, as one file `set.pb` under the key `<scope>/set` (a document an earlier attempt left there is discarded first and written again, never trusted), checks the generation again with `verify_keys` now requiring the set key, and then writes the seal record (5.4) and the `stage` record, each carrying the generation. Nothing is renamed or promoted: a generation is complete when its set document exists and a seal or `stage` record names it, and a generation no record names is an orphan. **What the engine discards (Decided here).** The engine never discards a generation that any record it can read names: a `seal` record, a `stage` record, or the `action` record of a Confirmed Build action (which carries `generation`, 3.3). It cannot read the run ledgers of other runs, and a record there may still name a generation that a seal has since replaced (run A built G1 and half-published; run B changed a build flag, sealed G2 and replaced the seal that named G1; run A's `stage` record still names G1), so **a generation that a seal named is not discarded by the engine after another seal replaces that seal**: it stays until no stage record names it, and removing it is the driver's pruning of the store, which `status --store` supports by listing each generation no given ledger names and the records that do name it (`resume::a_replaced_seals_generation_is_left_in_place`, `resume::a_publish_job_of_the_run_that_built_the_replaced_generation_still_finds_its_set`, `status::a_generation_no_given_ledger_names_is_listed_as_an_orphan`). The one thing the engine discards is its own run's unconfirmed work: before it begins a build in a new generation, the generations named `<run id>-a<n>` in the scope that no seal, `stage` or Confirmed `action` record names (an attempt cut short by a kill left partial members and confirmed nothing) are discarded (`resume::a_rerun_discards_its_own_earlier_unconfirmed_generation_only`; another run's orphans are left alone and `status` lists them). **Where attempt 2 finds attempt 1's generation (Decided here).** A Build action writes `generation` into its `action` record in the same write that confirms it, so the generation is on the run ledger from the first confirmed build and not only once sealed. A later attempt of the stage reads the `action` records first. When a build is Confirmed with generation G and G is not sealed, the attempt continues in G, which is neither renamed nor discarded: builds Confirmed with the same inputs are skipped as `NOOP` and never rebuilt (so a build that is not byte-identical cannot change a member that was already verified), the entry of a build that was cut short is discarded and rebuilt, and the remaining builds run into G. Only when no `action` record names an unsealed generation does the attempt begin a new generation, after the discard above. The name is therefore the name of the attempt that first wrote into the generation. Attempts only increase (the `stage` record holds the latest, 3.3), so a name is never begun twice, and `begin` on an existing key is still refused (`a_second_begin_on_one_key_is_refused`), which the engine reports as `REFUSED` naming the key and never overwrites. A wiped run ledger (5.8) leaves no `action` records: the stage is a first attempt, its own earlier unconfirmed generation is discarded by the rule above, and a sealed generation is found by adoption (5.4) and not discarded. Tests: `resume::a_kill_before_sealing_seals_the_earlier_attempts_generation` (every build Confirmed, killed before the seal; attempt 2 runs no build system, writes the set document into attempt 1's generation and seals it, and a counter on the fake build system asserts it was not called), `resume::a_kill_after_one_of_two_builds_continues_in_the_generation_of_the_confirmed_one`, `resume::a_wiped_run_ledger_discards_its_own_unnamed_generation_and_builds_again`. A crash anywhere in a rebuild leaves the previously sealed set intact, so the bytes that half-published coordinates were made from survive (`resume::a_crash_mid_rebuild_leaves_the_sealed_set_intact`). The set document is not trusted and is never in the ledger's place: every reader recomputes `set_hash` from the members and refuses a differing value (`SET_HASH`); a missing or unreadable document is `REFUSED` with `SET_HASH` naming the key. A PUBLISH job reads the `stage` record of its needed BUILD stage from the run ledger for `set` and `generation`, reads the set document at that generation, runs `verify_member` on every member and requires the recomputed hash to equal both the document's and the record's (`publish::the_publish_job_rebuilds_the_set_from_the_store_and_the_stage_record`, `publish::a_set_document_that_disagrees_with_the_stage_record_is_refused`, `publish::a_missing_set_document_is_set_hash`). The document stores no key: a member's key is always `StoreKey::member(scope, name)`, derived from the scope (the `stage` record's stage, platform, revision and generation) and the member's name, so a document cannot point a reader at another generation or scope (`descriptor::a_member_carries_no_store_key`, `publish::members_are_read_at_the_derived_key_only`). The `FileMeta` labels that `SET_CLOSURE` reads (4.4) come from the document's manifests, so the closure validation and the publisher read one source.

A located output is written into its own entry through the `EntryWriter` that `copy_out` is handed; the build system cannot address another member's entry, and the store refuses a path that escapes its entry (`..`, an absolute path, a symlink the filesystem store meets). Run identity is not in `Invocation`: the run id and attempt never reach a build, and the only run-dependent values a build can see are the stamp's fields through the placeholders, so a rebuild with the same stamp and the same bytes out of the build system has an identical set hash.

The engine, not the build system, verifies each member, against the manifest it composed. The check is not circular: the digest, size and shape are recomputed from the bytes in the store, so a build system that lists one file and leaves another in the tree, a tree that changes between listing and copy, and a store entry altered afterwards are each caught, and the same function runs again in the second verification and in PUBLISH from the set document. One `verify_member` function checks that the manifest name equals the declaration byte for byte; that the entry is exactly what the manifest says (for `FILE` the entry holds one file, named `Manifest.file`; for `OCI` every path of the entry lies under the directory `Manifest.file` and the tree is a layout: `oci-layout`, `index.json`, `blobs/sha256/<hex>`, each blob hashing to its name); the identity digest recomputed from those files (2) equals `sha256`; `size` equals the recomputed size (2); the file is non-empty; the platform is the run's or `any` (and for `OCI` equals the layout's `os`-`cpu`, `PLATFORM_MISMATCH`); the version equals `BuildStamp.version` (`MEMBER_VERSION`); the recorded `stamp` equals the build's; and no other path exists in the entry. A second function, `verify_keys(scope, set, expect)`, is about the generation and not about one member: the keys of the generation are exactly the member keys of the set, and with `expect` = `MembersAndSet` the set key must also exist, while with `MembersOnly` it is neither required nor refused; any other key refuses the set (`SET_MEMBER`). `verify_member` runs after each build, again before sealing (the second pass is the one hashed, so a later build that changed an earlier member is caught), and again by PUBLISH before it sends anything. `verify_keys` runs with `MembersOnly` before the set document is written, and with `MembersAndSet` after it is written, in adoption (5.4) and in PUBLISH (5.2), so the check before the document exists cannot demand the document (`verify_keys::before_the_set_document_exists_only_member_keys_pass`, `verify_keys::after_the_write_a_missing_set_document_is_refused`, `verify_keys::an_extra_key_is_set_member`, `build::the_second_verification_passes_before_the_set_document_exists`). Versions are in lockstep by default: a set whose members disagree with the release version is refused, never published. The release version is the required `--release-version` of a BUILD stage, recorded in the run record, so the reference value of the check has one source (2).

Artifacts build in Kahn order over `needs`, ties by name, one build-system invocation per artifact, so that a failure and an output belong to one target (the build system's own daemon and cache keep repeated invocations cheap). A failing build leaves no manifest. A build that cannot be started is `INDETERMINATE`; one that exits nonzero or is signalled is `FAILED` and names the artifact, its label and the tail of its output.

The real `ProcessRunner` (PR 12) owns the contract that is not in `verify_member` or the layering: it starts the child from the argument vector and the explicit environment only, inherits nothing and uses no shell, resolves a bare program name on the `PATH` of that explicit environment and never on its own (2, layering), starts it in its own process group, calls `beat()` on every chunk of the child's output and every exit poll, and kills the group on `Stop`; each is a kit scenario it must pass. ucdk sets no time limit on a build or a test (1.1). `{timestamp_ms}` is the stamp's `timestamp_ms`: a required flag for a stage with a Build or Test action, pinned in the run record, so a resume rebuilds with the same value, and kept by adoption (5.4), so a rebuilt member cannot differ because the time did. A `CONDA` or `PYTHON` coordinate needs a finer platform than `<os>-<cpu>` (a conda subdir), which neither `Coordinate` nor the metadata arms carry today; those types are not accepted by the machine reader until their arm adds the field and `Coordinate` carries it.

### 4.3 Publisher (a registry)

```rust
pub enum Presence { Absent, Staged(Held), Present(Held), Yanked(Held) }   // Held: identity digest, stamp, exceptional mark (2); Staged: held by the registry and not readable by a stranger, so only an observe that carries a grant can return it; a stranger's read answers Absent
pub enum StageAnswer { Staged, Duplicate }
pub enum CommitAnswer { Committed, Duplicate }
pub enum CommitUnit { Set, Coordinate }     // Set: one commit call makes every coordinate it names readable, or none; Coordinate: each one on its own
pub struct StageItem<'a> { pub coordinate: &'a Coordinate, pub file: &'a Blob<'a>, pub held: &'a Held }
pub trait Publisher: Send {
    fn types(&self) -> &[ArtifactType];
    fn stages(&self) -> bool;              // true if the channel holds staged bytes that are not yet readable; false: `stage` and `abort` are never called and `commit` carries the bytes
    fn commit_unit(&self) -> CommitUnit;
    fn conditional_put(&self) -> bool;     // true only if a commit is an atomic create-if-absent of the coordinate
    fn grant_limit(&self) -> usize;        // the most coordinates one grant may cover; usize::MAX when the channel has no limit
    fn observe(&mut self, g: &Grant, k: &Coordinate) -> Result<Presence, SeamError>;
    fn stage(&mut self, g: &Grant, items: &[StageItem<'_>]) -> Result<StageAnswer, SeamError>;   // creates the staged state; an atomic create-if-absent against held and staged coordinates
    fn abort(&mut self, g: &Grant, ks: &[Coordinate]) -> Result<(), SeamError>;                 // gives staged state back; never touches a committed coordinate
    fn commit(&mut self, g: &Grant, items: &[StageItem<'_>]) -> Result<CommitAnswer, SeamError>;   // makes the staged coordinates readable
    fn yank(&mut self, g: &Grant, k: &Coordinate, reason: &str) -> Result<(), SeamError>;
    fn fetch(&mut self, g: &Grant, k: &Coordinate) -> Result<Option<Vec<u8>>, SeamError>;
    fn newest(&mut self, g: &Grant, ch: &str, name: &str) -> Result<Vec<(Coordinate, Held)>, SeamError>;
    fn list(&mut self, g: &Grant, scope: &ListScope) -> Result<Vec<Listed>, SeamError>;   // may lag
}
```

**The channel kind is data, never a branch (Decided here).** `Channel.kind` picks which `Publisher` and `GrantSource` the session builds for the channel, and nothing else reads it: the engine sees only the trait, and every difference between registries is a method above (`stages`, `commit_unit`, `conditional_put`, `grant_limit`) or a kit scenario. The first kind the project uses is `PACKAGE_REGISTRY`: a registry that stages a whole set in one group (`stages() == true`), makes it readable in one commit (`CommitUnit::Set`) and bounds the coordinates one grant may cover. `DIRECTORY` is the reference kind with no network and no grants: it does not stage, commits each coordinate by an atomic rename (`CommitUnit::Coordinate`), and has an `Anonymous` push identity. A channel that cannot stage skips the stage phase and its grant; the commit grant covers the write. Another kind (an OCI registry, a conda channel) is a new implementation of the same traits and a new enum value, with no engine change.

There is **no delete and no force parameter**: the signature cannot express an overwrite, and **the contract does not allow one either (Decided here)**. **The write is an atomic create-if-absent in both phases.** `stage` creates the staged state only if the coordinate is neither held nor staged by someone else, and `commit` makes it readable only if no other writer has created the coordinate meanwhile: between `observe` returning `Absent` and either call, another writer may create the coordinate, and the call must then answer `Duplicate` and leave the existing bytes. A staged coordinate is not a published one: it is not readable, it is not permanent (`abort` gives it back), and no read-back or monotonic decision counts it. An implementation that cannot promise the create-if-absent (a plain tag push that replaces an existing tag) answers `conditional_put() == false` and is refused as a channel home, like `no_digest_exposed`. For `OCI` this means digest-addressed coordinates or a registry with tag immutability, which the first OCI publisher must declare; the kit scenario `commit_over_present_different_leaves_old_bytes` runs against every implementation that declares itself conditional. `stage` and `commit` carry the `Held` they are writing so a registry can store the stamp and the exceptional mark beside the bytes, which `newest` and `observe` return; a registry that cannot store them is refused as the home of a `monotonic` channel (kit scenario `observe_returns_the_stamp_it_was_given`). `observe` is a point read decided by fetching and hashing, and is authoritative. `list` may lag and is used only for reports (new names, with `newest`, 7), never to decide an effect. **`newest` is one contract (Decided here):** it returns every coordinate of the name that the channel holds, of any version and platform, yanked ones included, each with its `Held`, and compares nothing; the engine compares (5.6) and the plan reads whether the answer is empty (7). The kit scenario `newest_lists_every_held_coordinate_of_the_name` holds it. **A grant of the stage scope can observe the staged state its own action made, and a grant of the commit scope can observe it too (Decided here):** a staging channel kind whose scopes cannot is refused as a channel home (kit scenarios `a_stage_grant_observes_the_staged_state_it_made` and `a_commit_grant_observes_it_too`, beside `a_staged_coordinate_is_not_readable_by_a_stranger`). A registry that exposes no digest in `observe` is refused as a channel home for that type: comparing identity field by field with no common field is a refusal, never equality. `Duplicate` is never an error to retry; the caller observes to tell "same bytes" from "someone else's", and `Duplicate` over other bytes is a refusal that leaves no intent behind (5.2, commit phase, step 4). A transport failure on a mutating request is `Unknown`, because the caller cannot tell whether the bytes left. A `grant_limit` smaller than the number of coordinates of a Publish action is a refusal at preflight (`CREDENTIAL`, before any exchange), because one grant must cover every coordinate it is used for (6).

### 4.4 Validations and tests

There is no validator seam: a validation is a built-in kind that the engine evaluates, runs no command and creates nothing outside ucdk (1.1). **Rows are derived, not authored.** Before it reads anything the engine derives the list of row names from what the validation reads (one per member, one per coordinate, one per test target), and the pure `account_rows` (which takes the derived names with their one-sentence assertions as an `ExpectedRow` model type in `ucdk-release`, no longer a wire message) compares what was evaluated with that list index by index, because a count check alone passes a truncated run. A missing row, a swapped pair, a duplicate and an empty derived list are each a fault naming the first divergent index. The verdict is `SUCCEEDED` only with at least one asserted row and every asserted row `ROW_PASSED`. `ROW_NOT_REACHED` and `ROW_UNREADABLE` are never a pass. `INDETERMINATE` means the subject could not be read. A spec fault is exit class 3, a failed row is class 7. Timeouts and skipped-by-request are action-level facts, not row states. A validation takes no secret.

**`SET_CLOSURE` (Decided here).** Its subject is the sealed set: for a Build action, the set just sealed; for a Publish action, the set the stage's needed BUILD stage sealed, read from the store as PUBLISH reads it (5.2). The machine rule `machine.publish_stage_needs_validated_build` (2) names this kind. It has one derived row per member, `<member>: every requirement names a member of the set`. A member's requirements are the comma-separated names in its `FileMeta` label `requires`, which the declaration authored (an `OCI` member has none and its row passes with the single fact that it declares none). A requirement that names no member of the set is a failed row naming it. The system-library and glibc checks of an operating-system closure are not in v1: the kinds that carry them (`CONDA`, `PYTHON`) are not accepted yet (4.2), and a later kind adds them. It is a pure function of the set document (`ucdk_release::set_closure`, PR 3), so it has no seam and no fake.

**`CHANNEL_READBACK` (Decided here).** A validation names no channel; its subject is fixed by its holder. **On a Smoke action** the subject is the coordinates of the Smoke action's own artifacts and channel (they were published by an earlier Publish action of the stage, `machine.smoke_shape`). **On the stage** the subject is every coordinate of every Publish action of the stage, in the order the actions are listed and then the order of each action's artifacts, each read through that action's own channel; a stage of two Publish actions to two channels therefore has the rows of both, and a stage that holds a Publish and a Smoke action has the Publish action's rows at stage level and the Smoke action's rows on the Smoke action. Placement requires the holder: on the stage only when the stage holds at least one Publish action (`machine.validation_placement`). It has one derived row per coordinate, `<channel>/<name> <version> <platform> (<type>): the channel serves the set's digest`, so two channels never share a row name. The engine calls `Publisher::observe` for each (anonymously for a `PUBLIC` repository, so the read sees what a stranger sees; with the commit grant for a `PRIVATE` one), polls at most `wait_polls` times per coordinate with one `Pause` tick between polls, and the row passes when the answer is `Present` with the digest of the set. This is the read-back of what was published, never the observation that decides a commit (5.2), which carries a grant on every repository. Tests: `readback::a_stage_level_readback_covers_every_publish_action_and_each_channel` (two Publish actions, two channels: rows of both, a failure of one channel's coordinate fails the validation and names the channel), `readback::a_stage_with_a_publish_and_a_smoke_action_reads_each_coordinate_under_its_holder`.

**A Test action (Decided here).** Its subject is the build system: one derived row per target, named by its label, `<label>: the test target passes`. A row is `ROW_PASSED` only when `TestOutcome.passed` (the build system exited 0 and reports at least one test case run, 4.2); a failing target is `ROW_FAILED` with the tail of its output in the detail; a build system that could not be started is `ROW_UNREADABLE` and the action is `INDETERMINATE`. The action's verdict is `VALIDATION_FAILED` with `Reason.VALIDATION` (exit class 7) when any row failed. Targets run in the order listed and the action stops at the first target that is not a pass, the later rows being `ROW_NOT_REACHED`. A Test action carries no `validations` list because it already is one (`machine.test_shape`).

### 4.5 Other seams and the fakes, first

```rust
pub struct SourceStamp { pub build_number: u64, pub source_commit: String }
pub trait Source {                       // version control, behind one seam
    fn stamp(&self, revision: &Revision) -> Result<SourceStamp, SeamError>;
    fn is_ancestor(&self, a: &Revision, b: &Revision) -> Result<Tri, SeamError>;
}
pub enum GrantPhase { Stage, Commit }
pub struct GrantRequest<'a> {
    pub repository: &'a Repository,      // its `push` says whose identity, which audience and which scope names
    pub phase: GrantPhase,
    pub coordinates: &'a [Coordinate],   // what the grant must cover: the coordinates of one Publish action, at most Publisher::grant_limit
    pub exceptional: bool,               // use the exceptional subject and environment (6)
}
pub trait GrantSource {                  // Grant is opaque: neither Debug nor Display, no clone, zeroes on drop, carries only the issuer's stated expiry
    fn grant(&mut self, req: &GrantRequest<'_>) -> Result<Grant, SeamError>;   // an `Anonymous` push identity answers Grant::none() with no exchange
}
pub struct Stop;                         // a lease was fenced or lapsed: stop what you started

```

`Source::stamp` takes the newest first-parent commit at or below the revision that touches anything other than the machine's `stamp_ignore` paths; the build number is the first-parent count up to it, so a documentation-only commit never raises it. A shallow history, a head that is not the revision, or a dirty tree is a refusal. It returns the build number and the commit only. The `BuildStamp` a stage with a Build or Test action gives the build system, through placeholders, is those two plus the required flags `--release-version` and `--timestamp-ms` (2); both flags are recorded in the run record and a resume that presents a different value is `PIN_MISMATCH` (5.4).

`ucdk-release-fake` is the executable spec. It is in-memory and deterministic, with no clock, I/O or `HashMap`.

## 5. State, idempotency, crash and ambiguity (Proposal)

### 5.1 Principles

1. Observe before every effect. The ledger records intent before every effect. Nothing is trusted from an earlier read.
2. A coordinate is unique and permanent. Content identity is the digest, compared on exposed fields only.
3. Every local check happens before the first grant exchange or registry call. A refusal makes zero exchanges and zero calls.
4. An ambiguity is never a pass and never a plain failure. It is `INDETERMINATE` or `PARTIAL` and says what to look at.
5. The registry's state never depends on a record, and a record is never the authority on what is published: deleting every record changes no verdict about a coordinate (`publish::wiped_channel_ledger_changes_no_verdict`). The run-level gates do depend on records: stage admission (5.7), and the pin checks of 5.4. They fail closed where a record is what they check: a missing `stage` record for a needed stage is `STAGE_NOT_ADMITTED`, a `run` record that differs from the presented machine, revision, platform or stamp is `PIN_MISMATCH`, and either is a refusal, never a pass. The one place a missing record is not a refusal is a stage with no `needs` and no earlier `run` record (a fresh run, or a run whose ledger was wiped): there is nothing to compare, it starts a fresh run, and a changed machine cannot be detected (5.4). The crash sweep also runs with the run ledger wiped between runs (8).
6. A stage's actions run in order, each followed by its own validations, and then the stage's validations run; the run stops at the first action or validation that is not `SUCCEEDED` or `NOOP`. **The exception is a Publish action:** its validations run between its stage phase and its commit phase, because they gate the commit and nothing is readable before it (5.2); the engine never commits before they pass. Later items are reported `NOT_REACHED`, which never reads as a pass; it is a value of the report only and no record carries it (3.3). **A stage is confirmed only when every action and every validation, action-level and stage-level, is `SUCCEEDED` or `NOOP`**, and the `stage` record that says so (`confirmed=1`) is written last, after the final confirmation (3.3): a stage whose last action succeeded but whose stage-level `CHANNEL_READBACK`, or any action's validation, failed or did not run is not confirmed, and stage admission (5.7) refuses the stage that needs it.

### 5.2 Publish: stage, then commit (write-ahead)

Preflight, once per action and before any registry write (the grant exchange that its last step needs is the first one of the action): stage admission (5.7); the run hash against `--expect-hash` (`RUN_HASH_MISMATCH`); every coordinate to be written is in the declared set (`APPROVED_NAMES`: the engine refuses a name the machine does not declare, as the last gate against an undeclared upload); read the `stage` record of the needed BUILD stage (`set`, `generation`) and the set document at that generation (4.2); `verify_member` on every member and `verify_keys` requiring the set key; recompute the set hash and require it equal the document's, the stage record's and the `set` of the `SET_CLOSURE` validation record admission read; require the number of coordinates not to exceed `Publisher::grant_limit` (`CREDENTIAL`, before any exchange); then `observe` every member **with the first grant of the action, whatever the repository's visibility**: the stage grant when the channel stages and the commit grant when it does not, so the first exchange is the last step of preflight, after every local refusal (6). A stranger's read (`Grant::none()`) never sees staged state, so an observation that must tell `Staged` from `Absent` cannot be anonymous even on a `PUBLIC` repository; the stranger's reads are the read-back of a `PUBLIC` repository and a Smoke action (4.4). Any member `Present` or `Staged` with another digest stops the action `REFUSED` (`PUBLISH_DIFFERENT_BYTES`, every such member listed, nothing sent). Every member present with our digest makes the action `NOOP`. Any failed observe makes it `INDETERMINATE`. A publisher that is not `conditional_put`, or that cannot return a stamp for a `monotonic` channel, is refused here (`CHANNEL`).

Then the action runs up to three phases, and each one finds its starting state by observation, never by a record.

**Stage phase** (only when `Publisher::stages()`; a channel that does not stage goes straight to the commit phase and its grant covers the write).

- S1. Hold the stage grant (6): the one the preflight observation exchanged, else exchange it now (write the `grant` record `Intent`, renew both leases, call `GrantSource::grant`, record the answer). A refused exchange is `REFUSED` with `CREDENTIAL`, nothing landed (`publish::a_refused_stage_grant_stages_nothing`). Before each later call of the phase the grant's stated expiry is checked against the margin of 6, and a grant inside it is exchanged again first (a grant that was already inside the margin when issued serves its whole phase, and a margin exchange does not count against `Publish.attempts`, 6); that rule holds for every call of every phase below.
- S2. For every coordinate still `Absent`: renew both leases, then write the `publication` intent (`Intent`, `phase=staging`, digest, readable coordinate) under the fence. A `Fenced` or `LeaseLapsed` answer from either ledger stops the run before the call.
- S3. Renew both leases again, then `stage` every such coordinate in one call: `Staged`, `Unknown` or `InFlight` go to S4. `Duplicate` is observed: our digest is a converged earlier attempt, another digest is `REFUSED` (`PUBLISH_DIFFERENT_BYTES`) with the intents removed after the observe. `Transient` is observed first and `stage` is sent again only if a coordinate is still `Absent` and fewer than `Publish.attempts` calls of the phase have been sent (the first counts); `RateLimited` waits the stated `Pause` ticks, observes and retries within the same bound. `GrantRefused(Expired)` or `GrantRefused(AlreadyUsed)` exchanges a new stage grant (a new `grant` record), observes, and goes on from what it sees, and counts as an attempt of the same bound (`publish::an_expired_stage_grant_is_exchanged_again_and_the_state_observed`); `GrantRefused(Denied)` is `REFUSED` with `CREDENTIAL`. `Refused` or `Permanent` is `FAILED`, nothing landed, and each intent is removed only after an observe shows `Absent`.
- S4. Observe every coordinate, with the stage grant whatever the visibility. `Staged` with our digest (or `Present` with our digest, an earlier run having committed it) is staged. `Absent` after a `Staged` answer is `INDETERMINATE` (the registry may lag), intents left. Another digest is `REFUSED` (`PUBLISH_DIFFERENT_BYTES`), `PARTIAL` with `PUBLISH_STAGE` when some of our coordinates are staged, which the report names, because staged state is an effect that landed. Then each intent is rewritten with `phase=committing`, so a record that says `committing` is the record of a commit that may have started. The stage grant is dropped (zeroed) here and is never presented again in this action except for an `abort` or a retry of S3.

**Validation phase.** The action's own validations (`SET_CLOSURE`, 4.4) run now, with nothing readable yet. They are part of the action, not an add-on: a Publish action selected alone (`--only action:<name>`, 7) runs them like any other run, and a validation that cannot be evaluated (the set unreadable) ends the action `REFUSED` or `INDETERMINATE` before the commit phase, so no selection and no resume commits without them (`publish::a_selected_publish_action_runs_its_pre_commit_validation_before_the_commit`, `publish::a_publish_action_whose_validation_cannot_be_evaluated_does_not_commit`). A resume that finds the validation record `Confirmed` for the same `set` skips the read as `NOOP` by the rule of 5.4, which is the one case this phase does not read again. A failing validation ends the action `VALIDATION_FAILED`, and before it returns the engine calls `abort` for every coordinate it staged, under a stage grant (exchanged again if the first is no longer good), and observes that each is gone (`publish::a_failed_validation_before_commit_aborts_the_staged_state`). An abort that cannot be confirmed leaves the verdict `PARTIAL` with `PUBLISH_STAGE`, because staged state landed.

**Commit phase**, per wave: with `CommitUnit::Set` one wave holds every coordinate; with `CommitUnit::Coordinate` each coordinate is a wave, in Kahn order of the declared `needs`.

1. Exchange the commit grant (6), once before the first wave and again after an expiry: `grant` record `Intent`, renew, `GrantSource::grant`, record. This is a separate exchange from the stage grant, made after the validations passed and as late as possible, so no time spent staging or validating can have used up its lifetime. A refused exchange is `REFUSED` with `CREDENTIAL`, and `PARTIAL` instead when any coordinate is staged or committed, because those landed (`publish::a_refused_commit_grant_commits_nothing_and_reports_the_staged_state`).
2. `observe`, **with the commit grant whatever the repository's visibility** (a stranger's read answers `Absent` for staged state, so on a `PUBLIC` repository an anonymous observe would refuse every commit as `PUBLISH_STAGE`; `publish::staged_state_is_observed_with_a_grant_on_a_public_repository` stages and commits on a `PUBLIC` repository of a fake registry whose stranger reads cannot see staged state, and asserts that no observe of a staged coordinate was made with `Grant::none()`):
   - `Staged` with our digest: continue to 3. Nothing else is trusted about the staged state: not the record, not an earlier call.
   - `Staged` with another digest, or `Absent` for a coordinate the stage phase staged (the fake's `lose_staged_state`): `REFUSED` with `PUBLISH_STAGE`, nothing committed, `PARTIAL` if an earlier wave committed. The staged state that remains is reported and is given back with `ucdk release abort`.
   - `Present` with our digest: write a `publication` record `Confirmed`, with `Origin::Adopted` when no intent of ours exists (someone published identical bytes), otherwise confirm the intent. Effect `ALREADY_PRESENT`.
   - `Present` with another digest: `REFUSED` `PUBLISH_DIFFERENT_BYTES`, never retried, never forced. `PARTIAL` if an earlier coordinate of this action landed or any of ours is staged.
   - `Yanked`: `REFUSED` `PUBLISH_YANKED`. A yanked coordinate is burned whatever its bytes.
   - observe fails: `INDETERMINATE`, nothing written.
   - `Absent`, on a channel that does not stage: continue (the coordinate was never staged).
3. Renew both held leases (3.3), then write the intent when none exists (a channel that does not stage writes it here, `phase=committing`; a channel that stages wrote it in the stage phase), under the fence. A `Fenced` or `LeaseLapsed` answer from either ledger stops the run before the call.
4. Renew both leases again, then `commit` the wave (the seam is atomic create-if-absent, 4.3):
   - `Committed`, `Unknown` or `InFlight`: go to 5.
   - `Duplicate`: `observe`. Our digest is a converged earlier attempt: go to 5. Another digest means no commit of ours landed: the action is `REFUSED` (`PUBLISH_DIFFERENT_BYTES`, `PARTIAL` if an earlier wave landed or our staged state remains), the intent is removed under the fence after that `observe`, and `landed` stays false for this coordinate unless it is still staged (`publish::duplicate_over_other_bytes_is_refused_and_leaves_no_intent`).
   - `Transient`: `observe` first, and send another `commit` only if the coordinate is still `Staged` (`Absent` on a channel that does not stage) and fewer than `Publish.attempts` calls of the phase (the first counts; 0 reads as `DEFAULT_PUT_ATTEMPTS`, 3, in `ucdk-release`) have been sent (a registry may have committed before it failed; `publish::transient_is_observed_before_retry`, `publish::transient_retries_stop_at_the_attempt_bound`). A different digest or a failed observe ends the action as in 2. With the bound spent and the coordinate not committed nothing landed beyond the staged state, and the wave is `FAILED` as for `Permanent` below.
   - `RateLimited`: wait the stated `Pause` ticks, then `observe` and retry within the same `attempts` bound; a rate-limited answer counts as an attempt (`publish::rate_limited_answers_count_against_the_attempt_bound`).
   - `GrantRefused(Expired)` or `GrantRefused(AlreadyUsed)`: the commit grant is no longer good, which is also what an expiry between the staging and the commit looks like on a registry that checks at commit. Exchange a new commit grant (a new `grant` record, step 1), then go back to 2 and observe: `Staged` with our digest commits again, `Present` with our digest is read back, anything else is as in 2. Each exchange counts as an attempt of the same bound (`publish::an_expired_commit_grant_is_exchanged_again_and_the_staged_state_found_by_observation`). `GrantRefused(Denied)` is `REFUSED` with `CREDENTIAL`, `PARTIAL` when anything is staged or committed.
   - `Refused` or `Permanent`: the wave is `FAILED`, nothing committed. The intent is removed only after an `observe` shows `Absent` (nothing of ours is held); a coordinate still `Staged` keeps its intent, so the record says what the registry holds. The action stops at this wave and later ones are `NOT_REACHED` (open question 3 recommends this policy).
5. Read back: `observe` (with the commit grant for a `PRIVATE` repository, exchanged again if it expired), polled at most `Publish.polls` times (0 reads as `DEFAULT_READBACK_POLLS`, 3), with one `Pause` tick between polls and no sleep (`publish::read_back_polls_stop_at_the_bound_and_are_indeterminate`; `machine::zero_bounds_read_as_the_defaults`).
   - Our digest: record `Confirmed` (the guard renews first, or re-acquires when the lease lapsed during the poll and nothing was written meanwhile, 3.3 item 3); effect `PUBLISHED`.
   - Another digest: `PARTIAL`, `PUBLISH_READ_BACK`, needs a human, intent left, dependents not attempted.
   - Still `Absent` when the polls are spent: `INDETERMINATE` (the registry may lag); intent left.

A dependent artifact (a group or index naming its members) is attempted only after a barrier: every one of its dependencies is `Confirmed` and has been read back, all members first and the dependent after the last read-back (`publish::dependent_waits_for_every_member_read_back`); with `CommitUnit::Set` the whole set is one wave, so no dependent becomes readable ahead of a member. A leftover intent whose coordinate is `Absent` on the next run is written again and staged again; one whose coordinate is `Staged` with our digest goes to the validation phase and the commit phase again. A rerun never takes the staged state on trust: it observes first, and a record that says `committing` over a coordinate that is `Absent` is staged again, not assumed lost or committed. Uniqueness of the coordinate at the registry makes that safe, so no stamp is needed to find "our" object. An action is done only when every coordinate is `Confirmed`. The action stops at the first failed wave (question 3); there is no concurrency flag and no concurrency invariant to test.

**What `abort` does (Decided here).** `ucdk release abort` and the validation phase give back staged state with `Publisher::abort`, under a stage grant, for the coordinates of the action that are `Staged` with our digest by observation; it never touches a `Present` coordinate, and a coordinate that is no longer staged is not an error (`publish::abort_never_touches_a_committed_coordinate`). The `publication` intents it resolves are removed after an observe shows them `Absent`.

**A Test action** (Decided here) writes its `action` record `Intent` with its input digest, renews both leases, and runs each target in order through `BuildSystem::test` (one invocation per target, beating on progress, 3.3). It writes no `publication`, needs no grant and creates nothing ucdk knows about. Its rows are the derived rows of 4.4, written with the `Confirmed` action record (renewed or re-acquired first, 3.3 item 3). A resume with the same input digest skips a `Confirmed` Test action as `NOOP`: its targets are not run again, because the record says they passed for these inputs and the run hash pins them. A `--only action:<name>` run runs it again, which an action record allows. **A Smoke action** writes an `action` record, needs a grant only for a `PRIVATE` repository (the commit grant scope, exchanged for the read), observes each coordinate of the action's channel as a stranger would, and runs its `CHANNEL_READBACK` validations (4.4); it changes nothing outside the ledger.

### 5.3 The ambiguity table

| What happened | Local state | The next run | Verdict, exit |
|---|---|---|---|
| commit answer lost, registry committed | intent | observe: same digest, confirm | `INDETERMINATE` 5, then `NOOP` |
| commit answer lost, registry did not commit | intent | observe: still staged, commit again | `INDETERMINATE` 5, then `SUCCEEDED` |
| stage answer lost, registry staged | intent (`staging`) | observe: staged with our digest, go on to the validations and the commit | `INDETERMINATE` 5, then `SUCCEEDED` |
| killed after the stage, before the commit | intents (`staging` or `committing`) | observe: staged, so the validations run again and the commit follows; absent, so stage again | `INTERRUPTED` 6 |
| the staged state vanished before the commit | intents (`committing`) | refused (`PUBLISH_STAGE`), nothing committed; a new run stages again and commits once (`publish::staged_state_reaped_during_validation_is_refused_and_a_rerun_stages_again`, `publish::a_rerun_after_the_staged_state_vanished_stages_and_commits_each_coordinate_once`) | `REFUSED` 3, or `PARTIAL` 6 while any coordinate is still staged |
| a grant exchange refused (either phase) | `grant` record, `outcome=refused` | the same run exchanges again; the report names the repository, scope and the issuer's reason | `REFUSED` 3 (`CREDENTIAL`), `PARTIAL` 6 when anything is staged or committed |

| read-back shows other bytes after our commit | intent | same | `PARTIAL` 6 |

| a lease or its release could not be confirmed | unknown | the same run id and stage retakes it; others wait for the TTL | `INTERRUPTED` 6 (`LEASE_UNCONFIRMED`) |
| a build, test or validation outlives its lease with no progress event | lease lapsed, document unchanged | the result is recorded by re-acquiring (3.3 item 3); if another writer wrote meanwhile, it is not recorded | `SUCCEEDED`, or `INTERRUPTED` 6 (`LEASE_LOST`) |
| a killed attempt is retaken while its process still lives (a cancel race) | attempt 2 holds the lease under a newer fence | attempt 1 cannot re-acquire when its silent build ends, and attempt 2 goes on (3.3 item 3) | attempt 1 `INTERRUPTED` 6 (`LEASE_LOST`) |
| a stale run (a newer tip exists) | none | stops before any effect | `SUPERSEDED` 0 |
| source facts unknown, history unreadable | none | refused, never guessed | `INDETERMINATE` 5 |

Fencing protects the ledger, not the registry: a `stage` or `commit` already in flight is not recalled. The intent record and the coordinate's uniqueness make that call resolvable by the next holder. A run that has lost either lease starts no further grant exchange or registry write (3.3).

### 5.4 An interrupted run, and resume

A run is identified by the driver's run id and a required attempt (positive, no default, never minted here). The engine writes, before the first effect of a stage, the `run` record when the stage holds a Build or Test action and none exists (a `run` record is written once per run and read by every other stage), a `stage` record `Intent` (reads as RUNNING) carrying the attempt and the stage's platform, and an `action` record before each action. If it cannot write the first of them, the stage is `FAILED` with nothing done. A rerun uses a higher attempt and the same run id and stage, retakes the leases of that stage and channel at once (the holder is `run:<run id>/<stage>`, 3.3), and resumes the stage it is given. One release is one run id across all its stages (5.7), so the rerun of any stage finds the records of the stages before it:

1. A live lease held by another holder is `REFUSED` (`LEASE_HELD`), nothing changes, and the advice is that of 3.3. An expired lease is taken over after the skew bound (`MAX_CLOCK_SKEW` in `ucdk-ledger`, Exists), and the old holder's next write is refused as fenced.
2. The `run` record pins the machine hash, revision and the stamp (`version`, `build`, `commit`, `timestamp`); a stage's `stage` record pins its platform, its sealed set hash and its generation. A different machine, revision, release version or timestamp on resume is `REFUSED` (`PIN_MISMATCH`). Sealed members are re-hashed against the set; a difference is `REFUSED`.
3. Each non-final record is resolved:

| Record found | Meaning | Resume does |
|---|---|---|
| build `Intent`, no sealed set | a build was cut short | discards the cut-short member's entry and rebuilds it, in the generation the Confirmed Build actions of the stage name when there is one, otherwise in a new generation after discarding this run's unconfirmed earlier ones (4.2) |
| all builds confirmed, no sealed set | killed before sealing | re-verifies every member of the generation the `action` records name (4.2; no build system runs), replaces the set document and seals |
| test action `Intent` | the test run was cut short, or a target failed or ran nothing (a failure is not a state, 3.3) | runs its targets again, all of them, never `NOOP`: a test has no effect ucdk owns, and a build system's cache makes an unchanged target cheap |
| build action `Intent` after a failed build | a build failed (no manifest was written) | as the first row: the failed member's entry is discarded and it is built again |
| publication `Intent` | answer unknown | `observe` first, never `stage` or `commit` first (5.2) |
| grant `Intent` | an exchange whose answer is unknown | exchanges again; a token that was issued and not used expires (6) |
| validation `Intent` | cut short, or its rows did not all pass (a failure is not a state, 3.3) | evaluates it again, never `NOOP`: it reads a set or a channel and changes nothing outside ucdk |
| validation `Confirmed` with the same `set` (`SET_CLOSURE`) | passed on this very set | not read again, reported `NOOP` |
| validation `Confirmed` (`CHANNEL_READBACK`), or no validation record | a read-back is never skipped (the registry is the truth and may have changed); no record means the validation never ran in this run, which is the case when its action was skipped as `NOOP` or a new run id adopted a sealed set | evaluates it now and writes the record under this run |
| action `Confirmed`, same input digest (the action input digest, laid out in 2) | finished | skipped and reported `NOOP`; a published coordinate is still observed once, so a channel changed meanwhile is seen; the action's attached validations are then reached like any others and follow the validation rows above, so a skipped action never skips a validation that has no record |
| action `Confirmed`, different input digest | the run id is for one set of inputs | `REFUSED` `INPUTS_CHANGED`; use a new run id (a new run id adopts the sealed set, below) |

4. `status` reports a RUNNING record with no live lease as `INTERRUPTED` (exit 6) with the advice "run again to resume". The record is never rewritten to hide it.

**A new run id after a partial publish: adoption of a sealed set (Decided here).** Half-published coordinates are only recoverable if the next run uses the same bytes, and a build that is not bit-reproducible would otherwise produce another digest and be refused `PUBLISH_DIFFERENT_BYTES` for ever, with no delete to clear it. A BUILD stage therefore records a **seal**: a `seal` record in the seal ledger (3.3), written under the seal lease, which is taken for that write only, with `Confirmed` state, only after the set was verified twice, its set document written (4.2) and the stage's builds all `Confirmed`. Its name is `<stage>/<platform>/<revision>` and it carries the set hash, the generation that holds the set, the **build-inputs hash** and the producer's environment. The build-inputs hash is SHA-256 over the domain `ucdk/release-build-inputs/1` and the framed fields laid out in 2: the platform, the revision, the build stamp without its timestamp, the build system as authored, and for each of the action's artifacts (a list closed under `needs`, in Kahn order) its declaration (name, type, target label, target flags, target environment, needs, labels). Editing an unrelated stage, a Test action, a channel or a validation does not change it, so a machine edit made to fix the cause of a partial publish does not defeat adoption; editing the build system (its binary, config file, mode, flags or environment), a target's label, flags or environment, or an artifact does. A machine hash is not part of the key, but the machine's name is a field of the record, and **a seal ledger and a store root belong to one machine**: a BUILD that finds a record at its key whose `machine` differs from its own refuses the stage (`REFUSED`, `LEDGER`, naming the record) and never replaces it, so two machines whose stages share a name cannot replace each other's seals (`resume::a_seal_ledger_of_another_machine_is_refused_not_replaced`).

Before it builds, a Build action reads the seal record of its (stage, platform, revision) from `--seal-ledger` and adopts the stored set, reporting `NOOP` instead of rebuilding, only when **all** of these hold, each held by the test named:
1. the record exists in the seal ledger and is `Confirmed`. Every seal is written by `LeaseGuard::commit` under the seal lease, so a record in the ledger came from a holder of that lease; ucdk cannot prove more of a file anyone may edit, which is why the producer is inside the set hash and check 3 recomputes the bytes (risk 15). A record that is not `Confirmed`, or a generation in the store that no record names, is never adopted (`resume::a_store_entry_without_a_seal_record_is_not_adopted`, `resume::a_record_that_is_not_confirmed_is_not_adopted`);
2. its build-inputs hash equals the one computed now (`resume::a_changed_build_system_flag_or_target_is_not_adopted`, `resume::an_unrelated_machine_edit_still_adopts`);
3. the set document at the record's `generation` (4.2) is readable, every member passes `verify_member`, `verify_keys` requiring the set key passes, and the recomputed set hash equals the record's `set` (`resume::a_set_that_differs_from_its_seal_is_not_adopted`);
4. the set's `producer` equals this stage and environment, which the set hash covers, so a set made by any other stage or by a `CHANGE_CHECK` stage cannot be taken for it (`resume::a_set_from_another_producer_is_not_adopted`);
5. the set's member names equal the Build action's declared artifact names exactly (a list closed under `needs`, `machine.build_not_closed`), so a selective or partial earlier set is not taken for the whole (`resume::a_partial_set_is_not_adopted`).
The adopted set keeps its recorded timestamp and stamp, and the run record takes them. The adopting BUILD stage writes its own `stage` record with the adopted `set` and `generation` and rewrites the `generation` of its `action` records to it, because admission (5.7) reads the `stage` record (`resume::an_adopting_stage_writes_its_stage_record_with_the_adopted_generation`). The adopting stage's validations are not skipped with the build: the Build action is `NOOP`, and its `SET_CLOSURE` validation, having no record under this run, is evaluated against the adopted set and written with that `set`, then the stage's other actions and validations run and the stage is confirmed as any stage is, so a new run id that adopted a sealed set is admitted by the stage that needs it (`resume::an_adopting_run_evaluates_the_build_actions_validations`, `stage_admission::a_stage_built_by_adoption_is_admitted`). Adoption writes nothing to the seal ledger and takes no seal lease. **Writing a seal (Decided here).** When no record passes the checks, the BUILD builds in a new generation and, at the end, acquires the seal lease and re-reads the key: if a `Confirmed` record now exists that passes every check against its own stored set (another run sealed first), it adopts that set (its `action` and `stage` records take the adopted `set` and `generation`, as in adoption above) and only then discards its own generation, which no record names any more; otherwise it writes its record and releases the lease, and the generation the replaced record named stays where it is, because another run's `stage` record may name it (4.2) (`resume::a_concurrent_seal_that_passes_the_checks_wins`, `resume::a_seal_that_fails_the_checks_is_replaced_and_its_old_generation_is_left_in_place`). A stage has one platform and one Build action (`machine.stage_platform`, 2), so one key has one build action in one run. A `CHANGE_CHECK` stage neither reads nor writes the seal ledger; whoever may write the seal ledger is the trust anchor of adoption, and the driver gives `--seal-ledger` to release BUILD jobs only (ucdk refuses it for a `CHANGE_CHECK` stage but cannot know which jobs the driver trusts). `status` shows the sealed set hash. Held by `resume::new_run_id_adopts_the_sealed_set` and the end-to-end scenario `resume_with_new_run_id_after_partial_publish` (8).

**What adoption needs to persist.** Adoption needs the seal ledger and the store root to outlive the run that wrote them (5.8). Every store key and every seal name carries stage, platform and revision (4.2), so the driver persists the two as they are, and many revisions and platforms share one root without meeting (`resume::adoption_reads_only_its_own_key_and_a_replacement_touches_only_its_own_scope`: two revisions and two platforms in one store and one seal ledger). On an ephemeral runner with neither persisted by the driver, there is nothing to adopt: the Build action builds again, and a build that is not byte-identical produces another digest. A coordinate half published by the earlier run then stays `PUBLISH_DIFFERENT_BYTES` and the report says why and what to persist (`resume::without_a_persisted_seal_a_different_rebuild_is_refused_and_says_so`). This is stated, not hidden: the build-system kit's `same_command_same_bytes` is what makes it harmless for a reproducible build.

**Without the run records** (a wiped run ledger), exactly this holds, and the crash sweep asserts it: a stage that needs another has no `stage` record to read and is `STAGE_NOT_ADMITTED`; a stage with no `needs` starts a fresh run, because there is no `run` record to pin against, and a changed machine cannot be detected there. Resume is then neither an optimisation nor a gate for that stage; it is a new run. The gates that read a record fail closed where a record is what they check (5.1, 5.7) and nowhere else.

### 5.5 Yank and retention

- **No delete exists** in the trait, engine, ABI or CLI. It can be added later from history behind a new verb.
- **Yank (Proposal, section 0)** is explicit: `ucdk release yank --coordinate C --reason T --expect-hash H --run-id R [--run-ledger P]`. The engine takes the channel lease as `yank:<R>` (3.3), exchanges a commit-scope grant for the one coordinate (a yank changes what is published, so it needs the commit authority and no other; its `grant` record is written to the channel ledger under the same holder), writes `yanking`, calls `yank`, reads back `Yanked`, writes `yanked`. The bytes stay fetchable by exact coordinate, and re-publishing is refused. Yanking an `Adopted` publication takes the same flag and the record says it was adopted. **A yank stops later stages:** the publication record names the run and stage that published it (3.3); when `--run-ledger` is given and holds that run, the yank also sets `yanked=1` on that stage's `stage` record under the run ledger's lease (taken as `yank:<R>`, 3.3), so admission (5.7) refuses any later stage that needs it (`stage_admission::needed_stage_with_a_yanked_coordinate_is_refused`). Without `--run-ledger` the yank says on its last stderr line that later stages of the run are not stopped (`yank::without_a_run_ledger_says_later_stages_are_not_stopped`).
- **Retention** is "forever unless yanked". A registry that can only delete is refused as a channel home.
- **No validation leftovers.** A validation reads a set or a channel and creates nothing, so there is no validation run id, no journal, no sweep and no `leaks` verb (1.1). An operator re-run of a validation (`--only validation:<name>`) simply evaluates it again. What a test target creates outside ucdk is the test's and the build system's concern; ucdk records the test's result and nothing it made.

### 5.6 Admission, supersession, source policy

The driver supplies `SourceFacts`. The core reads no CI variable and runs no git outside `Source`.

**The gate depends on the trigger (Decided here).** A `RELEASE` stage that is not `exceptional` runs only when `on_mainline == YES`; `NO` is `NOT_ON_MAINLINE`; `UNKNOWN` is `INDETERMINATE`. A `CHANGE_CHECK` stage is exempt from `on_mainline`, from supersession and from `--admission`: it runs on a revision under review, which is never on the mainline, so those rules would refuse every one of its runs. It has its own gate: `SourceFacts.revision` is non-empty and equals the head `Source` reports with a clean tree (otherwise `REFUSED`, `SOURCE`); it takes no channel lease, no seal ledger and no grant (3.3, 6); `on_mainline` and `is_tip` are recorded and gate nothing. Held by `run::change_check_runs_off_the_mainline`, `run::change_check_runs_when_the_mainline_is_unknown`, `run::change_check_on_a_revision_that_is_not_the_head_is_refused`, `run::a_release_stage_off_the_mainline_is_refused`.

An `exceptional` stage on a run off the mainline needs a one-line reason of 1 to 200 bytes, the revision equal to the one the driver started, and uses the repository's `exceptional_subject` and `exceptional_environment` (6); what it publishes carries `exceptional = true` in its `Held`. A release run is never a dry plan: `plan` and `run` are separate verbs.

**`--admission` (Decided here).** It applies to `RELEASE` stages. A run whose revision is no longer the tip (`is_tip == NO`) stops `SUPERSEDED` before any record is created, and so does a rerun, **unless** the run ledger holds an unfinished record of this run id and stage (a `stage` record `Intent`, reading as RUNNING or INTERRUPTED): that rerun resumes (a publish still applies the monotonic rule below, so a moved tip never lets an older build replace a newer one). `is_tip == UNKNOWN` is `INDETERMINATE`. The attempt number is not consulted, and no stage is called "first". `SUPERSEDED` is class 0 by design: the report says nothing was run and a driver that wants to tell it from a success reads the verdict, not the class. Held by `admission::a_moved_tip_with_no_unfinished_record_is_superseded`, `admission::a_killed_stage_resumes_with_attempt_2_at_the_tip`, `admission::a_killed_stage_resumes_after_the_tip_moved`, `admission::an_unknown_tip_is_indeterminate`.

**Monotonic channels (Decided here).** A `monotonic` channel refuses a build older than one it holds. The held builds come from the registry (`newest` returns every held coordinate of the name with its `Held`, whose stamp was written at `stage` or `commit`, 4.3; the engine does the comparison), not from the ledger. Exceptional builds are never counted: they are reported, and never make a mainline run `SUPERSEDED` or `REFUSED`. Yanked builds are counted: a yank withdraws a coordinate, it does not un-build it. A set has several members, and the decision is made over all of them: the run is judged against the newest held build any member has, so one member with a newer mainline build decides for the set. A held build is newer than ours when its build number is greater. A held build with an equal build number and another commit is not newer by number alone: with `stamp_ignore` paths a docs-only child A of B keeps B's build number N, so running A against a channel that holds B at N must proceed. For an equal build number the engine therefore asks `Source` two questions, `ancestry(theirs, ours)` first and then `ancestry(ours, theirs)`: when theirs is an ancestor of ours the held build is not newer and is ignored (the run proceeds); otherwise it is newer. When `Source` says our revision is an ancestor of every newer build the run is `SUPERSEDED`; when the two are unrelated, `REFUSED` (`SUPERSEDED_BY_NEWER`); when `Source` cannot tell either question, `INDETERMINATE`, never `SUPERSEDED`. A refusal outranks a cannot-tell. This applies to `plan` too (`decide_supersede::equal_build_number_descendant_proceeds`, which pins that an equal number whose other commit is an ancestor of ours proceeds; `decide_supersede::equal_build_number_other_commit_supersedes`, which now covers only an equal number whose other commit is unrelated to ours or has ours as an ancestor; `decide_supersede::exceptional_builds_are_not_counted`, `decide_supersede::cannot_tell_is_indeterminate`, `decide_supersede::any_member_with_a_newer_build_decides_for_the_set`, `decide_supersede::yanked_builds_still_count`).

### 5.7 Stage admission (Decided here)

A stage is the unit of a driver job. **One release is one run id across all its stages (Decided here):** the driver gives every stage job of a release the id of its workflow run, including a stage that waits for a human approval inside that workflow run, and a rerun of a stage raises its attempt. Stage S is admitted, before its first effect, grant exchange or registry call, only if for every stage N in `S.needs` the run ledger holds a `stage` record for N that is confirmed (`confirmed=1`, which the engine wrote last, after every action and every validation of N, at the action level and at the stage level, was `SUCCEEDED` or `NOOP`: 3.3, 5.1) and whose `set` equals the set hash recomputed from the store now (from the set document at the record's `generation`, 4.2), and, when yank is taken (PR 9), is not marked `yanked`. The ledger is the run's, so the record carries this run id by construction. A stage that holds a Publish action additionally requires that the one needed BUILD stage's (`machine.publish_stage_needs_validated_build` allows exactly one) `SET_CLOSURE` validation record carries that same `set`. When S needs another stage N that also holds a Publish action (a chain of channels), S is admitted only if N's `stage` record carries a `set` equal to the one needed BUILD stage's: a PUBLISH stage's `stage` record carries the `set` and `generation` of the BUILD stage it needs (3.3), and `machine.publish_chain_shares_the_build` (2) already refuses a machine in which N and S need different BUILD stages, so two chained channels cannot be given the sets of two builds. Otherwise S is `REFUSED` with `STAGE_NOT_ADMITTED`, naming the first needed stage and why (missing, not confirmed, yanked, another set). A promotion approved in a separate, later workflow run has another run id and another run ledger, so it finds no record of N: it is `STAGE_NOT_ADMITTED` and the message says to run a release's stages under one run id. That shape is out of scope (section 0), not worked around. S running in another driver job needs the run ledger of 5.8 to see N's record; without it the refusal is the answer. The later channel therefore receives the bytes the earlier stage validated (same set hash, recomputed from the store), and a digest copy between channels stays out of scope. A coordinate yanked after N confirmed stops S only through the `yanked` mark that `yank --run-ledger` writes (5.5): admission reads records and does not observe N's channel. Admission reads records and the store, so a stage with `needs` takes `--run-id`, `--run-ledger` and `--store` whatever it holds, a Test-only stage after a Publish stage included (7). Tests: `stage_admission::needed_stage_not_confirmed_is_refused_with_zero_calls`, `stage_admission::a_failed_stage_level_readback_leaves_the_stage_unconfirmed_and_the_next_stage_is_refused` (a Publish stage whose actions all succeeded and whose stage-level `CHANNEL_READBACK` fails; the `stage` record has no `confirmed`; the stage that needs it makes zero registry calls and zero grant exchanges), `stage_admission::a_failed_action_level_validation_on_the_last_action_leaves_the_stage_unconfirmed`, `stage_admission::an_unrun_stage_validation_leaves_the_stage_unconfirmed`, `stage_admission::a_stage_built_by_adoption_is_admitted`, `stage_admission::a_needed_stage_in_another_runs_ledger_is_refused`, `stage_admission::set_changed_in_the_store_is_refused`, `stage_admission::a_validation_record_of_another_set_is_refused`, `stage_admission::missing_run_ledger_fails_closed`, `stage_admission::a_stage_after_an_approval_wait_in_the_same_run_is_admitted` (a `ManualClock` moved past the lease TTL and the attempt raised), `stage_admission::a_chained_publish_stage_that_took_another_set_is_refused`, `stage_admission::needed_stage_with_a_yanked_coordinate_is_refused` (PR 9, with yank).

### 5.8 Where state lives between jobs (Decided here)

Stages are separate driver jobs and the trust split (6) puts BUILD and PUBLISH in different ones, so four pieces of state must be visible to more than one job:

| State | Flag | Needs | Without it |
|---|---|---|---|
| channel ledger, one per channel | `--channel-ledger <path>` | a file every job that may publish to that channel locks: one filesystem shared by those jobs | no exclusion between pipelines: each holds a lease nobody else sees, and the registry's coordinate uniqueness and the monotonic check on stamps are the only guards; no verdict about a coordinate changes (5.1) |
| run ledger, one per run | `--run-ledger <path>` | a file the stage jobs of one run can all read and write, one at a time (see the holder rule, 3.3); it may travel between sequential jobs as an opaque file (a CI artifact), carried out by the driver after every job, including a failed or cancelled one (rule 3), and back in before the next | a stage that needs another is `STAGE_NOT_ADMITTED`; staged coordinates are found only by observation (5.2) |
| artifact store | `--store <dir>` | a directory root namespaced by stage, platform, revision and generation (4.2): the BUILD job fills it and the PUBLISH job reads it; it may move between jobs as an opaque directory (a CI artifact), because the PUBLISH job trusts nothing in it: it reads the set document at the generation its `stage` record names, runs `verify_member` on every member and recomputes the set hash (`SET_HASH` on a difference) | a PUBLISH job has no set to read (`SET_HASH`, or `STAGE_NOT_ADMITTED` without the run ledger); nothing can be adopted |
| seal ledger | `--seal-ledger <path>` | durable across runs, with the store root, for adoption (5.4); written by release BUILD jobs only | nothing is adopted: a rebuild that differs leaves a half-published coordinate `PUBLISH_DIFFERENT_BYTES`, and the report says why and what to persist |

Rules: (1) A Publish action refuses an in-memory channel ledger outside a test build (`LEDGER`, `publish::memory_channel_ledger_is_refused`): the intent that says a stage or a commit may have started must outlive the process. (2) **What the file ledger can promise.** Its exclusion is an advisory file lock plus a lease expiry in wall-clock milliseconds written by each host. It is supported on one host, or on a filesystem where that lock really excludes (a local one, not a network filesystem whose lock is advisory per client), with host clocks within `MAX_CLOCK_SKEW` (5 s) of each other. ucdk cannot detect a filesystem or a clock that breaks this, and the doc states the risk instead of pretending otherwise: on a network filesystem without working locks, or with clocks further apart, two jobs can both believe they hold a lease, and the single-publisher guarantee reduces to the registry's coordinate uniqueness (5.2). On ephemeral runners with no shared path a pipeline holds a lease nobody else sees, and the same reduction applies; the monotonic check still holds because it reads the registry, not the ledger. A networked ledger is open question 15, not a prerequisite of PRs 3 to 14. (3) A run ledger that travels as a copy is correct only for stages that never overlap: stage jobs with a `needs` edge between them are sequential by construction, and independent stages must be serialised by the driver when their ledger is a copy (with a shared file the lease serialises them, 3.3). **The driver carries the run ledger out after every job, including a failed or cancelled one** (an always-run step): a job destroyed after it wrote intent, action, validation or grant records would otherwise resume from nothing, and a staged coordinate whose intent was lost would be found only by observation. A stage that finds its own records missing from the copy it was given resumes as a first attempt: `observe` resolves every coordinate, staged ones included (5.2), and if a record it needs from an earlier stage is missing too it is the wiped-ledger case of 5.4. The crash sweep runs with a copy taken before the kill (`crash::publish_sweep_with_the_run_ledger_of_before_the_kill`). (4) A lost channel ledger changes no verdict about a coordinate (5.1). A lost run ledger refuses later stages (5.7) and leaves any staged coordinate to be found by observation and given back with `ucdk release abort` (5.2). (5) A publication record is audit data, so the channel ledger may be pruned of `Confirmed` records without changing a verdict; v1 does not prune, and each write rewrites the whole file, so a channel's write cost grows with its history, which question 16 recommends bounding with a compaction verb later.

## 6. Permissions (Proposal; the full text is [release-permissions.md](release-permissions.md))

- **No standing credentials in v1, and no stored secret.** A `PushIdentity` is `Anonymous` or `Federated`. A channel declares the identity it trusts (`subject`, `audience`, `environment`, an exceptional pair, `pinned_claims`) and the scope each phase needs (`stage_scope`, `commit_scope`). At run time the job's identity token, which the issuer accepts once, is exchanged for a short-lived grant scoped to one phase of one action and to the coordinates of that action. A grant is held in a `Grant` value that cannot be printed, cloned or logged and zeroes on drop. A long-lived token is not a variant (Q6). **Single use is the identity token's.** The grant is not itself single-use: it serves the several calls of its one phase (observe, stage or commit, a retry, an abort) and no call of another phase or action; an issuer whose grants are single-use answers a second call `GrantRefused(AlreadyUsed)`, and the engine exchanges again. A platform whose identity-token request credential has expired mid-job, or an issuer that cannot be reached, is `GrantRefused(Unreachable)` (4.1) and, outside a run, `NOT_UNDER_PLATFORM`.
- **Staging and committing are separate grants.** The stage grant covers the stage phase (and the abort of staged state); the commit grant is exchanged after the action's validations passed, with a new identity token, and covers the commit and the read-back. A grant that expired or whose identity token was already used is replaced, never retried; a grant is used only while its stated expiry is later than the ledger's clock reading plus the margin `GRANT_MARGIN` (30 s, well above `MAX_CLOCK_SKEW`, so the issuer's clock and ours may differ by that skew and a call that is in flight at the expiry still finds the grant good; the expiry is the issuer's, the reading is the one clock ucdk has, a grant already inside the margin when issued serves its whole phase with its one exchange, a margin exchange does not count against `Publish.attempts`, and a registry's `Expired` answer is the backstop: `publish::an_expired_commit_grant_is_exchanged_again_and_the_staged_state_found_by_observation`); the staged state is found by observation, never assumed; a refused exchange is `REFUSED` with `CREDENTIAL` (`PARTIAL` when anything is staged or committed) and no registry write follows it. Each exchange is recorded in the run ledger before (`Intent`) and after (`Confirmed`, with the issuer's stated expiry or the fault), and never holds a token (3.3). Where the issuer has one scope for both phases the two scope names are equal, and the separation is ucdk's own order of use and not the issuer's enforcement; the declaration says so and `ucdk release trust` prints it (question 20, risk 21).
- **One writer per repository.** `push` is required, never defaulted, and no flag overrides it. A stage's `environment` must equal the `environment` field of the repository's `Federated` identity (`exceptional_environment` for an exceptional run off the mainline), never a value parsed out of `subject`; the static rule is `machine.environment_mismatch` (2), and at run time the grant source compares the claims of the job's identity token with the declaration before any exchange, and refuses (`GrantRefused(Denied)`, `CREDENTIAL`) with the identity token unspent. ucdk may be stricter than the issuer and never looser (`credential::exceptional_run_presents_the_exceptional_environment`, `credential::a_mainline_run_presents_the_normal_environment`, `credential::a_differing_claim_is_refused_before_any_exchange`).
- **Per surface and host.** A grant is presented only on the repository and host it was issued for; a mismatch is a local fault with zero requests. A public repository is read anonymously by a read-back validation (the Smoke action), so it sees what a stranger sees; the observations that decide a publish (preflight, the stage phase, the commit phase) carry the action's grant whatever the visibility, because staged state is not readable by a stranger (5.2).
- **Nothing secret crosses the ABI, the ledger or an error.** Configuration is flags. The grant source reads its platform's standard token variables in-process, nowhere else, and a child process gets only the environment the machine names. An error is withheld when a server echoed a credential or any 16-byte run of it (`credential::an_error_echoing_a_sixteen_byte_run_of_a_token_is_withheld`). No credential value enters any hash: the machine hash covers the declared `Federated` fields and never an issued value (`grant::no_issued_value_enters_any_hash`, which varies what the fake issuer returns and shows the machine, run, build-inputs and action-input hashes unchanged).
- **Bootstrap** is the one-time step an administrator takes, with their own credentials, to create the trust on the channel with the registry's own tooling. `ucdk release trust` prints what the machine expects and `plan --check-credentials` exchanges and discards a grant for each phase and reports `MINTED`, `NOT_UNDER_PLATFORM`, `NOT_FEDERATED` or `REFUSED`; only `MINTED` is a pass.
- **Trust split (Decided here).** A `CHANGE_CHECK` stage holds Build and Test actions only, has no environment and cannot be needed by any stage, so code under review never reaches a push identity. A stage that holds a Publish action holds no Build or Test action (`machine.publish_stage_runs_code`), so a build or a test, which runs code, never runs in a process or environment that can present a push identity; the grant is exchanged after admission and never reaches a child process. A `needs` edge is a data dependency; trust is per stage. The build side is held too: a set carries the stage and environment that produced it inside its hash, adoption of a stored set needs a seal record that only a release BUILD stage writes (5.4), and a `CHANGE_CHECK` stage is refused the seal ledger, so bytes that code under review left in a shared store are never adopted as a release build. Validations take no grant except the read-back of a `PRIVATE` repository, which reads with the commit grant.

## 7. CLI verbs and exit codes (Proposal)

Configuration is flags, with no positional arguments (as `ucdk-cli/src/args.rs` already requires, Exists) and no environment variables. Paths in a machine are relative to `--root`, not the working directory.

| Verb | What it does | Writes |
|---|---|---|
| `ucdk release check --machine <f>` | validate the machine; print stages and actions in order, each with its validations; every refusal names `<source>: line N` | nothing |
| `ucdk release plan --stage S [--only ...] [--check-credentials]` (a stage with a Build or Test action takes `--release-version V`, and `--scratch D` when it holds a Test action; a stage with `needs` takes `--run-id R --run-ledger P --store D` whatever it holds, for admission and, when it holds neither a Build nor a Test action, to read the run's stamp and the sealed set it consumes: a Publish or Smoke stage, and a Test-only stage after a Publish stage, take the same flags, the latter with the stamp flags a Test action needs, checked against the run record) | what would build, test, stage and publish, each coordinate's observed state (`WOULD_BUILD`, `WOULD_TEST`, `WOULD_PUBLISH`, `ALREADY_PRESENT`), the layered command line and environment of each build and test target (`BuildSystem::command`, no effect), the credential check of 6, `new_names` (artifact names the channel has never held; a name is held if `newest(channel, name)` returns a non-empty list or `list` shows the name, because an index may lag, so a new version of a held name is not new; `observe` is a point read of one coordinate and is not used for this; only the selected stage's channels are read, no lookahead), the run hash, which is the hash `run` recomputes for the same inputs (2) | nothing |
| `ucdk release run --stage S --run-id R --attempt N --expect-hash H` (a stage with a Build or Test action also takes `--release-version V --timestamp-ms T`, and `--scratch D` when it holds a Test action; a stage with `needs` takes `--run-ledger P --store D`) | execute the selected actions and validations; create or resume the run | ledgers, store, build system, registry |
| `ucdk release trust --machine <f>` | print, per channel and repository, the trust the machine expects (subject, audience, environment, pinned claims, the scope of each phase, the artifact names), for the administrator who bootstraps it (6) | nothing |
| `ucdk release abort --stage S --run-id R --attempt N --expect-hash H` | give back the staged state of the stage's Publish actions (5.2); never touches a committed coordinate | ledgers, registry |
| `ucdk release status` (with `--run-ledger P --seal-ledger P --store D` it also lists each generation of the store that no given ledger names, and for a generation a replaced seal named, the `stage` records of the given run ledger that still do) | read the ledger and observe each recorded and declared coordinate; say whether they agree | nothing |
| `ucdk release yank --coordinate C --reason T --expect-hash H --run-id R [--run-ledger P]` (Proposal) | explicit withdrawal | ledger, registry |
| `ucdk ledger show` | the ledger document as data | nothing |

A run has no platform flag: the platform is the stage's (2). A `CHANGE_CHECK` stage takes its version like any stage with a Build or Test action: `--release-version` is required and the driver chooses it (a pull request revision needs a name for its change); it is hashed and recorded in the run record and reaches no registry, because a `CHANGE_CHECK` stage cannot publish. `--timestamp-ms` is not hashed, so `plan` does not take it.

Other flags: `--context key=value` (at most 32, untrusted), repeated `--only`, `--admission`, and the state flags of 5.8 (`--channel-ledger`, `--run-ledger`, `--seal-ledger`, `--store`).

**Selection and scope.** Selectors name what to run, never what to skip, so an action added later is not run by an old selective command. `--only action:x` runs that action and, for a Build or Smoke action, not the validations attached to it, which have their own selectors (a Test action has none). **A Publish action is the exception: `--only action:x` on one always runs its pre-commit validations between its stage phase and its commit phase, as in any run, and a Publish action whose validations cannot be evaluated is not committed** (5.2): no selector commits without the gate. `--only validation:y` runs one validation alone against what is already there; stage-level and action-level validations are named in one namespace. A selective run writes the records of what it ran and writes `confirmed=1` on the `stage` record only if, after it, every action and validation of the stage has its `Confirmed` record (3.3), so a selection can complete a stage that an earlier run left unconfirmed and can never confirm one that still has an item unrun. Any selector makes the run `SELECTIVE`, and the report cannot present a selective run as `FULL`. A selector matching nothing is refused (`SELECTOR_NO_MATCH`) and lists the stage's actions and validations. The set hash in a report is non-empty only for a run that passed everything it selected. The final stderr line states scope and verdict.

**Exit table** (one function, `exit_class(verdict, reason, landed)`, used by the CLI, the C ABI and both SDKs; today's table has the classes 0, 2, 3, 4, 6 and 8, Exists, and this adds 5 and 7; class 8, leaks, has no producer in the release machine and PR 10 removes it, 1.1). `landed` is whether the engine recorded a landed or staged coordinate in this run:

| Class | Code | Verdicts |
|---|---|---|
| done | 0 | `SUCCEEDED`, `NOOP`, `SUPERSEDED` |
| usage | 2 | malformed command line, selector or run id |
| refused | 3 | `REFUSED` with nothing landed: nothing external changed |
| failed, no effect | 4 | `FAILED` with nothing landed (a build failed): safe to repeat |
| indeterminate (new) | 5 | `INDETERMINATE` with nothing landed: cannot tell; never a pass |
| failed, changed | 6 | `PARTIAL` (including a `REFUSED` after an earlier coordinate landed), `INTERRUPTED` (including `LEASE_LOST` and `LEASE_UNCONFIRMED`), `FAILED` with a landed record, `INDETERMINATE` with a landed record, and a panic from `run`, `abort` or `yank`; run again with the same run id to resume |
| validation failed (new) | 7 | `VALIDATION_FAILED`: a test target did not pass, or a validation row failed; re-run the test with `--only action:<name>` or re-validate with `--only validation:<name>` |
| leaks | 8 | reserved: no release verdict maps to it (1.1) |

Codes 2, 3 and 4 promise that no external effect landed. An action record listing a landed or staged coordinate can never carry one of them: the class is a function of the verdict, the reason and `landed`, and the same verdict can have two classes (`FAILED` is 4 or 6). Retry advice derives from the class and a verb may make it stronger, never weaker; the class-6 advice of release verbs is "run the same stage again with the same run id" (the deploy advice, "plan again before running again", goes with the deploy verbs). Exit numbers appear in one file, held by a test. Error ids are the closed `Reason` set, carried as `UCDK-E-<NAME>`, asserted by tests and never matched by message text.

**The run verdict (Decided here).** A stage's actions, and then its stage validations, stop at the first one that is not `SUCCEEDED` or `NOOP` (5.1), so the run's verdict is the verdict of the action or validation that stopped it, or `SUCCEEDED`/`NOOP` when none did (`NOOP` only when every action was `NOOP`; a validation that is evaluated again and passes is a read and not an effect, so it does not turn a `NOOP` run into `SUCCEEDED`). `landed` is a property of the whole run, not of that action: it is true when any action of the run recorded a landed or staged coordinate. The class is then `exit_class(verdict, reason, landed)`: an earlier action that landed a coordinate and a later one that is `INDETERMINATE` is class 6, not 5, because the run changed something and "run again with the same run id" resolves both; the same holds for `REFUSED` and `FAILED`, which is why codes 2, 3 and 4 never carry a landed record. Held by `exit::no_effect_classes_never_with_a_landed_record` and `exit::indeterminate_with_a_landed_record_is_class_6`.

## 9. Design decisions and the defects they prevent (Proposal)

Each is a decision of this project, stated as behaviour with its mechanism.

- **One description of the machine.** The machine message is the only description of stages. The core reads no CI-vendor variable; a driver gets stage names, order, needs and environments as data from `check`. There is no second hand-written description to keep in agreement.
- **A build system builds and tests; ucdk does not.** A build is a build system pointed at a target and a test is a build system pointed at another; the machine defines the build system once and each artifact and test names its target, flags and environment under one layering rule (2). ucdk has no builder that is an arbitrary command, no compute model and no deadline of its own; the build system's scheduling, caching and hardware are its concern.
- **Durable progress and resume.** Run, action and validation records live in a leased, fenced ledger. A rerun skips confirmed actions with unchanged inputs and is correct without them.
- **Evidence is not authorization.** The gate between stages is a ledger fact written under the lease (a confirmed `stage` record for this run id) plus the set hash recomputed from the store (5.7); the rule is stated, not implied. The report is derived data; the exit class is what a driver branches on.
- **Every action has its validations attached.** A stage is an ordered list of actions; a build action carries the checks of the set it sealed, a publish action the checks between staging and commit, a smoke action the read-back, the stage the checks after its last action, and a test action none, because its target is the check. A validation is a built-in kind with derived rows; whatever runs code is a test target.
- **One publisher seam for every artifact type and channel kind.** The kit forces every type and kind through the same flow, so grants and flows cannot diverge by type, and the engine never branches on a channel kind (4.3).
- **Staging and committing are separate grants,** exchanged from a single-use identity token for one phase of one action, recorded without any secret; the staged state is found by observation (6, [release-permissions.md](release-permissions.md)).
- **Permanence with explicit yank.** No delete, no overwrite, burned coordinates; `stage` and `commit` are atomic create-if-absent, and a registry that cannot promise that is refused as a channel home.
- **Visibility is per repository**, not per channel.
- **Ecosystem facts live in typed metadata arms.** The core compares names and digests only and keeps no copied tables.
- **A closed `Reason` enum**, never message matching.
- **The build stamp is an input** from one `Source` implementation, not derived in several places.
- **A missing store entry is a named refusal**, not an empty directory that happens to fail later.
- **Wire goldens and the minor rule exist from the first message.**
- **Run identity is supplied by flags**, recorded, never trusted, and gates nothing.

## 10. Open questions, each with a recommendation

1. **Machine text form.** Does the CLI read only binary protobuf, or also a text form? Recommend: binary plus canonical JSON through `prost-reflect`'s serde support behind one flag; people author through SDKs. Verify the dependency passes `cargo deny` in the model PR before taking it.
2. **Ledger scope.** One per channel plus one per run, or a single ledger? Recommend three kinds (3.3): one per channel, one per run, and a seal ledger that outlives runs so a new run id can adopt a sealed set (5.4), whose lease is taken only for a write (3.3). A build never holds a channel lease and a change check never touches a channel or the seal ledger. A write that spans both (action record, then publication record) is covered by the crash sweep.
3. **Failure policy.** Stop at the first failed coordinate or attempt every independent member? Recommend stop at the first (one rule); resume on rerun. Revisit with concurrency.
4. **Group artifacts.** Is "one group artifact last" a model rule? Recommend no: a group is an artifact whose `needs` name its members. A closure rule (every requirement names another member) is the built-in `SET_CLOSURE` validation a publishing stage cannot omit (`machine.publish_stage_needs_validated_build`, 2; 4.4), not a core rule.
5. **First artifact types.** Recommend `FILE` and `OCI` first, real publishers last. The enum names the other types now so protos do not change when they arrive.
6. **Registries without a federated identity.** Recommend not supported in v1. Add a reference variant later only with an explicit repository field, refusal of anything but a name, and a warning in `plan`.
7. **Where the stamp comes from.** Recommend one `Source` implementation that runs fixed git argv commands through a `ProcessRunner` seam (never a shell, scripted in tests), refusing a shallow clone or dirty tree.
8. **Build provenance.** `ProducedBy` (run and attempt) is recorded and not hashed; the producing stage and environment are hashed (2). Recommend a signed provenance statement attached to the set later; not v1.
9. **Process runner.** Recommend argv only, no shell, an explicit environment and nothing inherited, no deadline of ucdk's own (the build system's timeouts and the driver's job limit apply); the real runner's tests spawn a small Rust helper binary built by cargo, never a shell, and the scripted runner serves the `Buck2` and `Bazel` implementations and the git `Source` of question 7.
10. **More than one platform.** Recommend one stage per platform in v1 (`machine.stage_platform`, 2), all under one run id; a group hash and an approval binding the platforms of a release come later.
11. **Order of the real channel kinds.** Recommend the `DIRECTORY` kind first (no network, a complete `Publisher` with no grants, usable to validate before publishing), then `PACKAGE_REGISTRY`, the first kind the project's own machine uses, whose publisher and grant source are tested against an in-process emulator in every pull request (PR 14), then OCI. Network clients wait for the dependency and TLS decision.
12. **Exceptional runs.** Recommend the field and the rules in 5.6 land with the model, but the verb path ships only when a real publisher exists.
13. **Ledger minor rule.** A new state name makes older readers refuse the document (3.3). Recommend accepting that, in PR 9 only, and amending the format header's rule, over raising the format major, because the golden bytes of the existing layout then keep reading.
14. **ABI numbering at the deletion.** Decided in 3.3: major 0 with a minor bump, and while the major is 0 the loader requires an exact minor match, so a stale SDK is refused by name. Raising the major to 1 at the deletion is the alternative and is not recommended, since section 5 of the architecture promises nothing before the first release.
15. **A networked ledger.** v1 arbitrates only runners that share a ledger file (5.8). Recommend a later ledger backend behind the existing `Ledger` trait (its conformance suite is the contract) when a first user needs cross-runner exclusion; it is not a prerequisite of PRs 3 to 14.
16. **Channel ledger compaction.** Recommend a later verb that prunes `Confirmed` publication records, which is safe because the registry is the authority (5.1); v1 accepts a write cost that grows with history.
17. **Promotion across workflow runs.** v1 admits a stage only through records of its own run id (5.7), so a promotion approved in a later, separate workflow run is refused by name. Recommend keeping that and, if a first user needs it, a later explicit `--admit-from <run id>` that reads the earlier run's ledger read-only and re-observes the needed coordinates, rather than loosening admission.
18. **The build system's version.** ucdk cannot observe which Buck2 or Bazel it runs, and the build-inputs hash covers the binary's name, and the `PATH` text that resolves it, and not its version or its bytes (2). Recommend an optional `BuildSystem.version` that is checked against the binary's own version output at the start of an action and refused on a difference, added once the first real implementation shows a stable query; until then the repository's own toolchain pins are the control.
19. **Where a Bazel output lives.** 4.2 intends `bazel cquery --output=files` and `bazel info execution_root` with the same arguments. Recommend confirming that against the real binary in the on-demand job before PR 12a is accepted, with the build event protocol file as the fallback source of output paths; the same job confirms the Buck2 spellings of 2, that each locating and test verb accepts the author's flags, that Buck2's `--event-log` writes JSON lines to the fixed file name `events.json-lines` and the field `ran` counts (4.2), and the two reports 4.2 reads for `ran` (Buck2's event log and Bazel's build event file with its `test.xml` files), with transcripts kept as the test data of PR 3c and 12a.
20. **Issuers with one scope for both phases.** The first package registry grants one publish scope, so the stage and commit grants are different exchanges but carry the same authority (6). Recommend asking the registry for stage-only grants; the declaration then changes its scope names and the engine does not change.
21. **Members with their own versions.** `independent_version` is gone because a manifest is composed by ucdk and no builder writes one. Recommend that, if a first user needs a member versioned apart from the release, the declaration gains a `version` (a fixed string or a placeholder), not a builder-written manifest.
22. **How a variable reaches an action.** The machine's environment is the build-system client's (2): a build system forwards what it chooses to actions, tests and a long-lived server, and ucdk can neither see nor change that. Recommend keeping it so, with the forwarding flags written in the same flag lists and hashed with them, and revisiting only if the on-demand job (question 19) shows a build system whose client environment reaches actions in a way a flag cannot express.
23. **What the first package registry must hold before the first machine publishes there.** Two prerequisites of PR 14, neither a design change: (a) the registry stores the `Held` stamp (build number, source commit, exceptional mark) beside each version, which `monotonic: true` and `observe_returns_the_stamp_it_was_given` need, and until it does the channel is `monotonic: false` as in 1.2; (b) the registry's package type is an `ArtifactType` the reader accepts: either the registry kind takes `FILE` members, or the ecosystem type lands with its platform-subdir arm (4.2) in a PR before 14. Recommend asking the registry for (a) and choosing (b) when the first real package type is named; PR 14 does not start until both have an answer.

## 12. Riskiest choices

1. Deleting `ucdk-engine` wholesale while moving its lease lifecycle into the ledger: the lease tests are the strongest proof of the fencing claims, and `guard.rs` is a rewrite over a bare ledger, not a move. 3.1 accounts for all 14 tests by name and by disposition, and the review of PR 2 checks each ported test keeps its ledger-side assertions.
2. Generalising `ucdk-ledger` off the provider types while keeping the on-disk format byte-identical: the golden file is the only guard. The same PR adds `Snapshot.fence`, `Snapshot.lease`, `Snapshot.at` and `FileLedger::open_read_only` (3.1), a public ledger API change that every release PR inherits.
3. `ucdk_ledger_show` as the one verb added in the deletion PR. If judged scope creep, the ABI suite has nothing real to call, and `SessionConfig.holder` and `test_clock_ms` would have no consumer until PR 10; 3.4 is what keeps them observable and tested.
4. The seam has no delete and no overwrite, so a registry that supports only replace or delete is refused; some real registries may need an explicit exception later.
5. Two ledger kinds with writes that span both: the crash sweep must cover the gap between a action record and a publication record, and renewal must cover both leases before each stage, commit and grant exchange (3.3).
6. No standing credentials in v1 may exclude a registry a first user needs.
7. Resume keyed by an input digest refuses a legitimately edited retry; users must choose a new run id, and the error must say so.
8. Stop at the first failed coordinate favours simplicity over throughput.
9. Derived row accounting: a validation's rows are a function of its subject, so changing how rows are derived changes what "every row passed" means; goldens pin the derived row names of each kind, and a failure names the first divergent index.
10. `Origin::Adopted` for identical bytes someone else published makes "ours" depend on bytes, not on who wrote them; yank needs the explicit flag for that reason.
11. Reading no CI variable pushes ref, run id and revision correctness to the driver; a driver that lies is detected only by the `Source` check of the revision.
12. A new ledger state name makes older readers refuse the document (question 13); an operator running an old binary against a new ledger gets a refusal, not a silent misread. The change is confined to PR 9.
13. Ephemeral runners with no shared ledger path get no cross-pipeline exclusion (5.8); the registry's uniqueness and the monotonic check on stamps are then the only guards.
14. `put` as atomic create-if-absent excludes registries that only replace; the first OCI publisher must be able to declare it (4.3).
15. Adoption of a sealed set trusts the seal ledger: whoever can write a `Confirmed` seal record can make a stored set adoptable. ucdk refuses the seal ledger to `CHANGE_CHECK` stages and hashes the producer into the set, but it cannot know which driver jobs are trusted; the driver must give `--seal-ledger` to release BUILD jobs only (5.4).
16. Leases of long builds, tests and validations are kept by explicit progress events, not by a timer. A build system invocation that is silent for longer than the TTL is recovered only by re-acquiring before the Confirmed write, and only when no grant of any holder was made since the guard's own (3.3).
17. A file ledger's exclusion is an advisory lock plus host clocks. It holds on one host or a filesystem with a working lock and clocks within the skew bound; ucdk cannot detect either failing (5.8).
18. `ucdk-ledger` has no coverage margin: after the deletion it stands at its floor, with the failing-lock closures reached by no test (3.1). Every later PR that touches the crate must land its lines with their tests.
19. Store generations that no record names (left by a run that died before sealing) are listed by `status` and never deleted by another run, and a generation that a seal named is not deleted by the engine after another seal replaces it, so a store grows until the driver prunes it (4.2); the engine never deletes a generation that a seal, a `stage` record or a Confirmed `action` record names.
20. A Test action proves what the build system saw, not what the store holds. The build system runs the test targets under the test's own flags and environment, and ucdk does not check that they build the bytes that were stored (1.1). A machine that needs both gives the test a dependency on the member targets and the same flags and environment, so the build system's cache returns identical outputs; the set hash and `verify_member` still protect the bytes.
21. The stage and commit grants of an issuer with one publish scope carry the same authority; the separation then rests on ucdk using them in order and never swapping them (6, question 20). Everything else in the permission model is enforced by the issuer or by a refusal that makes zero calls.

The command spellings of `Buck2` and `Bazel` (2, 4.2), the ucdk-owned report flags, the formats `ran` is read from, and the claim that both treat a later flag as overriding an earlier one are unconfirmed until the on-demand job against the real binaries runs; until then the argv goldens pin ucdk's own intent only (questions 18 and 19). Even confirmed, `ran` is only as strict as the report: a test that exercises nothing but is counted as one case by the build system passes.
23. A build that is not hermetic (reads the clock, the network or an undeclared input) produces a different digest on every run, so adoption of a sealed set rarely applies and a half-published set can be stuck at `PUBLISH_DIFFERENT_BYTES` (5.4). ucdk cannot see non-hermeticity; making targets hermetic is the build system's discipline and the machine author's.
24. The environment of a build-system invocation is the client's, not the action's: a variable the machine names may reach no action unless a flag forwards it, and a long-lived server may keep the environment it started with (2, question 22). A machine whose per-target environment seems to have no effect is usually missing the forwarding flag; ucdk hashes both, so the edit is seen, and cannot tell whether a byte changed.
