# ucdk release: build, test, publish

Status: design. **Exists** means the code is on `main` today. **Decided** means a project decision that this document records. **Proposal** means a decision for review with no code yet. Sections 0 and 3.1 are Decided, and where a section below states a rule as a decision (marked "Decided here") the project has taken it and the test that holds it is named, and the statements in 3.1 about today's code are Exists (each was checked against `main` when this was written). Everything else is Proposal. Section 3 says, crate by crate, what stays and what goes, so the deletion pull request that follows this one is a mechanical list.

## 0. Project decisions recorded here (Decided)

- The deployment side of ucdk is deleted and stays recoverable from git history. There are no real cloud providers for now.
- The release process is the priority. ucdk gains BUILD, TEST (validations) and PUBLISH, with artifacts, release sets, channels and validation runs.
- Fakes come first. A fake builder, a fake registry and a fake validator are the executable specification, as the fake provider was for deployment.
- The release machine is not modelled on the deploy engine to keep that engine. It reuses what fits: the ledger with lease and fence, the write-ahead intent pattern for the one step that writes somewhere ucdk does not own (PUBLISH), the Kahn ordering, the length-framed hash, the C ABI pattern, the generator and the gates. Nothing else.
- Sequence: (1) this design, (2) one deletion pull request, (3) the release pull requests (section 11).
- No earlier release PR changes a byte of the ledger format: PRs 5 to 7 write format 1.1, and the one format change (1.1 to 1.2, two new state names) lands in its own pull request, PR 8 (3.3).
- Out of scope for v1, each stated so an SDK author knows: computing the set of targets a change affects, and build units that are checked but never shipped (a `CHANGE_CHECK` stage builds every artifact it names); lookahead into the next stage's channel; copying bytes from one channel to another by digest; concurrency inside a step; callbacks into the host; a networked ledger (5.8); a release whose stages run under different run ids (5.7).

**Proposal, not yet decided: yank.** Withdrawing a published coordinate (`yank`, 5.5) is part of this design as a proposal. It is the reason for the format change of PR 8 and for nothing else. If it is not taken, PR 8 shrinks to validations, sweep and `ValidationStamp`, and the ledger stays at format 1.1 for good. Nothing in PRs 3 to 7 depends on it except the `Presence::Yanked` arm and the `PUBLISH_YANKED` reason, which are kept because a registry may report a coordinate withdrawn by someone else.

## 1. The model in one page (Proposal)

- A **release machine** is data: an ordered list of **stages**, each a list of **steps**. A step is a BUILD (turn declared artifacts into content-addressed files plus manifests) or a PUBLISH (put those files into a channel). Any step may carry **validations**: checks that must pass.
- An **artifact** is a file in a content-addressed store, described by a **manifest**: type, name, version, platform, sha256, typed metadata. The manifest is the only interface between a build and everything after it.
- A **release set** is the verified set of members one BUILD produced for one (revision, platform). Its **set hash** covers revision, platform, the producing stage and its environment, and every member, and not which run or attempt built it. BUILD and PUBLISH share one definition of the set, so they cannot disagree about it.
- A **channel** is a publish destination: per artifact type one repository (location, visibility, push identity). A published coordinate (channel, type, name, version, platform) is **permanent**. The seam has no delete and no overwrite. Withdrawal is an explicit `yank`, which keeps the bytes and marks the coordinate.
- A **validation** checks what a step made or published. It names its expected result rows up front. It passes only if at least one row is asserted and every asserted row passed. It carries a **validation run id**, stamped on everything it creates, journaled before creation and removable by that id.
- **Truth is observed.** The registry is truth for what is published. The ledger is the write-ahead record of what ucdk intended and confirmed. A publish whose answer was lost is resolved by reading the coordinate back. Registry correctness never depends on a record: with every record deleted, the same rules reach the same registry state. Run-level gates do depend on records (stage admission, pin checks, who may remove a validation leftover) and fail closed when a record they need is missing (5.1, 5.4, 5.7).
- **One core, many hosts.** Rust core, C ABI, generated Python and TypeScript SDKs, the CLI. Builders, publishers and validators are traits, each with an in-memory fake, and each with a contract kit every real implementation must pass.

## 2. The protos (`ucdk.release.v1`, Proposal)

Everything crossing the ABI is protobuf bytes. The package sits beside the existing ones. Retired numbers are `reserved`. The generator reads the proto list in `ucdk_codegen::PROTO_FILES` (Exists; today two files), so the new file is one more entry. Enum zero values are `*_UNSPECIFIED` and are refused on read. Names (stage, step, validation, channel) match `[a-z][a-z0-9-]*`, at most 63 bytes, no trailing `-`. Artifact names also allow `_`.

Three names differ from their neighbours on purpose. `ucdk.api.v1` already has a message `Outcome`, an enum `ErrorCode` and an enum `CredentialSource` (all Exists, all deploy-shaped). The release package therefore says `Verdict`, `Reason` and `PushIdentity`, so a generated SDK never has two things of one name in one namespace.

```proto
syntax = "proto3";
package ucdk.release.v1;

// ---- declaration (authored; the SDKs build these) ----
message Machine {
  int32 schema_version = 1;          // 1. A newer major is a distinct refusal.
  string name = 2;
  repeated Stage stages = 3;
  repeated ArtifactDecl artifacts = 4;   // declaration order is part of the contract
  repeated Channel channels = 5;
  repeated string stamp_ignore = 6;      // path globs whose commits never raise the build number
}
message Stage {
  string name = 1;                   // also the unit of trust and of driver job
  repeated string needs = 2;         // earlier-declared stages; a DAG ordered by Kahn; each must be confirmed for the run before this stage's first effect (5.7)
  Trigger trigger = 3;
  string environment = 4;            // the trust scope the driver gives this stage; default = name
  bool exceptional = 5;              // may run off the mainline, with a reason (5.6)
  repeated Step steps = 6;           // run in this order; stop at the first not SUCCEEDED/NOOP; a stage with a PUBLISH step has no BUILD step (2, checked)
}
enum Trigger { TRIGGER_UNSPECIFIED = 0; RELEASE = 1; CHANGE_CHECK = 2; }  // CHANGE_CHECK: BUILD only
message Step {
  string name = 1;                   // unique in the stage
  oneof action { Build build = 2; Publish publish = 3; }
  repeated Validation validations = 4;   // any step kind may carry them
}
message Build   { string platform = 1; repeated string artifacts = 2; }
message Publish { string platform = 1; repeated string artifacts = 2; string channel = 3; }
// platform: "<os>-<cpu>" or "any". Never a cloud or a registry.

message Validation {
  string name = 1;                   // unique in the stage
  string validator = 2;              // a registered validator kind ("fake", later real ones)
  Subject subject = 3;               // what it reads
  repeated ExpectedRow rows = 4;     // authored up front; the denominator
  uint32 wait_polls = 5;             // CHANNEL_READBACK: bounded polls for absence; 0 = none
  map<string, string> options = 6;   // read only by the validator kind
}
enum Subject { SUBJECT_UNSPECIFIED = 0; LOCAL_SET = 1; CHANNEL_READBACK = 2; }
message ExpectedRow { string name = 1; string asserts = 2; }   // asserts: one sentence of what it proves

message ArtifactDecl {
  string name = 1;                   // byte-equal to its manifest name
  ArtifactType type = 2;
  Command builder = 3;               // executable (bare name or absolute path) and args; argv only
  repeated string needs = 4;         // artifacts that must exist first (a group names its members)
  reserved 5;
  bool independent_version = 6;      // default false: the member's version equals BuildStamp.version
}
message Command { string executable = 1; repeated string args = 2; }   // placeholders and the empty output directory belong to the process builder (4.2)
enum ArtifactType { ARTIFACT_TYPE_UNSPECIFIED = 0; FILE = 1; OCI = 2; CONDA = 3; PYTHON = 4; NPM = 5; }

message Channel {
  string name = 1;
  repeated Repository repositories = 2;   // at most one per artifact type
  bool monotonic = 3;                // never takes a build older than one it holds (5.6)
}
message Repository {
  ArtifactType type = 1;
  string location = 2;               // compared byte for byte; no two repositories share one
  Visibility visibility = 3;         // per repository, hence per artifact type
  PushIdentity push = 4;             // required; never defaulted
}
enum Visibility { VISIBILITY_UNSPECIFIED = 0; PUBLIC = 1; PRIVATE = 2; }
message PushIdentity { oneof kind { Anonymous anonymous = 1; Federated federated = 2; } }
message Anonymous {}
message Federated {
  string subject = 1;                // the one identity the registry trusts to push
  string audience = 2;
  string exceptional_subject = 3;    // used by an exceptional run; must differ from subject
  string environment = 4;            // the environment `subject` names; a stage that publishes here has this `environment` (6)
  string exceptional_environment = 5;  // the environment `exceptional_subject` names; set exactly when exceptional_subject is
}

// ---- produced (by a build; read by publish and validate) ----
message Manifest {
  int32 schema_version = 1;
  ArtifactType type = 2;
  string name = 3;
  string version = 4;                // equals BuildStamp.version unless the declaration says independent_version
  string platform = 5;               // the release's, or "any"
  string file = 6;                   // bare name inside the store entry (a file, or an OCI layout directory)
  string sha256 = 7;                 // the identity digest, 64 lowercase hex; what it digests depends on the type (below)
  uint64 size = 8;                   // FILE: the file's length; OCI: the sum of the lengths of the blobs the manifest reaches; recomputed by verify_member
  Stamped stamp = 9;                 // which build made it; recorded so a registry can be asked and a monotonic channel decided
  oneof metadata { FileMeta file_meta = 10; OciMeta oci = 11; }  // typed per ecosystem
}
message Stamped { uint64 build_number = 1; string source_commit = 2; }   // BuildStamp without version and timestamp
message FileMeta { map<string, string> labels = 1; }
message OciMeta  { reserved 3; string os = 1; string cpu = 2; }         // the image manifest digest is the sha256 field
message Member { Manifest manifest = 1; string store_key = 2; }
message ReleaseSet {
  int32 schema_version = 1;
  string revision = 2;               // full commit id
  string platform = 3;
  repeated Member members = 4;       // sorted by name
  string set_hash = 5;               // recomputed on read; a differing value is refused
  Producer producer = 6;             // hashed: the stage and environment that built the set
  ProducedBy produced_by = 7;        // never hashed: which run and attempt
}
message Producer { string stage = 1; string environment = 2; }   // the BUILD stage's name and its `environment` (default = name)
message ProducedBy { string run_id = 1; uint32 attempt = 2; }
message BuildStamp {                 // an input to a build; never typed, never read from the environment
  string version = 1; uint64 build_number = 2; string source_commit = 3; uint64 timestamp_ms = 4;
}
// Where each BuildStamp field comes from (BUILD stage): `version` from the required flag --release-version,
// `build_number` and `source_commit` from Source::stamp (4.5), `timestamp_ms` from the required flag
// --timestamp-ms. A stage with no BUILD step reads the stamp the needed stage recorded (3.3), never a flag.
message Coordinate { string channel = 1; ArtifactType type = 2; string name = 3; string version = 4; string platform = 5; }
message Held { string digest = 1; Stamped stamp = 2; bool exceptional = 3; }   // what a registry reports for a coordinate it holds

// ---- facts supplied by the driver ----
message RunIdentity {
  string run_id = 1;                 // [a-z0-9_-]{1,63}; never minted here
  uint32 attempt = 2;                // >= 1, required, no default
  map<string, string> context = 3;   // <= 32 pairs, recorded verbatim, gates nothing
}
message SourceFacts {
  string revision = 1;
  Tri on_mainline = 2;               // UNKNOWN is never a pass
  Tri is_tip = 3;
  string reason = 4;                 // 1..200 bytes, one line, for an exceptional run
}
enum Tri { TRI_UNSPECIFIED = 0; YES = 1; NO = 2; UNKNOWN = 3; }

// ---- results ----
enum Verdict {
  VERDICT_UNSPECIFIED = 0;
  SUCCEEDED = 1; NOOP = 2; SUPERSEDED = 3;          // exit class done
  REFUSED = 4; FAILED = 5; INDETERMINATE = 6;
  PARTIAL = 7; INTERRUPTED = 8; VALIDATION_FAILED = 9;
  reserved 10;                                      // CANCELLED: nothing can produce it while callbacks are out of scope
}
enum Reason {                        // stable; message text is for humans and never parsed
  REASON_UNSPECIFIED = 0;
  MACHINE_FORMAT = 1; MACHINE_VERSION = 2; STAGE_UNKNOWN = 3; SELECTOR = 4; SELECTOR_NO_MATCH = 5;
  SET_MEMBER = 6; SET_HASH = 7; CHANNEL = 8; CREDENTIAL = 9; APPROVED_NAMES = 10;
  PUBLISH_DIFFERENT_BYTES = 11; PUBLISH_YANKED = 12; PUBLISH_READ_BACK = 13; PUBLISH_UPLOAD = 14;
  NOT_ON_MAINLINE = 15; EXCEPTIONAL_REASON = 16; SUPERSEDED_BY_NEWER = 17; INPUTS_CHANGED = 18;
  VALIDATION = 19; CANNOT_TELL = 20; LEASE_HELD = 21; LEASE_LOST = 22; LEDGER = 23; BUILD_FAILED = 24;
  ROW_ACCOUNTING = 25; PIN_MISMATCH = 26; SOURCE = 27;
  STAGE_NOT_ADMITTED = 28; RUN_HASH_MISMATCH = 29; LEASE_UNCONFIRMED = 30; MEMBER_VERSION = 31; PLATFORM_MISMATCH = 32;
}
enum RowState { ROW_UNSPECIFIED = 0; ROW_PASSED = 1; ROW_FAILED = 2; ROW_NOT_RUN = 3; ROW_NOT_REACHED = 4; ROW_UNREADABLE = 5; }
message Row { string name = 1; RowState state = 2; string detail = 3; }
message ValidationReport { string name = 1; Verdict verdict = 2; repeated Row rows = 3; repeated string leftovers = 4; string validation_run_id = 5; }
message StepReport {
  string name = 1; Verdict verdict = 2; Reason reason = 3; string message = 4;
  repeated Effect effects = 5; repeated ValidationReport validations = 6;
  repeated string new_names = 7;     // artifact names the channel has never held (7, plan)
}
message Effect { string what = 1; string subject = 2; EffectState state = 3; }
enum EffectState { EFFECT_UNSPECIFIED = 0; BUILT = 1; PUBLISHED = 2; ALREADY_PRESENT = 3; WOULD_BUILD = 4; WOULD_PUBLISH = 5; NOT_REACHED = 6; YANKED = 7; }
```

The request and response messages (`ReleaseCheckRequest`, `ReleasePlanRequest`, `ReleaseRunRequest`, `ReleaseStatusRequest`, `YankRequest`, `LeaksRequest`, their responses) are `ucdk.api.v1` messages owned by `ucdk-api`, as today; the generic `LedgerShowRequest` and `LedgerShowResponse` arrive earlier, in the deletion PR, and are specified in 3.4. A run request carries the machine, run identity, source facts, stage, selectors and the approved run hash. The report is a pure function of the ledger and the engine's step results. No decision reads a report. A machine refusal carries a stable rule id (`machine.<name>`, listed below and held by tests) next to `MACHINE_FORMAT`, so a test names the rule it holds and no one parses a message.

**Identity digest (Decided here).** `Manifest.sha256` is the identity of a member, and it is the only digest a publisher compares. For `FILE` it is the SHA-256 of the file's bytes. For `OCI` it is the image manifest digest of the layout (hex, no algorithm prefix), which is what a registry reports; `OciMeta` has no second digest and the layout directory's own bytes are not the identity. A new `ArtifactType` names its identity before it is accepted (`machine::every_artifact_type_names_its_identity`). `verify_member` recomputes the identity from the stored bytes, and for `OCI` requires `os`-`cpu` to equal the run's platform (`PLATFORM_MISMATCH`; `any` is refused for `OCI`).

The set hash is SHA-256 over a domain tag `ucdk/release-set/1` followed by a newline (the convention the plan hash uses today, Exists), the revision, the platform, the producer (stage name, then environment), and for each member sorted bytewise by name: name, version, type, platform, file, size (decimal), sha256, build number (decimal), source commit, and the metadata arm as its field number followed by each of its fields in field-number order (a map in sorted key order). Each field is framed by its 8-byte big-endian length with the `Framed` hasher that 3.1 moves into `ucdk-core`. Revision and platform are inside the hash so an approval of one commit or platform cannot be replayed on another; the typed metadata and the stamp are inside it so two sets that differ in an OCI `os`, `cpu` or a build number cannot share a hash (`set_hash::every_metadata_field_changes_the_hash` flips each field of each arm in turn). The producer is inside it so a set built by a `CHANGE_CHECK` stage, or by any other stage or environment, can never carry the hash of a set a release BUILD stage made, whatever bytes it holds (`set_hash::changes_with_the_producing_stage_and_environment`); `file` and `size` are inside it so two sets with one hash cannot publish different file names (`set_hash::file_and_size_change_the_hash`). `ProducedBy` (the run id and attempt) and the stamp's timestamp are never hashed (`set_hash::ignores_the_run_and_attempt_that_built_it`).

The **machine hash** is SHA-256 over the domain `ucdk/release-machine/1` and the `Machine` message in canonical encoding (fields in number order, map entries in sorted key order, defaults omitted; the generated types use ordered maps), held by `machine_hash::golden_text`. The **run hash** is SHA-256 over the domain `ucdk/release-run/1` and, framed: the machine hash, the stage name, the selectors sorted bytewise, the revision, the platform, the build stamp (version, build number, source commit; for a stage with no BUILD step, the one the run record holds) and, only when the stage has no BUILD step, the sealed set hash. The timestamp is not hashed: the run record pins it and adoption keeps it (5.4). It approves this machine, this stage and selection, this revision and platform, and where the stage consumes a sealed set, that set. It never covers observed registry state, the run id, the attempt or a ledger, so a resume after a partial publish presents the hash that was approved (`run::approved_hash_survives_a_kill_and_resume`). `plan` prints it; `run` and `yank` take it as `--expect-hash` (a yank's hash is over `ucdk/release-yank/1`, the machine hash, the coordinate and the reason); a different value is `REFUSED` with `RUN_HASH_MISMATCH` before any record is written.

Checked on read. Every rule below is written as the condition that is refused, each refusal is named by a rule id, and each is held by one test in PR 3:
- `machine.unknown_enum`: an unknown enum value. `machine.stage_cycle`: a stage cycle, a stage needing itself or a later stage. `machine.duplicate_name`: a stage name, a step or validation name within a stage, an artifact name or a channel name used twice. `machine.unknown_channel`: a PUBLISH step or lookup naming a channel that is not declared (the message lists the declared ones).
- `machine.change_check_publishes`: a `CHANGE_CHECK` stage that holds a PUBLISH step, has `needs`, is needed by another stage, sets `environment`, or sets `exceptional`.
- `machine.build_platform_twice`: a stage that holds two BUILD steps naming one platform. A stage seals one set per platform (5.4), so two steps of one platform would seal under one key.
- `machine.artifact_cycle`: an artifact `needs` cycle (every member is listed) or a dangling name.
- `machine.channel_shape`: a channel with no repository, two repositories of one type in a channel, a location shared by two repositories (within or across channels), a repository with no `push`.
- `machine.exceptional_subject`: `exceptional_subject` equal to `subject`, `exceptional_subject` set without `federated`, `exceptional_environment` equal to `environment`, or one of the pair set without the other.
- `machine.publish_undeclared`: a PUBLISH step naming an undeclared artifact, or a channel with no repository for that artifact's type.
- `machine.readback_on_build`: a `CHANNEL_READBACK` validation on a BUILD step. `machine.local_set_without_build`: a `LOCAL_SET` validation with no BUILD before it.
- `machine.environment_mismatch`: a stage that holds a PUBLISH step and whose `environment` is not the `environment` of every `federated` repository it publishes to (6); for an `exceptional` stage, whose `environment` is neither that nor the repository's `exceptional_environment`. `environment` is an explicit field of `Federated`, never parsed out of `subject`.
- `machine.publish_stage_has_build` (the trust split, Decided here): a stage that holds both a PUBLISH step and a BUILD step. A command that builds never runs in a process or environment that can present a push identity.
- `machine.publish_stage_needs_validated_build`: a stage that holds a PUBLISH step and does not directly need a stage that holds a BUILD step with a `LOCAL_SET` validation whose `validator` is `set-closure`. The closure is therefore a named validator kind, not any validator: a fake registered under another name does not satisfy the rule. `set-closure` is specified in 4.4; the platform and lockstep checks are not part of it but of `verify_member`, which a publishing stage runs itself (4.2).
- `machine.gating_stage_lacks_readback`: a stage that holds a PUBLISH step and is needed by another stage and carries no `CHANNEL_READBACK` validation, so the stage a later one waits for has read back what it published.
- `machine.exceptional_needs_exceptional`: an `exceptional` stage that needs a stage that is not `exceptional`, or a non-`exceptional` stage that needs an `exceptional` one.
- `machine.every_artifact_type_names_its_identity` (2).

## 3. How it maps onto ucdk's crates

### 3.1 What stays and what goes (Decided)

**Stays (the framework the release machine reuses):**
- The ledger with lease and fencing: `MemoryLedger`, `FileLedger`, `Clock`, `SystemClock`, `ManualClock`, `Token`, `Snapshot`, the compare-and-swap write, the fenced write, the file format (atomic replace, checksum, newer-major refusal).
- The C ABI pattern in `ucdk-capi`: cdylib, header, opaque handles, status codes, panic containment, versioning, buffer ownership.
- The generator `ucdk-codegen` and the Python and TypeScript SDK loaders.
- The `xtask` gates and the per-crate 99% line and branch floor.
- `ucdk-api`'s `ExitClass` enum and code table, and the pattern of one function from a result to its class (re-created over the release verdict in PR 9).

**Goes (one deletion pull request, right after this design, removes exactly this list and stays green):** the resource catalog (`Service`, `Job`) and the `ucdk.resource.v1` deploy kinds, descriptor lowering, the deploy verbs `plan`, `apply`, `destroy`, `status` and `leaks` (and the catalog-loading call that feeds them), the provider trait, the provider contract kit and the fake provider, plus their API messages, SDK templates and tests. `docs/architecture.md` is trimmed and marked historical where it describes deployment.

Per crate and module. "Moves" names the destination so the deletion cannot remove something the release side reuses.

| Crate or module | Verdict | What and why |
|---|---|---|
| `ucdk-proto` | **goes** | Holds only `resource.proto`, which also supplies `google.protobuf.Duration` to the descriptor pool: `api.proto` imports it (line 14), and `golden_coverage.rs` reads `Duration` from the pool. ### 3.3 What each existing layer gains (Proposal)

- **Ledger records (Decided here).** Release records use the record fields that exist: `path`, `kind`, `name`, `origin`, `state`, `physical`, `deps` and `outputs`. A record's path is `<tag>/k<key>` (`RecordKey::segment`, 3.1), the key hashed from the readable name, which is kept in `name` because versions contain characters a path segment does not allow; the owner is the first segment, the tag. The payload is `outputs`, a string map written by one codec in `ucdk-release` whose keys come from a closed list; `deps` is empty. Format 1.1 is not changed by PRs 5 to 7.

  | kind (`Tag`) | `name` | `physical` | `outputs` keys |
  |---|---|---|---|
  | `run` | the run id | none | `machine` (machine hash), `revision`, `platform`, `version`, `build`, `commit`, `timestamp` (the build stamp, pinned for the run, 5.4); written once by the first BUILD stage, read by the others |
  | `stage` | `<stage>` | none | `attempt` (the latest attempt of this stage), `set`, `confirmed` (`1` once every step is `Confirmed`), `yanked` (`1` once a coordinate the stage published was yanked, 5.5) |
  | `step` | `<stage>/<step>` | none | `input` (the input digest: step spec, set hash, platform, revision), `set` |
  | `publication` | the readable coordinate | none | `digest`, `build`, `commit`, `exceptional` (`1` or absent), `run`, `stage`, `attempt` (which run's leftover intent a reader is looking at); `origin` is `Adopted` when the bytes were found, not written |
  | `validation` | `<stage>/<validation>` | the validation run id | `k` (the start counter), `set` (the set the validation read) |
  | `created` | `<kind>/<id>` | the object id | `vr` (the validation run id) |
  | `seal` (in the seal ledger, below) | `<stage>/<platform>/<revision>` | none | `set` (the set hash), `inputs` (the build-inputs hash, 5.4), `environment` (the producer's), `version`, `build`, `commit`, `timestamp`, `run`, `attempt` |

  Each field is tested by `codec::every_record_kind_round_trips` and `codec::payload_keys_are_a_closed_list` (PR 3), and the new keys by `codec::publication_record_carries_run_stage_and_attempt` and `codec::stage_record_carries_attempt_and_yanked` (PR 3). The states `yanking` and `yanked` are the only format change: PR 8 writes ledger format 1.2 (a state name added), and an older reader refuses a document that holds a state it does not know (`format.rs` reports "not a state"), which is the right behaviour for a ledger a newer engine wrote. The format header's rule "a minor adds tags, never changes one" is amended in that PR to "a minor adds tags and state names; a reader refuses a state it does not know"; `leased.ucdk` and `records.ucdk` (3.1) stay as goldens that must still read.
- **Ledgers, lease, fence and holder (Decided here).** Three kinds of ledger document: one **per channel** (publication records), one **per run** (run, stage, step, validation and created records) and one **seal ledger** (seal records, 5.4; durable across runs, written only by BUILD stages of a `RELEASE` trigger). A `CHANGE_CHECK` stage takes no channel lease, and is refused a seal ledger (`LEDGER`, `run::change_check_is_refused_a_seal_ledger`). The **holder** of every lease a process takes is `run:<run id>/<stage>`, the same for every attempt of that stage (an explicit `SessionConfig.holder` overrides it and is the operator's choice). Stages of one run therefore exclude each other on the run ledger by lease, and never fence each other: `Doc::acquire` grants at once only to the holder already named in the lease, so a rerun of the same run id and stage retakes its leases immediately after a kill, while a sibling stage of the same run, or another run id, is refused (`LEASE_HELD`) until the lease is given back or lapses plus `MAX_CLOCK_SKEW`. Whether sibling stages may run at the same time is answered by that rule: they may be started, one of them runs and the other is refused with the advice to run it again when the first ends; stages ordered by `needs` never meet this. The release TTL is the existing 600 s. A `LEASE_HELD` refusal says so and gives the advice: "rerun the same stage of the same run id, or wait for the lease to lapse (at most the TTL plus the skew bound)"; it is class 3 and promises nothing changed. `yank` takes the holder `yank:<run id>` (the `--run-id` flag it requires) and only the channel lease; a yank right after a killed publish waits out that publish's lease, and says so. `leaks` and `ledger show` take no lease and write nothing. Held by `lease::sibling_stages_do_not_fence_each_other`, `lease::a_sibling_stage_is_refused_while_the_other_holds_the_run_lease`, `lease::the_same_stage_and_run_id_retakes_both_leases_at_once`, `lease::yank_waits_for_a_killed_publishers_lease_and_says_so`.
- **Renewal, builds and validations (Decided here).** A release step is a whole build, publish or validation, not one node, so the guard renews at every effect and the long steps are kept alive by explicit progress events, never by a timer.
  1. *Before an effect:* the guard renews every held lease (run and channel) immediately before each intent write and before each `put`, once per coordinate and once per artifact build, and the engine stops before the `put` on `Fenced` or `LeaseLapsed` from either ledger. Held by `publish::run_lease_lost_means_zero_puts`, `publish::channel_lease_lost_means_zero_puts` and `lease::renews_both_leases_before_each_put` (11).
  2. *During a build or validation:* `BuildRequest` and `ValidationRequest` carry `&dyn Heartbeat` (`fn beat(&self) -> Result<(), Stop>`, in `ucdk-release-seams`). A builder or validator calls `beat()` on each progress event it can observe: the process builder on every chunk of the child's output and every exit poll, a validator between rows and between its own remote calls. The engine's `beat()` calls `renew_if_due()` on each held lease, which renews when less than half the TTL remains by the ledger's own clock (`Snapshot.at`), so a busy builder renews about every half TTL of ledger time and a chatty one does not hammer the ledger. `Stop` (a lease fenced or lapsed) makes the builder stop what it started (the process builder kills its child) and answer `Refused(LEASE_LOST)`; the engine then records nothing further and reports `INTERRUPTED` with `LEASE_LOST`. The seam has no timer and the engine has no thread: with no events there is no renewal, by design, and (3) covers that case. Held by `lease::a_build_longer_than_the_ttl_that_reports_progress_keeps_both_leases` (a `ManualClock` moved by the fake builder between beats), `lease::a_beat_after_a_takeover_stops_the_builder_and_records_nothing`, `lease::a_beat_renews_only_when_less_than_half_the_ttl_remains`, and the builder-kit scenario `builder_beats_on_progress_and_stops_when_told` (4.6).
  3. *Before a Confirmed write after an effect* (a build or validation result, a publication confirmed after its read-back poll): the guard renews, and when the lease has lapsed and the document is still at the token the guard last wrote, `reacquire_if_unchanged(token)` takes it again under a new fence and the write goes ahead. A lapse with another writer in between changes the token, so the write is refused (`Lost`, `INTERRUPTED`, `LEASE_LOST`). This is the recovery for a silent build or validation longer than the TTL: its result can be recorded, so a rerun adopts it (5.4) instead of rebuilding for ever. It is never used before an intent or a `put`: nothing starts under a re-acquired lease. Held by `lease::a_silent_build_longer_than_the_ttl_is_confirmed_by_reacquiring`, `lease::a_silent_build_whose_lease_was_taken_over_is_not_confirmed`, `lease::a_publication_confirmed_after_a_slow_read_back_poll_is_recorded`, and the end-to-end scenario `long_build_under_a_manual_clock` (8).
  4. *A `put` may outlive its lease.* The lease protects the ledger, not the registry (5.3): `put` has no deadline parameter and the engine cannot interrupt a seam call, so a hung registry call can land after the lease lapsed, and the next holder resolves it by `observe` (5.2). The claim that a put "cannot outlive the lease" is not made. Held by `publish::a_put_that_outlives_its_lease_is_resolved_by_the_next_holder`.
- **Engine.** A new engine on the same seam pattern (plain `Request` and `Outcome` enums, as `ucdk-engine/src/seam.rs` has today). It is not a reconciler: there is no desired-versus-observed graph, only an ordered machine and a record of where the run is. A step is `next = decide(machine, snapshot)` (pure) followed by executing `next` and writing the result. Only PUBLISH behaves like the old engine (5.2). The engine takes a `Pause` as a parameter, and `LeaseGuard` takes no clock (it reads time only through the ledger, `Snapshot.at`, 3.1); neither reads any other time: `SystemTime::now` and `Instant::now` appear in one production constructor, `SystemClock`, and an `xtask lint` rule refuses them anywhere else in non-test code (`lint::wall_clock_is_read_only_in_system_clock`, PR 4).
- **`ucdk-api`: which taxonomy carries what (Decided here).** An `Error` with an `ErrorCode` answers a call that made no verdict: a malformed request, a session or ledger that could not be opened (`LEDGER`, `LEDGER_BUSY`), a busy session. A `Reason` lives inside a verdict, after the engine started: a ledger failure during a run is `Reason.LEDGER`, a held lease `Reason.LEASE_HELD`. One function, `exit_class(verdict, reason, landed)`, maps to the class, where `landed` says whether the engine recorded a landed coordinate or an announced created object. Every verdict is named, so a new variant does not compile until it has a class. `Outcome` keeps wrapping a verb's answer next to its `ExitClass`; a call that made no verdict is its `invalid` arm (usage) or its `error` arm (a ledger that could not be opened or read), as 3.4 states.
- **C ABI.** Release verbs with the existing signature: `ucdk_release_check`, `_plan`, `_run`, `_status`, `_yank`, `_leaks`, plus the kept `ucdk_ledger_show`. **Version rule (Decided here):** the deletion PR removes six exported functions, and under the loader rule "same major, library minor at least the SDK's" a stale SDK would pass the check and fail at symbol lookup. While the major is 0 the loader therefore requires an exact minor match, the deletion PR bumps the minor (`UCDK_ABI_MINOR` 2 to 3, `SDK_ABI` to `(0, 3)`), the header and `architecture.md` section 5 record the rule, the loaders' `accepts()` and the three tests that assert the old rule change (3.1, SDK row), and both SDKs gain a test (`loader::a_stale_sdk_is_refused_by_name` in `test_library.py` and `library.test.ts`, naming both versions). `SessionConfig` loses `provider`, `provider_options`, `cell`, `credentials` and `profile` (numbers reserved) and gains `builder`, `publisher`, `validator` (names selected from a registry, `fake` first), `channel_ledgers`, `run_ledger`, `seal_ledger` and `store`. It keeps `holder` and the feature-gated `test_clock_ms`. Credentials never cross as bytes. Callbacks into the host are out of scope for v1. **A long effectful verb:** a session runs one call at a time, so `status`, `yank` and `leaks` on a session whose `run` is in progress answer `BUSY` (documented in the header and held by `abi::busy_during_a_run`). A panic inside `run` or `yank` (the verbs that write outside the ledger: `leaks`, `check`, `plan`, `status` and `ledger show` write nothing) is contained as before, answers `PANIC` and poisons the session, and the SDK and CLI report it as exit class 6 (effect possible), never one of the no-effect classes; a panic in a read-only verb is class 4. The CLI catches unwinding in `main_entry` and maps it the same way, so the process never exits with 101 (`cli::a_panic_maps_into_the_exit_table`, `abi::release_run_panic_is_class_6`). A poisoned session never released its leases; the next run of the same run id and stage retakes them at once, others wait for the TTL.

- **Codegen and SDKs.** The same generator over `ucdk.api.v1` and `ucdk.release.v1`. Release declarations are plain generated messages. Typed templates for `ArtifactDecl`, `Repository` and `Validation` options are rebuilt from descriptors in `ucdk-codegen` in PR 9, the PR that regenerates the trees, so the generated output changes in one PR and `sdk-fresh` stays green; they carry no per-kind code, and PR 10 holds only hand-written SDK code.

## 4. Interfaces: builder, publisher, validator (Proposal)

All seams are synchronous, take `&mut self` and are `Send`. A session runs one call at a time. Every fallible method returns a classified error, never a bare bool or exception.

### 4.1 Error classification

```rust
pub enum SeamError {
    Refused(Reason),        // nothing happened; do not retry as is
    Permanent(String),      // will fail again; nothing happened
    Transient(String),      // failed, and may have landed: observe, then retry only if absent (5.2)
    RateLimited(Backoff),   // refused before it ran; retry after the stated number of Pause ticks
    InFlight(String),       // something may be underway; observe
    Unknown(String),        // the answer was lost; the effect may have landed; observe
}
```

`Refused`, `Permanent` and `RateLimited` promise that no external effect landed. `Transient`, `InFlight` and `Unknown` do not: a registry may commit and then fail the response (a 5xx after the commit), and a seam that cannot tell must not call that `Permanent`, so `Transient` is "retry is allowed, after looking", not "nothing happened". The engine resolves all three by observing, never by assuming (`publish::transient_is_observed_before_retry`, kit scenario `transient_after_commit_is_observed_before_retry` against the fault `fail_after_commit(n)`).

### 4.2 Artifact store and builder

The store is a keyed tree, because a member is a file or an OCI layout directory and `verify_member` must see exactly what is in an entry:

```rust
pub struct StoreKey(String);                     // one per member: "m/<member name>"
pub trait EntryWriter {                          // scoped to one key; a builder gets only its own
    fn put_file(&mut self, rel: &str, bytes: &[u8]) -> Result<(), SeamError>;   // rel: relative, no "..", no empty part, never absolute
}
pub trait ArtifactStore: Send {
    fn begin(&mut self, key: &StoreKey) -> Result<Box<dyn EntryWriter + '_>, SeamError>;  // an empty entry; refused when it exists
    fn files(&mut self, key: &StoreKey) -> Result<Vec<String>, SeamError>;      // every relative path of the entry, sorted; empty when there is no entry
    fn get(&mut self, key: &StoreKey, rel: &str) -> Result<Option<Vec<u8>>, SeamError>;
    fn discard(&mut self, key: &StoreKey) -> Result<(), SeamError>;             // the whole entry
    fn keys(&mut self) -> Result<Vec<StoreKey>, SeamError>;                      // for the "nothing else is in the store" check
}
pub struct BuildRequest<'a> {
    pub decl: &'a ArtifactDecl,
    pub platform: &'a str,
    pub stamp: &'a BuildStamp,      // an input; the builder never reads git or the environment
    pub inputs: &'a [Member],       // verified members this one needs
    pub heartbeat: &'a dyn Heartbeat,   // call on each progress event; Err(Stop) means stop (3.3)
}
pub trait Builder: Send {
    fn kind(&self) -> &str;
    fn plan(&self, req: &BuildRequest<'_>) -> Result<Vec<String>, SeamError>;   // no effect
    fn build(&mut self, req: &BuildRequest<'_>, out: &mut dyn EntryWriter) -> Result<Manifest, SeamError>;
}
```

A builder writes files into its own entry through the `EntryWriter` it is handed and returns a manifest naming them; it cannot address another member's entry, and the store refuses a path that escapes its entry (`..`, an absolute path, a symlink the filesystem store meets). Run identity is not in `BuildRequest`: nothing run-specific reaches a member's bytes, so an identical rebuild has an identical set hash.

The engine, not the builder, verifies each member. One `verify_member` function checks that the manifest name equals the declaration byte for byte; that the entry is exactly what the manifest says (for `FILE` the entry holds one file, named `Manifest.file`; for `OCI` every path of the entry lies under the directory `Manifest.file` and the tree is a layout: `oci-layout`, `index.json`, `blobs/sha256/<hex>`, each blob hashing to its name); the identity digest recomputed from those files (2) equals `sha256`; `size` equals the recomputed size (2); the file is non-empty; the platform is the run's or `any` (and for `OCI` equals the layout's `os`-`cpu`, `PLATFORM_MISMATCH`); the version equals `BuildStamp.version` unless the declaration sets `independent_version` (`MEMBER_VERSION`); the recorded `stamp` equals the build's; and no other path exists in the entry and no other key in the store belongs to this set. It runs after each build, again before sealing (the second pass is the one hashed, so a later build that changed an earlier member is caught), and again by PUBLISH before it sends anything. Versions are in lockstep by default: a set whose members disagree with the release version is refused, never published. The release version is the required `--release-version` of a BUILD stage, recorded in the run record, so the reference value of the check has one source (2).

Artifacts build in Kahn order over `needs`, ties by name. A failing build leaves no manifest. A build that cannot be started is `INDETERMINATE`; one that exits nonzero, is signalled or times out is `FAILED` and names the artifact and the tail of its output. A shared stage budget hands each build the whole seconds left on an injected monotonic clock; under one second left, the build is not started and is reported not built.

The process builder (PR 11) owns the builder contract that is not in `verify_member`: it substitutes the placeholders `{out_dir}`, `{platform}`, `{revision}`, `{source_commit}`, `{build_number}` and `{timestamp_ms}` in `args` (there is no `{release_dir}` placeholder: nothing a build needs lies outside its own output directory), hands each build an empty output directory, treats a nonzero exit as a refusal, and calls `beat()` on every chunk of the child's output; each is a kit scenario it must pass. `{timestamp_ms}` is the stamp's `timestamp_ms`: a required flag for a BUILD stage, pinned in the run record, so a resume rebuilds with the same value, and kept by adoption (5.4), so a rebuilt member cannot differ because the time did. A `CONDA` or `PYTHON` coordinate needs a finer platform than `<os>-<cpu>` (a conda subdir), which neither `Coordinate` nor the metadata arms carry today; those types are not accepted by the machine reader until their arm adds the field and `Coordinate` carries it.

### 4.3 Publisher (a registry)

```rust
pub enum Presence { Absent, Present(Held), Yanked(Held) }   // Held: identity digest, stamp, exceptional mark (2)
pub enum PutAnswer { Created, Duplicate }
pub trait Publisher: Send {
    fn types(&self) -> &[ArtifactType];
    fn conditional_put(&self) -> bool;     // true only if put is an atomic create-if-absent
    fn observe(&mut self, c: &Presented, k: &Coordinate) -> Result<Presence, SeamError>;
    fn put(&mut self, c: &Presented, k: &Coordinate, file: &Blob<'_>, held: &Held) -> Result<PutAnswer, SeamError>;
    fn yank(&mut self, c: &Presented, k: &Coordinate, reason: &str) -> Result<(), SeamError>;
    fn fetch(&mut self, c: &Presented, k: &Coordinate) -> Result<Option<Vec<u8>>, SeamError>;
    fn newest(&mut self, c: &Presented, ch: &str, name: &str) -> Result<Vec<(Coordinate, Held)>, SeamError>;
    fn list(&mut self, c: &Presented, scope: &ListScope) -> Result<Vec<Listed>, SeamError>;   // may lag
}
```

There is **no delete and no force parameter**: the signature cannot express an overwrite, and **the contract does not allow one either (Decided here)**. `put` is an atomic create-if-absent: between `observe` returning `Absent` and `put`, another writer may create the coordinate, and `put` must then answer `Duplicate` and leave the existing bytes. An implementation that cannot promise that (a plain tag push that replaces an existing tag) answers `conditional_put() == false` and is refused as a channel home, like `no_digest_exposed`. For `OCI` this means digest-addressed coordinates or a registry with tag immutability, which the first OCI publisher must declare; the kit scenario `put_over_present_different_leaves_old_bytes` runs against every implementation that declares itself conditional. `put` carries the `Held` it is writing so a registry can store the stamp and the exceptional mark beside the bytes, which `newest` and `observe` return; a registry that cannot store them is refused as the home of a `monotonic` channel (kit scenario `observe_returns_the_stamp_it_was_given`). `observe` is a point read decided by fetching and hashing, and is authoritative. `list` may lag and is used only for reports (new names, with `newest`, 7), never to decide an effect. A registry that exposes no digest in `observe` is refused as a channel home for that type: comparing identity field by field with no common field is a refusal, never equality. `Duplicate` is never an error to retry; the caller observes to tell "same bytes" from "someone else's", and `Duplicate` over other bytes is a refusal that leaves no intent behind (5.2 step 4). A transport failure on a mutating request is `Unknown`, because the caller cannot tell whether the bytes left.

### 4.4 Validator

```rust
pub struct ValidationRequest<'a> {
    pub decl: &'a Validation,
    pub validation_run_id: &'a str,          // stamp everything you create with it
    pub source: &'a mut dyn ArtifactSource,  // LOCAL_SET (store) or CHANNEL_READBACK (publisher; anonymous when public)
    pub members: &'a [Member],
    pub journal: &'a dyn CreatedJournal,
    pub heartbeat: &'a dyn Heartbeat,        // call between rows and between remote calls; Err(Stop) means stop (3.3)
}
pub trait CreatedJournal { fn will_create(&self, kind: &str, id: &str) -> Result<(), SeamError>; }
pub trait Validator: Send {
    fn kind(&self) -> &str;
    fn creates(&self) -> bool;         // true if run() can create objects outside ucdk (needs a durable run ledger, 5.8)
    fn run(&mut self, req: &mut ValidationRequest<'_>) -> Result<Vec<Row>, SeamError>;
    fn sweep(&mut self, validation_run_id: &str) -> Result<Vec<Leftover>, SeamError>;
    fn remove(&mut self, l: &Leftover) -> Result<(), SeamError>;   // only what the ledger names
}
```

A validator returns rows; the engine turns rows into a verdict with the pure `account_rows`. Emitted row names are compared with `decl.rows` index by index, because a count check alone passes a truncated run. A missing row, a swapped pair, a duplicate, an empty authored list and a blank `asserts` are each a fault naming the first divergent index. The verdict is `SUCCEEDED` only with at least one asserted row and every asserted row `ROW_PASSED`. `ROW_NOT_REACHED` and `ROW_UNREADABLE` are never a pass. `INDETERMINATE` means the validator could not read its subject. A spec fault is exit class 3, a failed row is class 7. Timeouts and skipped-by-request are step-level facts, not row states. A validator takes no secret.

**The `set-closure` validator (Decided here).** The machine rule `machine.publish_stage_needs_validated_build` (2) names this validator kind, so a validator of any other name does not stand in for it. It reads a `LOCAL_SET` and has one authored row per member, `<member>: every requirement names a member of the set`. A member's requirements are the comma-separated names in its `FileMeta` label `requires` (an `OCI` member has none and its row passes with the single fact that it declares none). A requirement that names no member of the set is a failed row naming it. The system-library and glibc checks of an operating-system closure are not in v1: the kinds that carry them (`CONDA`, `PYTHON`) are not accepted yet (4.2), and a later validator kind adds them. The real `set-closure` validator is PR 12's first validator; the fake registers a `FakeValidator` under the same kind name in tests, which is how the machine rule is exercised before it exists.

## 5. State, idempotency, crash and ambiguity (Proposal)

### 5.1 Principles

1. Observe before every effect. The ledger records intent before every effect. Nothing is trusted from an earlier read.
2. A coordinate is unique and permanent. Content identity is the digest, compared on exposed fields only.
3. Every local check happens before the first registry call or credential presentation. A refusal makes zero calls.
4. An ambiguity is never a pass and never a plain failure. It is `INDETERMINATE` or `PARTIAL` and says what to look at.
5. The registry's state never depends on a record, and a record is never the authority on what is published: deleting every record changes no verdict about a coordinate (`publish::wiped_channel_ledger_changes_no_verdict`). The run-level gates do depend on records: stage admission (5.7), the pin checks of 5.4 and the authority to remove a validation leftover (5.5). They fail closed where a record is what they check: a missing `stage` record for a needed stage is `STAGE_NOT_ADMITTED`, a `run` record that differs from the presented machine, revision, platform or stamp is `PIN_MISMATCH`, and either is a refusal, never a pass. The one place a missing record is not a refusal is a stage with no `needs` and no earlier `run` record (a fresh run, or a run whose ledger was wiped): there is nothing to compare, it starts a fresh run, and a changed machine cannot be detected (5.4). The crash sweep also runs with the run ledger wiped between runs (8).
6. Steps run in order and the run stops at the first step or validation that is not `SUCCEEDED` or `NOOP`. Later items are recorded `NOT_REACHED`, which never reads as a pass.

### 5.2 Publish of one coordinate (write-ahead)

Preflight, once per step and before any put or credential presentation: stage admission (5.7); the run hash against `--expect-hash` (`RUN_HASH_MISMATCH`); every coordinate to be written is in the declared set (`APPROVED_NAMES`: the engine refuses a name the machine does not declare, as the last gate against an undeclared upload); `verify_member` on every member; recompute the set hash and require it equal the sealed one and the `set` of the validation record admission read; `observe` every member. Any member `Present` with another digest stops the step `REFUSED` (`PUBLISH_DIFFERENT_BYTES`, every such member listed, nothing sent). Every member present with our digest makes the step `NOOP`. Any failed observe makes it `INDETERMINATE`. A publisher that is not `conditional_put`, or that cannot return a stamp for a `monotonic` channel, is refused here (`CHANNEL`).

Then per coordinate, in Kahn order of the declared `needs`:

1. Resolve the credential once. A source that cannot serve this repository is a local fault before any request.
2. `observe`:
   - `Present` with our digest: write a `publication` record `Confirmed`, with `Origin::Adopted` when no intent of ours exists (someone published identical bytes), otherwise confirm the intent. Effect `ALREADY_PRESENT`.
   - `Present` with another digest: `REFUSED` `PUBLISH_DIFFERENT_BYTES`, never retried, never forced. `PARTIAL` if an earlier coordinate of this step landed.
   - `Yanked`: `REFUSED` `PUBLISH_YANKED`. A yanked coordinate is burned whatever its bytes.
   - observe fails: `INDETERMINATE`, nothing written.
   - `Absent`: continue.
3. Renew both held leases (3.3), then write the intent (`State::Intent`, digest, readable coordinate) under the fence. A `Fenced` or `LeaseLapsed` answer from either ledger stops the run before the `put`.
4. Renew both leases again, then `put` (the seam is atomic create-if-absent, 4.3):
   - `Created`, `Unknown` or `InFlight`: go to 5.
   - `Duplicate`: `observe`. Our digest is a converged earlier attempt: go to 5. Another digest means no put of ours landed: the step is `REFUSED` (`PUBLISH_DIFFERENT_BYTES`, `PARTIAL` if an earlier coordinate of this step landed), the intent is removed under the fence after that `observe`, and `landed` stays false for this coordinate (`publish::duplicate_over_other_bytes_is_refused_and_leaves_no_intent`).
   - `Transient`: `observe` first, and retry within the declared attempt bound only if the coordinate is still `Absent` (a registry may have committed before it failed; `publish::transient_is_observed_before_retry`). A different digest or a failed observe ends the step as in 2.
   - `RateLimited`: wait the stated `Pause` ticks, then `observe` and retry within the same bound.
   - `Refused` or `Permanent` (including authentication): the coordinate is `FAILED`, no effect landed. The intent is removed only after an `observe` shows `Absent`. The step stops at this coordinate and later ones are `NOT_REACHED` (open question 3 recommends this policy).
5. Read back: `observe`, polled up to a counted bound.
   - Our digest: record `Confirmed` (the guard renews first, or re-acquires when the lease lapsed during the poll and nothing was written meanwhile, 3.3 item 3); effect `PUBLISHED`.
   - Another digest: `PARTIAL`, `PUBLISH_READ_BACK`, needs a human, intent left, dependents not attempted.
   - Still `Absent`: `INDETERMINATE` (the registry may lag); intent left.

A dependent artifact (a group or index naming its members) is attempted only after a barrier: every one of its dependencies is `Confirmed` and has been read back, all members first and the dependent after the last read-back (`publish::dependent_waits_for_every_member_read_back`). A leftover intent whose coordinate is `Absent` on the next run is written again and re-put. Uniqueness of the coordinate at the registry makes that safe, so no stamp is needed to find "our" object. A step is done only when every coordinate is `Confirmed`. The step stops at the first failed coordinate (question 3); there is no concurrency flag and no concurrency invariant to test.

### 5.3 The ambiguity table

| What happened | Local state | The next run | Verdict, exit |
|---|---|---|---|
| put answer lost, registry committed | intent | observe: same digest, confirm | `INDETERMINATE` 5, then `NOOP` |
| put answer lost, registry did not commit | intent | observe: absent, put again | `INDETERMINATE` 5, then `SUCCEEDED` |
| coordinate present with other bytes | none | refused again, always | `REFUSED` 3 (reported `PARTIAL` 6 if earlier ones landed) |
| read-back shows other bytes after our put | intent | same | `PARTIAL` 6 |
| registry index lags | intent | observe settles | `INDETERMINATE` 5 |
| process killed mid-step | run and step `Intent`, maybe a publication intent | lease lapses (plus skew); observe resolves | reads as `INTERRUPTED` 6 |
| lease lost to a newer holder mid-run (either ledger) | fenced out | the stalled run stops before its next put and at its next ledger write; yanks and deletes nothing | `INTERRUPTED` 6 (`LEASE_LOST`) |
| a lease or its release could not be confirmed | unknown | the same run id and stage retakes it; others wait for the TTL | `INTERRUPTED` 6 (`LEASE_UNCONFIRMED`) |
| a build or validation outlives its lease with no progress event | lease lapsed, document unchanged | the result is recorded by re-acquiring (3.3 item 3); if another writer wrote meanwhile, it is not recorded | `SUCCEEDED`, or `INTERRUPTED` 6 (`LEASE_LOST`) |
| a stale run (a newer tip exists) | none | stops before any effect | `SUPERSEDED` 0 |
| source facts unknown, history unreadable | none | refused, never guessed | `INDETERMINATE` 5 |

Fencing protects the ledger, not the registry: a `put` already in flight is not recalled. The intent record and the coordinate's uniqueness make that put resolvable by the next holder. A run that has lost either lease starts no further put (3.3).

### 5.4 An interrupted run, and resume

A run is identified by the driver's run id and a required attempt (positive, no default, never minted here). The engine writes, before the first effect of a stage, the `run` record when the stage holds a BUILD step and none exists (a `run` record is written once per run and read by every other stage), a `stage` record `Intent` (reads as RUNNING) carrying the attempt, and a `step` record before each step. If it cannot write the first of them, the stage is `FAILED` with nothing done. A rerun uses a higher attempt and the same run id and stage, retakes the leases of that stage and channel at once (the holder is `run:<run id>/<stage>`, 3.3), and resumes the stage it is given. One release is one run id across all its stages (5.7), so the rerun of any stage finds the records of the stages before it:

1. A live lease held by another holder is `REFUSED` (`LEASE_HELD`), nothing changes, and the advice is that of 3.3. An expired lease is taken over after the skew bound (`MAX_CLOCK_SKEW` in `ucdk-ledger`, Exists), and the old holder's next write is refused as fenced.
2. The `run` record pins the machine hash, revision, platform and the stamp (`version`, `build`, `commit`, `timestamp`); a stage's `stage` record pins its sealed set hash. A different machine, revision, platform, release version or timestamp on resume is `REFUSED` (`PIN_MISMATCH`). Sealed members are re-hashed against the set; a difference is `REFUSED`.
3. Each non-final record is resolved:

| Record found | Meaning | Resume does |
|---|---|---|
| build `Intent`, no sealed set | a build was cut short | discards that member's store entry from the run and rebuilds |
| all builds confirmed, no sealed set | killed before sealing | re-verifies every member, seals |
| publication `Intent` | answer unknown | `observe` first, never `put` first (5.2) |
| validation `Intent` | cut short | sweeps its validation run id, then starts again with `k+1` (5.5) |
| `created` `Intent` | a resource may exist | sweeps it with the validation; never assumes absence |
| step `Confirmed`, same input digest (step spec, set hash, platform, revision) | finished | skipped and reported `NOOP`; a published coordinate is still observed once, so a channel changed meanwhile is seen |
| step `Confirmed`, different input digest | the run id is for one set of inputs | `REFUSED` `INPUTS_CHANGED`; use a new run id (a new run id adopts the sealed set, below) |

4. `status` reports a RUNNING record with no live lease as `INTERRUPTED` (exit 6) with the advice "run again to resume". The record is never rewritten to hide it.

**A new run id after a partial publish: adoption of a sealed set (Decided here).** Half-published coordinates are only recoverable if the next run uses the same bytes, and a builder that is not bit-reproducible would otherwise produce another digest and be refused `PUBLISH_DIFFERENT_BYTES` for ever, with no delete to clear it. A BUILD stage therefore records a **seal**: a `seal` record in the seal ledger (3.3), written under that ledger's lease, with `Confirmed` state, only after the set was verified twice and the stage's builds all `Confirmed`. Its name is `<stage>/<platform>/<revision>` and it carries the set hash, the **build-inputs hash** and the producer's environment. The build-inputs hash is SHA-256 over the domain `ucdk/release-build-inputs/1` and, framed: the platform, the revision, the build stamp without its timestamp, and for the step's artifacts and everything they `need` (in Kahn order) each declaration (name, type, builder, args, needs, `independent_version`). Editing an unrelated stage, a channel or a validation does not change it, so a machine edit made to fix the cause of a partial publish does not defeat adoption; editing a builder command or an artifact does. A machine hash is not part of the key.

Before it builds, a BUILD step reads the seal record of its (stage, platform, revision) from `--seal-ledger` and adopts the stored set, reporting `NOOP` instead of rebuilding, only when **all** of these hold, each held by the test named:
1. the record exists and is `Confirmed`, and was written under the lease (a record that is not `Confirmed`, or an entry in the store with no record, is never adopted: `resume::a_store_entry_without_a_seal_record_is_not_adopted`);
2. its build-inputs hash equals the one computed now (`resume::a_changed_builder_command_is_not_adopted`, `resume::an_unrelated_machine_edit_still_adopts`);
3. the stored set passes `verify_member` and its recomputed set hash equals the record's `set` (`resume::a_set_that_differs_from_its_seal_is_not_adopted`);
4. the set's `producer` equals this stage and environment, which the set hash covers, so a set made by any other stage or by a `CHANGE_CHECK` stage cannot be taken for it (`resume::a_set_from_another_producer_is_not_adopted`);
5. the set's member names equal the step's declared artifact names exactly, so a selective or partial earlier set is not taken for the whole (`resume::a_partial_set_is_not_adopted`).
The adopted set keeps its recorded timestamp and stamp, and the run record takes them. A stage seals one set per platform (`machine.build_platform_twice`, 2), so one key never has two builders. A `CHANGE_CHECK` stage neither reads nor writes the seal ledger; whoever may write the seal ledger is the trust anchor of adoption, and the driver gives `--seal-ledger` to release BUILD jobs only (ucdk refuses it for a `CHANGE_CHECK` stage but cannot know which jobs the driver trusts). `status` shows the sealed set hash. Held by `resume::new_run_id_adopts_the_sealed_set` and the end-to-end scenario `resume_with_new_run_id_after_partial_publish` (8).

**What adoption needs to persist.** Adoption needs the seal ledger and the store to outlive the run that wrote them (5.8). On an ephemeral runner with neither persisted by the driver (a cache keyed by revision and platform is enough), there is nothing to adopt: the BUILD step builds again, and a builder that is not byte-identical produces another digest. A coordinate half published by the earlier run then stays `PUBLISH_DIFFERENT_BYTES` and the report says why and what to persist (`resume::without_a_persisted_seal_a_different_rebuild_is_refused_and_says_so`). This is stated, not hidden: the builder kit's `same_request_same_bytes` is what makes it harmless for a reproducible builder.

**Without the run records** (a wiped run ledger), exactly this holds, and the crash sweep asserts it: a stage that needs another has no `stage` record to read and is `STAGE_NOT_ADMITTED`; a stage with no `needs` starts a fresh run, because there is no `run` record to pin against, and a changed machine cannot be detected there. Resume is then neither an optimisation nor a gate for that stage; it is a new run. The gates that read a record fail closed where a record is what they check (5.1, 5.7) and nowhere else.

### 5.5 Yank, retention and validation leftovers

- **No delete exists** in the trait, engine, ABI or CLI. It can be added later from history behind a new verb.
- **Yank (Proposal, section 0)** is explicit: `ucdk release yank --coordinate C --reason T --expect-hash H --run-id R [--run-ledger P]`. The engine takes the channel lease as `yank:<R>` (3.3), writes `yanking`, calls `yank`, reads back `Yanked`, writes `yanked`. The bytes stay fetchable by exact coordinate, and re-publishing is refused. Yanking an `Adopted` publication takes the same flag and the record says it was adopted. **A yank stops later stages:** the publication record names the run and stage that published it (3.3); when `--run-ledger` is given and holds that run, the yank also sets `yanked=1` on that stage's `stage` record under the run ledger's lease, so admission (5.7) refuses any later stage that needs it (`admission::needed_stage_with_a_yanked_coordinate_is_refused`). Without `--run-ledger` the yank says on its last stderr line that later stages of the run are not stopped (`yank::without_a_run_ledger_says_later_stages_are_not_stopped`).
- **Retention** is "forever unless yanked". A registry that can only delete is refused as a channel home.
- **Validation run id.** `vr-` plus the first 12 hex digits of SHA-256 over (run id, stage, validation), then `-k`, where `k` is the start counter in the validation's record. It is at most 63 bytes, label-safe and deterministic for a resume. A resume of a cut-short validation sweeps `k` before starting `k+1`, so a validation never runs on top of its own leftovers. An operator re-run (`--only validation:<name>`) also takes the next `k`.
- **Journal first.** `CreatedJournal::will_create` writes a `created` record in `Intent`, fenced, before the validator creates anything. A validator that cannot journal does not create. Removal needs both the stamp and the record: `Reaping` intent first, record dropped only after a read shows the object gone. A stamped object that no record names is reported by `leaks` (exit class 8) and never removed on that evidence. If the run ledger is lost, the `created` records are lost with it: the objects are found only by their stamp, reported, and removed by a person with the validator's own tools; a validator that `creates()` therefore refuses a non-durable run ledger (5.8).

### 5.6 Admission, supersession, source policy

The driver supplies `SourceFacts`. The core reads no CI variable and runs no git outside `Source`.

**The gate depends on the trigger (Decided here).** A `RELEASE` stage that is not `exceptional` runs only when `on_mainline == YES`; `NO` is `NOT_ON_MAINLINE`; `UNKNOWN` is `INDETERMINATE`. A `CHANGE_CHECK` stage is exempt from `on_mainline`, from supersession and from `--admission`: it runs on a revision under review, which is never on the mainline, so those rules would refuse every one of its runs. It has its own gate: `SourceFacts.revision` is non-empty and equals the head `Source` reports with a clean tree (otherwise `REFUSED`, `SOURCE`); it takes no channel lease, no seal ledger and no credential (3.3, 6); `on_mainline` and `is_tip` are recorded and gate nothing. Held by `run::change_check_runs_off_the_mainline`, `run::change_check_runs_when_the_mainline_is_unknown`, `run::change_check_on_a_revision_that_is_not_the_head_is_refused`, `run::a_release_stage_off_the_mainline_is_refused`.

An `exceptional` stage on a run off the mainline needs a one-line reason of 1 to 200 bytes, the revision equal to the one the driver started, and uses the repository's `exceptional_subject` and `exceptional_environment` (6); what it publishes carries `exceptional = true` in its `Held`. A release run is never a dry plan: `plan` and `run` are separate verbs.

**`--admission` (Decided here).** It applies to `RELEASE` stages. A run whose revision is no longer the tip (`is_tip == NO`) stops `SUPERSEDED` before any record is created, and so does a rerun, **unless** the run ledger holds an unfinished record of this run id and stage (a `stage` record `Intent`, reading as RUNNING or INTERRUPTED): that rerun resumes (a publish still applies the monotonic rule below, so a moved tip never lets an older build replace a newer one). `is_tip == UNKNOWN` is `INDETERMINATE`. The attempt number is not consulted, and no stage is called "first". `SUPERSEDED` is class 0 by design: the report says nothing was run and a driver that wants to tell it from a success reads the verdict, not the class. Held by `admission::a_moved_tip_with_no_unfinished_record_is_superseded`, `admission::a_killed_stage_resumes_with_attempt_2_at_the_tip`, `admission::a_killed_stage_resumes_after_the_tip_moved`, `admission::an_unknown_tip_is_indeterminate`.

**Monotonic channels (Decided here).** A `monotonic` channel refuses a build older than one it holds. The held builds come from the registry (`newest` returns each coordinate's `Held`, whose stamp was written at `put`), not from the ledger. Exceptional builds are never counted: they are reported, and never make a mainline run `SUPERSEDED` or `REFUSED`. Yanked builds are counted: a yank withdraws a coordinate, it does not un-build it. A set has several members, and the decision is made over all of them: the run is judged against the newest held build any member has, so one member with a newer mainline build decides for the set. A held build is newer than ours when its build number is greater, or equal with another commit. When `Source` says our revision is an ancestor of every newer build the run is `SUPERSEDED`; when unrelated, `REFUSED` (`SUPERSEDED_BY_NEWER`); when `Source` cannot tell, `INDETERMINATE`, never `SUPERSEDED`. This applies to `plan` too (`decide_supersede::equal_build_number_other_commit_supersedes`, `decide_supersede::exceptional_builds_are_not_counted`, `decide_supersede::cannot_tell_is_indeterminate`, `decide_supersede::any_member_with_a_newer_build_decides_for_the_set`, `decide_supersede::yanked_builds_still_count`).

### 5.7 Stage admission (Decided here)

A stage is the unit of a driver job. **One release is one run id across all its stages (Decided here):** the driver gives every stage job of a release the id of its workflow run, including a stage that waits for a human approval inside that workflow run, and a rerun of a stage raises its attempt. Stage S is admitted, before its first effect, credential presentation or registry call, only if for every stage N in `S.needs` the run ledger holds a `stage` record for N that is confirmed (every step `SUCCEEDED` or `NOOP`), is not marked `yanked`, and whose `set` equals the set hash recomputed from the store now. The ledger is the run's, so the record carries this run id by construction. A stage that holds a PUBLISH step additionally requires that the needed BUILD stage's `LOCAL_SET` validation record carries that same `set`. Otherwise S is `REFUSED` with `STAGE_NOT_ADMITTED`, naming the first needed stage and why (missing, not confirmed, yanked, another set). A promotion approved in a separate, later workflow run has another run id and another run ledger, so it finds no record of N: it is `STAGE_NOT_ADMITTED` and the message says to run a release's stages under one run id. That shape is out of scope (section 0), not worked around. S running in another driver job needs the run ledger of 5.8 to see N's record; without it the refusal is the answer. The later channel therefore receives the bytes the earlier stage validated (same set hash, recomputed from the store), and a digest copy between channels stays out of scope. A coordinate yanked after N confirmed stops S only through the `yanked` mark that `yank --run-ledger` writes (5.5): admission reads records and does not observe N's channel. Tests: `admission::needed_stage_not_confirmed_is_refused_with_zero_calls`, `admission::a_needed_stage_in_another_runs_ledger_is_refused`, `admission::set_changed_in_the_store_is_refused`, `admission::missing_run_ledger_fails_closed`, `admission::a_stage_after_an_approval_wait_in_the_same_run_is_admitted` (a `ManualClock` moved past the lease TTL and the attempt raised), `admission::needed_stage_with_a_yanked_coordinate_is_refused`.

### 5.8 Where state lives between jobs (Decided here)

Stages are separate driver jobs and the trust split (6) puts BUILD and PUBLISH in different ones, so four pieces of state must be visible to more than one job:

| State | Flag | Needs |
|---|---|---|
| channel ledger, one per channel | `--channel-ledger <path>` | a file every job that may publish to that channel locks: one filesystem shared by those jobs |
| run ledger, one per run | `--run-ledger <path>` | a file the stage jobs of one run can all read and write, one at a time (see the holder rule, 3.3); it may travel between sequential jobs as an opaque file (a CI artifact), carried out by the driver after each job writes it and back in before the next |
| artifact store | `--store <dir>` | a directory the BUILD job fills and the PUBLISH job reads; it may move between jobs as an opaque directory (a CI artifact), because the PUBLISH job trusts nothing in it: it runs `verify_member` on every member and recomputes the set hash (`SET_HASH` on a difference) |
| seal ledger | `--seal-ledger <path>` | durable across runs, with the store, for adoption (5.4); written by release BUILD jobs only; without it nothing is adopted |

Rules: (1) A PUBLISH step refuses an in-memory channel ledger outside a test build (`LEDGER`, `publish::memory_channel_ledger_is_refused`), and a validation whose validator `creates()` refuses an in-memory run ledger. (2) **What the file ledger can promise.** Its exclusion is an advisory file lock plus a lease expiry in wall-clock milliseconds written by each host. It is supported on one host, or on a filesystem where that lock really excludes (a local one, not a network filesystem whose lock is advisory per client), with host clocks within `MAX_CLOCK_SKEW` (5 s) of each other. ucdk cannot detect a filesystem or a clock that breaks this, and the doc states the risk instead of pretending otherwise: on a network filesystem without working locks, or with clocks further apart, two jobs can both believe they hold a lease, and the single-publisher guarantee reduces to the registry's coordinate uniqueness (5.2). On ephemeral runners with no shared path a pipeline holds a lease nobody else sees, and the same reduction applies; the monotonic check still holds because it reads the registry, not the ledger. A networked ledger is open question 15, not a prerequisite of PRs 3 to 12. (3) A run ledger that travels as a copy is correct only for stages that never overlap: stage jobs with a `needs` edge between them are sequential by construction, and independent stages must be serialised by the driver when their ledger is a copy (with a shared file the lease serialises them, 3.3). (4) A lost channel ledger changes no verdict about a coordinate (5.1). A lost run ledger refuses later stages (5.7) and leaves validation leftovers to `leaks` (5.5). (5) A publication record is audit data, so the channel ledger may be pruned of `Confirmed` records without changing a verdict; v1 does not prune, and each write rewrites the whole file, so a channel's write cost grows with its history, which question 16 recommends bounding with a compaction verb later.

## 6. Credentials (Proposal)

- **No standing credentials in v1.** A `PushIdentity` is `Anonymous` or `Federated`. The driver's platform issues a short-lived identity token, the source exchanges it for a short-lived push token for one repository, and it is held in a `Presented` value that cannot be printed, cloned or logged and zeroes on drop. A long-lived token is not a variant (Q6).
- **One writer per repository.** `push` is required, never defaulted, and no flag overrides it. A stage's `environment` must equal the `environment` field of the repository's `Federated` identity (`exceptional_environment` for an exceptional run off the mainline), never a value parsed out of `subject`; the static rule is `machine.environment_mismatch` (2), and at run time the identity token's environment claim is compared with the same field before the exchange, otherwise the publish is `REFUSED` before any request (`credential::exceptional_run_presents_the_exceptional_environment`, `credential::a_mainline_run_presents_the_normal_environment`).
- **Per surface and host.** A credential is presented only on the surface and host it was issued for; a mismatch is a local fault with zero requests. A public repository is read anonymously, so a read-back validation sees what a stranger sees.
- **Nothing secret crosses the ABI, the ledger or an error.** Configuration is flags. The source reads its platform's standard token variables in-process, nowhere else. An error is withheld when a server echoed the credential or any 16-byte run of it.
- **Trust split (Decided here).** A `CHANGE_CHECK` stage holds BUILD steps only, has no environment and cannot be needed by any stage, so code under review never reaches a push identity. A stage that holds a PUBLISH step holds no BUILD step (`machine.publish_stage_has_build`), so a builder, whose command is arbitrary, never runs in a process or environment that can present a push identity; the token is minted after admission and never reaches a child process. A `needs` edge is a data dependency; trust is per stage. The build side is held too: a set carries the stage and environment that produced it inside its hash, adoption of a stored set needs a seal record that only a release BUILD stage writes (5.4), and a `CHANGE_CHECK` stage is refused the seal ledger, so bytes that code under review left in a shared store are never adopted as a release build. Validators never receive a credential.
- `plan --check-credentials` mints and discards a token and reports `MINTED`, `NOT_UNDER_PLATFORM` or `NOT_FEDERATED`. The last two are never a pass.

## 7. CLI verbs and exit codes (Proposal)

Configuration is flags, with no positional arguments (as `ucdk-cli/src/args.rs` already requires, Exists) and no environment variables. Paths in a machine are relative to `--root`, not the working directory.

| Verb | What it does | Writes |
|---|---|---|
| `ucdk release check --machine <f>` | validate the machine; print stages and steps in order; every refusal names `<source>: line N` | nothing |
| `ucdk release plan --stage S [--only ...]` | what would build and publish, each coordinate's observed state (`WOULD_BUILD`, `WOULD_PUBLISH`, `ALREADY_PRESENT`), `new_names` (artifact names the channel has never held; a name is held if `newest(channel, name)` returns a coordinate of any version or `list` shows the name, because an index may lag, so a new version of a held name is not new; `observe` is a point read of one coordinate and is not used for this; only the selected stage's channels are read, no lookahead), the run hash | nothing |
| `ucdk release run --stage S --run-id R --attempt N --expect-hash H` (a BUILD stage also takes `--release-version V --timestamp-ms T`) | execute the selected steps and validations; create or resume the run | ledgers, store, registry |
| `ucdk release status` | read the ledger and observe each recorded and declared coordinate; say whether they agree | nothing |
| `ucdk release yank --coordinate C --reason T --expect-hash H --run-id R [--run-ledger P]` (Proposal) | explicit withdrawal | ledger, registry |
| `ucdk release leaks` | list stamped validation leftovers no record accounts for | nothing |
| `ucdk ledger show` | the ledger document as data | nothing |

Other flags: `--context key=value` (at most 32, untrusted), repeated `--only`, `--admission`, and the state flags of 5.8 (`--channel-ledger`, `--run-ledger`, `--seal-ledger`, `--store`).

**Selection and scope.** Selectors name what to run, never what to skip, so a step added later is not run by an old selective command. `--only step:x` runs the step without its validations. `--only validation:y` runs one validation alone against what is already there. Any selector makes the run `SELECTIVE`, and the report cannot present a selective run as `FULL`. A selector matching nothing is refused (`SELECTOR_NO_MATCH`) and lists the stage's steps and validations. The set hash in a report is non-empty only for a run that passed everything it selected. The final stderr line states scope and verdict.

**Exit table** (one function, `exit_class(verdict, reason, landed)`, used by the CLI, the C ABI and both SDKs; today's table has the classes 0, 2, 3, 4, 6 and 8, Exists, and this adds 5 and 7). `landed` is whether the engine recorded a landed coordinate or an announced created object in this run:

| Class | Code | Verdicts |
|---|---|---|
| done | 0 | `SUCCEEDED`, `NOOP`, `SUPERSEDED` |
| usage | 2 | malformed command line, selector or run id |
| refused | 3 | `REFUSED` with nothing landed: nothing external changed |
| failed, no effect | 4 | `FAILED` with nothing landed (a build failed, a validator failed before creating anything): safe to repeat |
| indeterminate (new) | 5 | `INDETERMINATE` with nothing landed: cannot tell; never a pass |
| failed, changed | 6 | `PARTIAL` (including a `REFUSED` after an earlier coordinate landed), `INTERRUPTED` (including `LEASE_LOST` and `LEASE_UNCONFIRMED`), `FAILED` with a landed record, `INDETERMINATE` with a landed record, and a panic from `run` or `yank`; run again with the same run id to resume |
| validation failed (new) | 7 | `VALIDATION_FAILED`; re-validate with `--only validation:<name>` |
| leaks | 8 | `leaks` found unaccounted validation leftovers; a run that finds leftovers reports them and keeps its own class |

Codes 2, 3 and 4 promise that no external effect landed. A step record listing a landed coordinate or an announced created object can never carry one of them: the class is a function of the verdict, the reason and `landed`, and the same verdict can have two classes (`FAILED` is 4 or 6). Retry advice derives from the class and a verb may make it stronger, never weaker; the class-6 advice of release verbs is "run the same stage again with the same run id" (the deploy advice, "plan again before running again", goes with the deploy verbs). Exit numbers appear in one file, held by a test. Error ids are the closed `Reason` set, carried as `UCDK-E-<NAME>`, asserted by tests and never matched by message text.

**The run verdict (Decided here).** Steps stop at the first one that is not `SUCCEEDED` or `NOOP` (5.1), so the run's verdict is the verdict of the step that stopped it, or `SUCCEEDED`/`NOOP` when none did (`NOOP` only when every step was `NOOP`). `landed` is a property of the whole run, not of that step: it is true when any step of the run recorded a landed coordinate or an announced created object. The class is then `exit_class(verdict, reason, landed)`: an earlier step that landed a coordinate and a later one that is `INDETERMINATE` is class 6, not 5, because the run changed something and "run again with the same run id" resolves both; the same holds for `REFUSED` and `FAILED`, which is why codes 2, 3 and 4 never carry a landed record. Held by `exit::no_effect_classes_never_with_a_landed_record` and `exit::indeterminate_with_a_landed_record_is_class_6`.

## 8. Testing plan (Proposal)

Rules that bind every layer: tests are Rust (SDK tests in their own language, scoped to the binding); every crate on its own reaches 99% of lines and branches (`cargo xtask coverage`, Exists), from its first PR, so each PR in 11 names the pure functions it lands and its test list is the minimum; a bug fix ships with a test that failed first; each test is documented by name and the behaviour it asserts; workflow `run:` lines are single `cargo xtask` verbs; **no test asserts timing**. Polls and backoff are counted through `Pause`; leases move through `ManualClock`; `LeaseGuard`, the engine and every seam take the clock or `Pause` as a parameter and `SystemTime::now` is read only in `SystemClock` (3.3). **Every pull-request suite uses in-process emulators and temporary directories and needs no network and no credentials; a live registry is never reached from CI.** The directory registry's kit runs against a temporary directory, the first real validator against an in-process stub, and a later OCI publisher against an in-process loopback stub.

| Layer | What is tested | How | Defect class it catches |
|---|---|---|---|
| `ucdk-core` | path and key grammar, hash hex rules, framing, Kahn order | unit; golden for key and framed hash text; order on cycles and unknown needs | a changed key or hash that orphans stored records; nondeterministic order |
| `ucdk-release-proto` | wire bytes, descriptor shape | golden bytes per message; descriptor breaking-change check; reserved numbers listed | a renumbered or retyped field |
| `ucdk-release` | machine validation, selection, set hash, run hash, `decide_publish`, `account_rows`, state codec | one unit test per refusal naming its rule; goldens for set-hash text; exhaustive tables of (presence, digest, yank, monotonic, history) to verdict; transition table total over every (state, event) | a rule silently not enforced; a set hash that includes the run or attempt that built it, or leaves out the producing stage; a vacuous pass |
| seams and kits | the contract every implementation meets | kits on the fakes; kit self-test with non-conforming stubs | a kit scenario that cannot fail |
| `ucdk-release-fake` | fakes obey their own kits; each fault switch does what it says | kit plus per-fault tests and call-log tests | a fake that hides the defect it should expose |
| `ucdk-ledger` | CAS, lease, fence, format, guard | conformance on both ledgers; file torn, corruption, newer-major tests; guard tests on `ManualClock` | a lost update; a torn file read as a ledger; a stalled holder writing |
| `ucdk-release-engine` | publish rules (5.2), resume (5.4), yank, sweep, admission | integration over the fakes with call logs; crash sweep | a put before its intent; a delete; a different digest overwritten |
| `ucdk-api`, `ucdk-capi`, `ucdk-cli` | conversions, exit table, ABI, text | round trips; exhaustive match; in-process ABI conformance; CLI goldens over a world of fakes | an unmapped verdict; ownership, panic and version defects |
| SDKs and generator | binding and generated code | wire goldens, shared scenario files, end to end through the real library, `sdk-fresh` | an SDK that disagrees with the core or the other SDK; stale generated code |

**Crash and fault sweep.** Run a machine to completion on a fake world and count seam calls and ledger writes. Then for every N, run again stopping at call N (a kill modelled as the end of the run function with ledger and fakes kept), run once more to resume, and assert:
- the channel holds each coordinate at most once and only with the sealed digest;
- no record is `Confirmed` without a read showing it after;
- every `put` is preceded in the combined log by its intent write;
- every created resource has a `created` record written before the create;
- after a sweep no fake resource carries the validation run id;
- the final report equals the uninterrupted run's except for attempts.

It runs on the memory and the file ledger, a pass with the run ledger wiped between the stopped run and the resume (the run must then refuse a stage that needs another, never pass it, and leave no registry state changed), and a further pass runs the same releases through `lose_answer_after_commit` at every put. Lease checks: a dead holder blocks the next run until the clock passes lapse plus skew; a holder whose clock moved past its lease is refused at its next write and changes nothing after.

**Gates are proven.** For each refusal in 5.2, 5.6 and 5.7, a test asserts that the registry's commit log is empty and the credential source saw zero presentations. A run that has lost its run lease, or its channel lease, makes zero registry puts after the loss (`publish::run_lease_lost_means_zero_puts`, `publish::channel_lease_lost_means_zero_puts`). A panic during a publish ends in class 6 (`abi::release_run_panic_is_class_6`).

**End to end.** One scenario set (machine, flags, expected class, golden text) is run in process by the CLI tests and through the built library by the Python and TypeScript tests, comparing the same expected values (the mechanism exists today for deploy scenarios: `ucdk-cli/tests/scenario.rs` and the SDK tests read the same data): `build_publish_validate`, `rerun_is_noop`, `resume_after_kill_during_publish`, `conflict_refused`, `validation_failed_exit_7`, `indeterminate_is_never_green`, `selective_run_says_so`, `superseded_runs_nothing`, `yank_then_republish_refused`, `leaks_reports_unrecorded_object`, `resume_with_new_run_id_after_partial_publish`, `stage_needing_an_unconfirmed_stage_is_refused`, `long_build_under_a_manual_clock` (a build whose clock passes the TTL several times, with beats and then silent), `change_check_on_a_pull_request_revision`, `stage_after_an_approval_wait_in_the_same_run`.

**Where it runs.**

| Suite | Pull request | After merge or on demand |
|---|---|---|
| `check` (fmt, clippy, deny, SPDX, run lines, direction, purity, unsafe scope, public-text lint, sign-off, sdk-fresh) | yes | yes |
| unit, golden, kits on fakes, crash sweeps, 99% floors (`coverage`) | yes | yes |
| ABI conformance in process, header and symbol check | yes | yes |
| SDK conformance (`sdk-test`) | Linux | all supported platforms |

| a real implementation's kit against its own emulator (in its own crate) | yes | yes |
| a registry over the network | never | explicit flag, named account, no CI |

## 9. Design decisions and the defects they prevent (Proposal)

Each is a decision of this project, stated as behaviour with its mechanism.

- **One description of the machine.** The machine message is the only description of stages. The core reads no CI-vendor variable; a driver gets stage names, order, needs and environments as data from `check`. There is no second hand-written description to keep in agreement.
- **Durable progress and resume.** Run, step and validation records live in a leased, fenced ledger. A rerun skips confirmed steps with unchanged inputs and is correct without them.
- **Evidence is not authorization.** The gate between stages is a ledger fact written under the lease (a confirmed `stage` record for this run id) plus the set hash recomputed from the store (5.7); the rule is stated, not implied. The report is derived data; the exit class is what a driver branches on.
- **Validations are not tied to one ecosystem or to PUBLISH.** A validator is a registered kind with typed options, attachable to any step, reading a local set or a channel read-back.
- **One publisher seam for every artifact type.** The kit forces every type through the same flow, so credentials and flows cannot diverge by type.
- **Permanence with explicit yank.** No delete, no overwrite, burned coordinates; `put` is an atomic create-if-absent, and a registry that cannot promise that is refused as a channel home.
- **Visibility is per repository**, not per channel.
- **Ecosystem facts live in typed metadata arms.** The core compares names and digests only and keeps no copied tables.
- **A closed `Reason` enum**, never message matching.
- **The build stamp is an input** from one `Source` implementation, not derived in several places.
- **A missing store entry is a named refusal**, not an empty directory that happens to fail later.
- **Wire goldens and the minor rule exist from the first message.**
- **Every validation object is recorded before it is created** and swept after.
- **Run identity is supplied by flags**, recorded, never trusted, and gates nothing.

## 10. Open questions, each with a recommendation

1. **Machine text form.** Does the CLI read only binary protobuf, or also a text form? Recommend: binary plus canonical JSON through `prost-reflect`'s serde support behind one flag; people author through SDKs. Verify the dependency passes `cargo deny` in the model PR before taking it.
2. **Ledger scope.** One per channel plus one per run, or a single ledger? Recommend three kinds (3.3): one per channel, one per run, and a seal ledger that outlives runs so a new run id can adopt a sealed set (5.4). A build never holds a channel lease and a change check never touches a channel or the seal ledger. A write that spans both (step record, then publication record) is covered by the crash sweep.
3. **Failure policy.** Stop at the first failed coordinate or attempt every independent member? Recommend stop at the first (one rule); resume on rerun. Revisit with concurrency.
4. **Group artifacts.** Is "one group artifact last" a model rule? Recommend no: a group is an artifact whose `needs` name its members. A closure rule (every requirement names another member) is the named `set-closure` validation a publishing stage cannot omit (`machine.publish_stage_needs_validated_build`, 2; 4.4), not a core rule.
5. **First artifact types.** Recommend `FILE` and `OCI` first, real publishers last. The enum names the other types now so protos do not change when they arrive.
6. **Registries without a federated identity.** Recommend not supported in v1. Add a reference variant later only with an explicit repository field, refusal of anything but a name, and a warning in `plan`.
7. **Where the stamp comes from.** Recommend one `Source` implementation that runs fixed git argv commands through a `ProcessRunner` seam (never a shell, scripted in tests), refusing a shallow clone or dirty tree.
8. **Builder provenance.** `ProducedBy` (run and attempt) is recorded and not hashed; the producing stage and environment are hashed (2). Recommend a signed provenance statement attached to the set later; not v1.
9. **Process builder.** Recommend argv only, no shell, output to log files, an injected monotonic clock for deadlines, a scripted runner for tests.
10. **More than one platform.** Recommend one run per platform in v1; a group hash and an approval binding it come with a second platform.
11. **First real registry.** Recommend a directory channel (no network, a complete `Publisher`, usable to validate before publishing), then OCI. Network clients wait for the dependency and TLS decision.
12. **Exceptional runs.** Recommend the field and the rules in 5.6 land with the model, but the verb path ships only when a real publisher exists.
13. **Ledger minor rule.** A new state name makes older readers refuse the document (3.3). Recommend accepting that, in PR 8 only, and amending the format header's rule, over raising the format major, because the golden bytes of the existing layout then keep reading.
14. **ABI numbering at the deletion.** Decided in 3.3: major 0 with a minor bump, and while the major is 0 the loader requires an exact minor match, so a stale SDK is refused by name. Raising the major to 1 at the deletion is the alternative and is not recommended, since section 5 of the architecture promises nothing before the first release.
15. **A networked ledger.** v1 arbitrates only runners that share a ledger file (5.8). Recommend a later ledger backend behind the existing `Ledger` trait (its conformance suite is the contract) when a first user needs cross-runner exclusion; it is not a prerequisite of PRs 3 to 12.
16. **Channel ledger compaction.** Recommend a later verb that prunes `Confirmed` publication records, which is safe because the registry is the authority (5.1); v1 accepts a write cost that grows with history.
17. **Promotion across workflow runs.** v1 admits a stage only through records of its own run id (5.7), so a promotion approved in a later, separate workflow run is refused by name. Recommend keeping that and, if a first user needs it, a later explicit `--admit-from <run id>` that reads the earlier run's ledger read-only and re-observes the needed coordinates, rather than loosening admission.

## 12. Riskiest choices

1. Deleting `ucdk-engine` wholesale while moving its lease lifecycle into the ledger: the lease tests are the strongest proof of the fencing claims, and `guard.rs` is a rewrite over a bare ledger, not a move. 3.1 accounts for all 14 tests by name and by disposition, and the review of PR 2 checks each ported test keeps its ledger-side assertions.
2. Generalising `ucdk-ledger` off the provider types while keeping the on-disk format byte-identical: the golden file is the only guard. The same PR adds `Snapshot.fence`, `Snapshot.lease`, `Snapshot.at` and `FileLedger::open_read_only` (3.1), a public ledger API change that every release PR inherits.
3. `ucdk_ledger_show` as the one verb added in the deletion PR. If judged scope creep, the ABI suite has nothing real to call, and `SessionConfig.holder` and `test_clock_ms` would have no consumer until PR 9; 3.4 is what keeps them observable and tested.
4. The seam has no delete and no overwrite, so a registry that supports only replace or delete is refused; some real registries may need an explicit exception later.
5. Two ledger kinds with writes that span both: the crash sweep must cover the gap between a step record and a publication record, and renewal must cover both leases before each put (3.3).
6. No standing credentials in v1 may exclude a registry a first user needs.
7. Resume keyed by an input digest refuses a legitimately edited retry; users must choose a new run id, and the error must say so.
8. Stop at the first failed coordinate favours simplicity over throughput.
9. Authored row accounting puts a burden on validator authors; the kit must make the failure obvious.
10. `Origin::Adopted` for identical bytes someone else published makes "ours" depend on bytes, not on who wrote them; yank needs the explicit flag for that reason.
11. Reading no CI variable pushes ref, run id and revision correctness to the driver; a driver that lies is detected only by the `Source` check of the revision.
12. A new ledger state name makes older readers refuse the document (question 13); an operator running an old binary against a new ledger gets a refusal, not a silent misread. The change is confined to PR 8.
13. Ephemeral runners with no shared ledger path get no cross-pipeline exclusion (5.8); the registry's uniqueness and the monotonic check on stamps are then the only guards.
14. `put` as atomic create-if-absent excludes registries that only replace; the first OCI publisher must be able to declare it (4.3).
15. Adoption of a sealed set trusts the seal ledger: whoever can write a `Confirmed` seal record can make a stored set adoptable. ucdk refuses the seal ledger to `CHANGE_CHECK` stages and hashes the producer into the set, but it cannot know which driver jobs are trusted; the driver must give `--seal-ledger` to release BUILD jobs only (5.4).
16. Leases of long builds and validations are kept by explicit progress events, not by a timer. A builder that is silent for longer than the TTL is recovered only by re-acquiring before the Confirmed write, and only when no other writer wrote meanwhile (3.3).
17. A file ledger's exclusion is an advisory lock plus host clocks. It holds on one host or a filesystem with a working lock and clocks within the skew bound; ucdk cannot detect either failing (5.8).
