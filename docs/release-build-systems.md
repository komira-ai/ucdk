# ucdk release: build-system details

Status: design (Decided where a section says so, otherwise Proposal). This page holds three things that [release.md](release.md) summarises and that need more room than that file has under the project's size bound: section 1.1 (what the build-system model changes in the earlier design, part by part), section 2.1 (the exact rule that matches a flag against the flags ucdk owns) and section 4.2.1 (the `OutputFiles` seam and the report files a test invocation writes). Section numbers below without a file name are those of release.md.

## 1.1 What the build-system model changes (Decided)

The spine of the design is `Machine { BuildSystem build_system; repeated Stage stages }`, `Stage { repeated Action actions; repeated Validation validations }` and `Action { oneof kind { Build, Test, Publish, Smoke }; repeated Validation validations }` (2). Every later section follows it: the machine rules are stated per action kind and per validation holder (2), the hashes cover the build system and the targets as 2 says, the engine runs a stage's actions in order and then its validations (5), records are per action (3.3), selectors are `action:<name>` and `validation:<name>` (7), and the testing plan and the PR sequence are organised by action kind (8, 11). What this changes in the earlier design, part by part:

| Part of the earlier design | What happens | Why |
|---|---|---|
| `Step`, `Stage.steps`, `step` ledger records, selector `step:<name>` | **Become** `Action`, `Stage.actions`, `action` records, `action:<name>`. `Build { platform, artifacts }` and `Publish { platform, artifacts, channel, attempts, polls }` keep their fields; `Test` and `Smoke` are new; `Stage` gains `validations`. | A stage is an ordered list of actions with their validations. |
| `ArtifactDecl.builder` and the `Command` message | **Go.** `ArtifactDecl.target` (`Target`: label, flags, environment) replaces them. | A build is the build system pointed at a target, not an arbitrary command. |
| `ArtifactDecl.independent_version` | **Goes** (number 6 reserved). Every member carries the release version. `MEMBER_VERSION` stays as the check that a stored manifest equals the stamp. | The manifest is composed by ucdk, and the only source of a different version was the builder's own manifest. |
| The `Builder` trait, `BuildRequest` (with `inputs`, the verified members a build needs), `Builder::plan`, `FakeBuilder`, the builder kit | **Go.** `BuildSystem` (4.2) replaces them, with `Buck2` and `Bazel` implementations over a `ProcessRunner` and an `OutputFiles`, a `FakeBuildSystem` as the executable specification and `run_build_system_kit`. A build no longer writes into the store through an `EntryWriter` or returns a manifest: the engine copies the one located output and composes the manifest. | The build graph carries a build's dependencies, so ucdk hands a build no members. |
| The process builder (PR 12), its placeholders `{out_dir}`, `{platform}`, `{revision}`, `{source_commit}`, `{build_number}`, `{timestamp_ms}`, the empty output directory per build, and its `process::` tests of them | **Go.** One closed list of placeholders in flag and environment values replaces them (2), and the Buck2 and Bazel implementations replace the process builder. `process::the_environment_is_not_inherited` is kept as a `ProcessRunner` test. | Process spawning is a `ProcessRunner` concern, and a placeholder is how the stamp reaches the build system. |
| The shared stage budget (whole seconds left on a monotonic clock), the builder kit scenario `timeout_is_reported_not_hung`, "a build that times out is `FAILED`" | **Go.** ucdk sets no deadline on a build or a test. The build system's timeouts and the driver's job limit do; a job that is killed leaves a lapsed lease and a resume (5.4). | Scheduling and time limits belong to the build system and the driver. |
| The builder heartbeat as a compute concept | **Becomes** progress events of a build-system invocation. The `Heartbeat` seam stays, and the `ProcessRunner` calls `beat()` on each chunk of output and each exit poll of a build or a test; `Stop` kills the child. Lease renewal is unchanged (3.3): `renew_if_due` on a beat and the re-acquire before a Confirmed write. | A build or test invocation can outlive the lease, which is all the heartbeat was for. |
| Build-inputs hash fields: builder executable, builder args, `independent_version` | **Go.** The build system (kind, binary, config file, mode, flags, environment), each declaration's target (label, flags, environment) and labels come in (2). | They are what decides a member's bytes and manifest. |
| `machine.publish_stage_has_build`; `machine.readback_on_build`; `machine.local_set_without_build`; `machine.step_without_action` | **Become** `machine.publish_stage_runs_code` (it now covers Test actions too), `machine.validation_placement` and `machine.action_without_kind` (the rename of the last). `machine.validation_placement` no longer lets `SET_CLOSURE` sit on a stage: the earlier "stage of a Build action" placement was a check that admission never read, and the one closure admission reads is the Build action's (5.7). It still allows `SET_CLOSURE` on a Publish action, where it is now evaluated in the preflight, before any grant exchange, and no longer between the stage and commit phases (5.2). New rules cover the build system, targets, placeholders, tests, smoke actions, scopes, a stage with no actions and an empty artifact list (2); `machine.schema_version`, `machine.bad_name` and `machine.unknown_stage` are kept and now listed there. | Code runs only in a stage that cannot present a push identity; a pure check of the set makes no exchange; and the rule list is the code's rule list. |
| Validations that run their own commands (the registered `Validation.validator` kind name, `options`, authored `rows`, the `Validator` trait, `FakeValidator`, the validator kit) | **Go.** A test is a build-system target (a Test action). What is kept is what is neither a build nor a test: `Subject.LOCAL_SET` with the validator `set-closure` becomes the built-in kind `SET_CLOSURE`, and `Subject.CHANNEL_READBACK` becomes the built-in kind `CHANNEL_READBACK`. Both are evaluated by ucdk (a pure function of the set; a read of a channel through the `Publisher`), their rows are derived, and there is no third kind. | A check that runs code is a test target; a registry of validator kinds would be a second way to run commands. |
| Everything that existed because a validator could create objects outside ucdk: the validation run id (`vr-<hash>-k`), `CreatedJournal`, `created` records, `ValidationStamp`, `sweep` and `remove`, the `leaks` verb and `LeaksRequest`, `ValidationReport.leftovers` and `validation_run_id`, the `k` payload key, the rule that a creating validator refuses an in-memory run ledger | **Go.** Exit class 8 stays in the enum the deletion PR keeps, no release verdict maps to it, and PR 10 removes it with the match. | No kept validation creates anything. What a test target creates outside ucdk is the test's and the build system's concern: ucdk cannot stamp or sweep it and does not claim to. A later validator kind that creates objects brings its own journal with its own design. |
| `Publisher::put`, the one-call write | **Becomes** `stage` and `commit` (4.3). A channel that cannot stage skips the stage phase and `commit` does the atomic create-if-absent that `put` did. | Permissions are per phase, and some registries hold staged bytes without publishing them. |
| `CredentialSource`, `Presented`, `plan --check-credentials` reporting `MINTED`, `NOT_UNDER_PLATFORM`, `NOT_FEDERATED` | **Become** `GrantSource`, `Grant` and a check that reports one of those per phase, plus `REFUSED`. `Federated` gains the scope each phase needs (stage, commit and, on a `PRIVATE` repository, read) and the other claims the issuer pins; `grant` ledger records and the reasons `BUILD_OUTPUT` and `PUBLISH_STAGE` are new (2, 3.3, 6). | Stage, commit and read are separate grants. |
| Verbs | `ucdk release leaks` goes. `ucdk release trust` (print the trust a machine expects) and `ucdk release abort` (discard staged state) are new (7). | Bootstrap needs the expected trust as data; a failed commit needs a way to give the staged state back. |
| The four kits (builder, publisher, validator, store) | The builder and validator kits go. Six remain: `run_build_system_kit`, `run_process_runner_kit`, `run_publisher_kit`, `run_grant_source_kit`, `run_store_kit` and `run_output_files_kit` (4.6). | A seam each, and one contract per seam. |
| The `input` digest of an `action` record ("the action as authored, the build system, the set hash, platform, revision") | **Gets a byte layout** with its own domain tag and fields per action kind (2). Validations, the attempt and poll bounds and the timestamp are not in it. | It decides `NOOP` versus `INPUTS_CHANGED` for every action kind, so two implementations must agree on its bytes. |
| The stage record's `confirmed` ("every action is `Confirmed`") | **Becomes** the conjunction of every action and every action-level and stage-level validation, written last (3.3, 5.7). | A stage whose read-back failed must not admit the stage that waits for it. |
| Open questions 4, 8, 9, 11 and 15; risks 5, 9, 16 and 19; PRs 3 to 8 and 10 to 13 | Reworded or re-scoped. Questions 18 to 23, risks 20 to 24 and PR 14 (the package-registry channel kind) are new (10, 12, 11). PR 3 is split into 3 and 3b to 3d, and PR 12 into 12a and 12b (11). | The sections follow the spine, and the sizes follow the size rule. |

## 2.1 Reserved flags: how an element is matched (Decided here)

ucdk's own flags come after the author's two flag lists (the argument vector of 2, element 7), so that no author can override them, and `machine.reserved_flag` refuses an author flag that names one. The refusal has to be decidable from one argv element, because a flag is one element (`--output=files`) or two (`--output`, then `files`), and it has to cover the spellings a parser reads as the same flag. The lists are closed and per kind:

| Kind | Listed flags (the names without `--`) |
|---|---|
| Buck2 | `show-output`, `show-full-output`, `show-simple-output`, `show-json-output`, `show-full-json-output`, `event-log` |
| Bazel | `output`, `build_event_json_file`, `build_event_text_file`, `build_event_binary_file`, `symlink_prefix` |

**The rule.** For one element `E` of the base `flags` or of a target's `flags`, and the listed flags of the machine's `build_system.kind`:

1. `E` equal to `--` is refused, for both kinds: it ends option parsing, so ucdk's own flags, which follow, would be read as positional words.
2. For Buck2, `E` that starts with `@` is refused: it names an argument file whose contents ucdk cannot read and which could hold a listed flag. (The `@<mode>` element of the argument vector is generated by ucdk and is not an author flag. Bazel has no such element form.)
3. `E` that does not start with `--` is accepted: it is a value (`files`), a short option (`-c`) or a word.
4. Otherwise the **name** is the text after `--` up to the first `=` (all of it when there is none). A name that is empty is accepted. The name and every listed flag are compared with `-` read as `_`.
5. The **candidates** are the name and, when the name starts with `no`, the name with that `no` and one following `_` removed (the negated spellings `--nooutput`, `--no_output`, `--no-event-log`); an empty candidate is dropped.
6. `E` is refused when some candidate equals a listed flag of the kind. For Buck2 it is refused as well when some candidate is a strict prefix of a listed flag, because Buck2's parser may infer a long flag from a prefix. For Bazel a strict prefix is accepted, because `--build` and `--nobuild` are Bazel's own flags and Bazel's parser does not abbreviate. A name longer than a listed flag that only starts with it (`--output_filter`, `--build_event_json_file_path_conversion`) is not a candidate match and is accepted.

Both lists are checked, for the machine's own kind only: a name listed for Bazel is not refused in a Buck2 machine. The two behaviours the rule assumes of the parsers (Buck2 may infer a prefix, Bazel does not; each reads the negated spellings) are exactly the ones the on-demand job confirms (question 19); a behaviour it does not confirm changes the clause and its test, not the structure of the rule.

| Element | Buck2 | Bazel |
|---|---|---|
| `--event-log=x`, `--event-log` | refused (listed) | accepted (not listed) |
| `--event_log` | refused (`_` read as `-`) | accepted |
| `--no-event-log` | refused (negated) | accepted |
| `--event` | refused (prefix) | accepted |
| `--output=files`, `--output` | accepted | refused (listed) |
| `--nooutput`, `--no_output` | accepted | refused (negated) |
| `--build_event_json_file=x` | accepted | refused (listed) |
| `--build_event` | accepted | accepted (prefix, not refused for Bazel) |
| `--build`, `--nobuild` | accepted | accepted |
| `--output_filter=x`, `--build_event_json_file_path_conversion` | accepted | accepted (longer name) |
| `--` | refused | refused |
| `@argfile` | refused | accepted |
| `files`, `-c`, `release.version=1` | accepted | accepted |

Tests (PR 3, `ucdk_release::flags`): `flags::an_element_equal_to_a_listed_flag_is_refused`, `flags::a_listed_flag_with_an_equals_value_is_refused`, `flags::a_negated_listed_flag_is_refused`, `flags::a_strict_prefix_of_a_listed_buck2_flag_is_refused`, `flags::a_strict_prefix_of_a_listed_bazel_flag_is_accepted`, `flags::hyphen_and_underscore_spellings_match_alike`, `flags::a_longer_name_that_only_starts_like_a_listed_flag_is_accepted`, `flags::a_value_or_a_short_option_is_never_matched`, `flags::a_flag_listed_for_the_other_kind_is_accepted`, `flags::the_end_of_options_marker_is_refused_for_both_kinds`, `flags::a_buck2_argfile_element_is_refused_and_a_bazel_one_is_not`; each of the table's rows is one case of the first test it names or of the table-driven `flags::the_match_table_of_the_design_is_the_function` (which holds the rows above as data, so this page and the function cannot drift). `machine::a_reserved_flag_is_refused` reaches the same function through a whole machine, once for the base list and once for a target's list.

## 4.2.1 `OutputFiles`: the seam, its fake, its kit and its reader (Decided here)

`OutputFiles` is the read-only view of local files that `Buck2` and `Bazel` use for the two things they read from the disk: the files of the output that the build system's own listing named (existence, shape, the relative paths under a directory, the bytes `copy_out` copies) and the report file of a test invocation (4.2, item 3). It has no write method, so a build system implementation cannot change the output tree, and the `EntryWriter` of the store is the only way into the store.

```rust
pub trait OutputFiles: Send {
    fn stat(&mut self, path: &str) -> Result<Option<FileKind>, SeamError>;    // what is at `path`; a symlink is `Symlink` and is not followed; `Ok(None)` is "nothing there"
    fn list(&mut self, path: &str) -> Result<Vec<DirEntry>, SeamError>;       // every entry below the directory `path`, recursively, sorted bytewise by `rel`, each with its kind
    fn read(&mut self, path: &str) -> Result<Vec<u8>, SeamError>;             // the bytes of the regular file at `path`; a symlink, a directory or nothing there is `Permanent`
}
pub enum FileKind { File, Directory, Symlink }
pub struct DirEntry { pub rel: String, pub kind: FileKind }   // rel: relative to the listed directory, "/" separated
pub fn entry_path(dir: &str, rel: &str) -> Result<String, SeamError>;   // `dir` + "/" + `rel`, or `Refused`; pure, in `ucdk-release-seams`
```

**Contract.** Every `path` is absolute with no `..` part, and is the build system's own answer, an entry path made by `entry_path`, or a file under the engine's report directory; a `path` that is relative or has a `..` part is `Refused`. **A read has one shape (Decided here).** `read(path)` reads the regular file at `path`, and nothing else is a read: a located `FILE` output that `copy_out` copies, and the report file of a test invocation (`Invocation.report`), are single files with no directory around them, and are read as `read(path)`. A file under a listed directory is read as `read(entry_path(dir, rel)?)`, where `entry_path` accepts a `rel` only when it is non-empty, has no empty part, no `.` or `..` part and is not absolute, and otherwise answers `Refused`; the rule about `rel` is therefore in one pure function and not in each reader. The three methods answer the three questions `Locate` (4.2, item 2) and `copy_out` need, each with one method: *is there something, and what* (`stat`), *what is in it* (`list`, with the kind of every entry, so a symlink is told from a file and a directory without a second call), and *its bytes* (`read`, of one regular file). Only the final component of `path` is looked at without following: `stat` of a symlink is `Symlink` whether it points at a file, a directory or nothing, and `list` reports a symlink entry and does not descend into it. Absence is told from failure in one place: `stat` answers `Ok(None)` for a path where nothing is, and `Unknown` when the disk could not be asked, so the engine never takes an I/O failure for a missing output or the reverse. `list` of a path that does not exist, or is not a directory, is a named error (`Permanent` with the path), never an empty answer, because an empty listing would read as "no output"; `read` of a file that does not exist, is a directory or is a symlink is `Permanent` with the path as well (both are the answer for a caller that skipped `stat`; `Buck2` and `Bazel` always call `stat` first, so a `Permanent` here means the tree changed under them). How `Located.shape` is found is therefore the same for both build systems, whatever their listing gives (Buck2's listing is a label and an absolute path; Bazel's is a relative path joined to the execution root): the engine-side code of `Buck2` and `Bazel` calls `stat` on the path and maps `None` and `Symlink` to `BUILD_OUTPUT`, `File` and `Directory` to the shape, and for a directory lists it once and maps any `Symlink` entry to `BUILD_OUTPUT`. A read answers the bytes the file holds at the call, which is what lets the engine copy and then verify from the store (4.2). No call changes the tree. A failure to read that is not one of those (the disk failed) is `Unknown`, because the engine cannot tell what is there.

**Where it lands (Decided here; the rule is in 11).** The trait, `FakeOutputFiles` and `run_output_files_kit` land in PR 4 with the other seams, and the real reader lands in PR 12a with `Buck2` and `Bazel`, the first real implementations that use it, so 12a cannot be accepted before it exists and passes its kit. It is not part of the store PR 12b. The `Buck2` and `Bazel` tests run over a `FakeProcessRunner` and a `FakeOutputFiles` in every pull request. `FakeBuildSystem` does not use it: it is the specification of what the build-system seam promises, and it makes its outputs and its reports itself.

Kit scenarios (`run_output_files_kit`, 4.6), fourteen, each with the one non-conforming stub that the kit's self-test feeds it and that the scenario must fail:

| Scenario | What it asserts | Stub it must fail |
|---|---|---|
| `a_listing_is_sorted_relative_paths` | `list` answers every entry below a directory, nested ones included, sorted bytewise by `rel` | a listing in directory-walk order |
| `a_listing_names_the_kind_of_every_entry` | each entry is `File`, `Directory` or `Symlink` | a listing that calls every entry `File` |
| `a_listed_symlink_is_never_descended` | a symlink to a directory is one entry of kind `Symlink` and nothing below it is listed | a listing that follows the link |
| `stat_tells_a_file_a_directory_a_symlink_and_nothing_apart` | four paths, four answers (`File`, `Directory`, `Symlink` for a link to a file and one to a directory and one dangling, `None`) | a `stat` that follows links |
| `a_missing_path_is_none_from_stat_and_permanent_from_list_and_read` | absence is `Ok(None)` from `stat`; `list` and `read` of it are `Permanent` naming the path | a `list` that answers an empty listing |
| `listing_a_file_and_reading_a_directory_or_a_symlink_are_refused` | each is `Permanent` with the path | a `read` that follows a symlink |
| `a_single_file_output_is_read_without_a_rel` | a regular file at an absolute path with no directory around it (a located `FILE` output) is read by `read(path)` and answers its bytes | a `read` that needs a listed directory above the file |
| `a_report_file_is_read_directly` | a file in a scratch directory, named by the invocation's report path, is read by `read(path)` and answers its bytes | a `read` that answers `Permanent` for a path it was not listed under |
| `reading_a_directory_is_refused_even_when_it_is_the_located_output` | `read` of a directory, the path `stat` called `Directory`, is `Permanent` with the path | a `read` that answers an empty file |
| `a_path_that_is_relative_or_climbs_is_refused` | `stat`, `list` and `read` of a relative path and of a path with a `..` part are `Refused` | a `read` that joins or resolves the path unchecked |
| `an_entry_of_a_listed_directory_is_read_through_its_joined_path` | for every `File` entry of a `list`, `read(entry_path(dir, rel)?)` answers that file's bytes | an `entry_path` that drops a nested part |
| `a_read_returns_the_file_as_it_is_at_the_call` | a file changed between two reads is read with its new bytes | a reader that caches the first answer |
| `no_call_changes_the_tree` | a tree, with the bytes of each file, compared before and after every method is equal | a `read` that touches the file |
| `a_dot_part_a_repeated_slash_and_a_trailing_slash_name_the_path_they_stand_in` | a `.` part, an empty part and a trailing slash (a file's and a symlink's too) name nothing of their own: the reader strips them itself, and the slashed path answers as the unslashed one | a reader that refuses a path with a `.` part |

Each is run against `FakeOutputFiles` in PR 4 and against the real reader over a temporary directory in 12a (`output_files::*`, 11). `entry_path` is pure and is tested once, in PR 4, where it lands: `output_files::entry_path_joins_a_checked_rel` and `output_files::entry_path_refuses_an_empty_dot_dotdot_or_absolute_rel_and_an_empty_part` (it answers `Refused` for `""`, `"."`, `".."`, `"a/../b"`, `"/a"` and `"a//b"`). The faults of `FakeOutputFiles` that the `Buck2` and `Bazel` tests use are `missing`, `unreadable`, `symlink_at` and `changes_after_listing` (4.5 of release.md).

## 4.2.2 The report files (Proposal; confirmed by the on-demand job, question 19)

A Test invocation is given a report path by the engine (2, layering: `<scratch>/<invocation>/events.json-lines` for Buck2, `events.json` for Bazel). Both files are JSON lines (one JSON object per line), so the pure `ucdk_release::test_report` reads them with `serde_json`, which 3.2 already lists for OCI layouts, and **no XML parser and no other dependency is added**: Bazel's per-case `test.xml` files are not read.

- **Buck2** (`events.json-lines`): `ran` counts the lines that carry a `TestResult` record, anywhere in the event, whose `status` is `PASS`, `FAIL`, `FATAL`, `TIMEOUT` or `RERUN`, written as the name or as the `TestStatus` enum number (1, 2, 5, 6 and 8; Buck2's event log writes this protobuf enum field as a number). Any other status of any type, such as `SKIP`, `OMITTED`, the listing statuses, `UNKNOWN`, `INFRA_FAILURE` or `NOT_SET_TEST_STATUS`, is not counted.
- **Bazel** (`events.json`, the build event protocol's JSON form): `ran` is the sum, over the lines that carry a `testSummary` for the target, of its `totalRunCount`, counting a summary only when its `overallStatus` is none of `NO_STATUS`, `FAILED_TO_BUILD` and `TOOL_HALTED_BEFORE_TESTING`. An intended line, whose field names are fixed with the transcripts of PR 3c: `{"id":{"testSummary":{"label":"//release:set_test"}},"testSummary":{"totalRunCount":1,"overallStatus":"PASSED"}}`. This counts runs of the target and not cases, which is what the build event protocol reports without reading the target's own result file; a target that runs once and exercises nothing passes, which is the build system's property and is stated in risk 22.
- Any other outcome (no file, a line that is not JSON, no counted event) is `ran = 0`, and a target with `ran = 0` is not a pass, whatever the exit code (`test_report::a_missing_or_unparseable_report_is_zero_cases`).

Tests (PR 3c): `test_report::a_buck2_event_log_counts_results_that_are_not_skips`, `test_report::a_buck2_status_given_as_its_enum_number_counts_when_it_means_a_test_ran`, `test_report::a_bazel_event_file_counts_the_runs_of_each_test_summary`, `test_report::a_bazel_summary_that_tested_nothing_counts_no_run` (`NO_STATUS`, `FAILED_TO_BUILD` and `TOOL_HALTED_BEFORE_TESTING` each, with a `totalRunCount` above zero), `test_report::a_missing_or_unparseable_report_is_zero_cases`. `ucdk-release` keeps the dependency list of 3.2, so `cargo deny` and the purity gate see nothing new.
